## Checkpoint Resolution

The plan opened with a `checkpoint:decision` (blocking-human, gate=blocking-human) confirming the provider availability & slot data model shape. The user selected the **recommended** option:

- Separate `users` (auth/login accounts) and `patients` (operational profiles that may have no login) tables — satisfies both IAM-01 (self-registration) and PPL-01 (front-desk-created profiles without a login).
- Provider availability modeled as **weekly availability templates** (config/rules), not materialized slot rows.
- `provider_slots` table created now but left **empty** — no 90-day horizon/regeneration logic this phase (Phase 2's job).
- `provider_slots` carries a **live PostgreSQL GiST exclusion constraint** (`EXCLUDE USING gist (provider_id WITH =, tstzrange(start_time,end_time) WITH &&) WHERE (status <> 'cancelled')`, `btree_gist` extension enabled), proven by an integration test inserting two overlapping ranges for the same provider and asserting the second insert is rejected.

This decision is recorded in the models.py module docstring, the migration file, and STATE.md — not just here — since it is load-bearing for every subsequent plan in this phase and for Phase 2's booking saga.

## Decisions Made
- Hand-authored the initial migration rather than using `alembic revision --autogenerate` — kept the exclusion constraint's raw `EXCLUDE USING gist` DDL explicit and auditable rather than relying on autogenerate's constraint-diffing (which does not reliably detect `ExcludeConstraint` changes)
- Used a `_uuid_pk()` factory function instead of a single shared `mapped_column()` instance for every table's primary key — a shared Column/MappedColumn instance cannot be attached to more than one Table in SQLAlchemy
- Built `provider_specialties` with plain `sqlalchemy.Table` + `Column` (Core), not `mapped_column` (ORM) — `mapped_column()` requires a declarative-class mapping context that a bare association `Table` doesn't have
- Wrote the exclusion-constraint integration test using `db_session.begin_nested()` (SAVEPOINT) around the expected-to-fail insert so the `IntegrityError` only rolls back that one statement, keeping the shared `db_session` fixture's own outer-transaction teardown clean (avoids an otherwise-harmless but noisy `SAWarning: transaction already deassociated from connection`)
- `ensure_audit_indexes` reads/writes `settings.mongo_db_name` (the app's real configured database name), not a hardcoded test-only database — the test for it targets that same database and cleans up the collection itself in a `finally` block, since the shared `mongo_client` fixture's teardown only drops `{mongo_db_name}_test`
