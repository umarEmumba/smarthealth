<objective>
Build the Visit service (D-04) and its duplicate-safe visit state machine (VISIT-01, VISIT-02, VISIT-03, VISIT-05; D-15, D-17, D-18).

Purpose: Check-in, start and complete are synchronous, row-level state transitions (research Pattern 9): a conditional `UPDATE ... WHERE status=<expected>` plus a state-history row in one transaction, so concurrent duplicates cannot double-fire. Check-in requires a `confirmed` appointment, verified with Scheduling through a new internal lookup over an aud-scoped service token (D-06). Completion commits with `downstream_started_at IS NULL`; plan 02-11 adds the non-blocking downstream workflow and sweeper on top (VISIT-04).

Dependency note: functionally this plan needs 02-01 (service tokens), 02-03 (provider by-user), 02-05 (`visit_db`, `visit_service_url`) and 02-06 (appointments). It is ordered after 02-09 because both edit `services/scheduling/app.py`, `tests/conftest.py` and the isolation maps in the shared working tree.

Design choices within discretion: transitions are `POST /api/visits/{id}/start` and `/complete` (consistent with Scheduling's `/cancel` and `/reschedule` sub-resources) rather than a generic PATCH; `visit_state_history` carries `UNIQUE (visit_id, to_status)` as a second, data-layer guard, valid because the state machine never re-enters a state; check-in is not restricted to the appointment's calendar day in this phase (documented limitation).

Output: `services/visit/**`, Scheduling `GET /internal/appointments/{id}`, gateway row, harness/isolation wiring, tests.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-50 | Elevation of Privilege | start/complete by a provider | high | mitigate | Provider-by-user lookup must equal `visit.provider_id`; otherwise identical 404; patient role refused |
