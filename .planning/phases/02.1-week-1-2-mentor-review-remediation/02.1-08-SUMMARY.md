# Phase 02.1 Plan 08: Scheduling-side ScheduleChangeWorkflow Summary

**A Temporal Schedule polls Provider's change feed and starts one ScheduleChangeWorkflow per event; each run withdraws the provider's stale available future slots, flags the confirmed bookings on stale booked slots (they stay confirmed for staff to cancel or reschedule), re-checks held slots after the hold TTL, regenerates the new candidates and requests one notification intent per flagged booking, so editing or deactivating a template or deactivating a provider no longer leaves bookable slots that do not exist.**

## Performance

- **Duration:** about 31 min (includes a Compose rebuild and an 8-minute full test run)
- **Tasks:** 3 of 3 (3 task commits)
- **Files:** 8 created, 13 modified

## Accomplishments

- **Claim verified (as planned).** Before this plan nothing in Scheduling reacted to a template or provider change: slots are generated on demand and `insert_generated_slots` never revisits one, so search kept listing slots built from the old template, and a deactivated provider's booking was accepted (202) and only failed later in the saga's validate step. Reproduced in the code and now covered end to end.
- **Poller (Task 1).** `poll_schedule_changes` lists up to 100 pending events, `start_once`s `schedule-change-{event_id}` (second pass delay = hold TTL + 1 = 11 minutes) and only then acknowledges; a failure on one event is logged and skipped. The Schedule `{prefix}-schedule-change-poller` runs it every 15 s with overlap SKIP. A lost acknowledgement re-delivers the event, the start is a no-op (running: attached; closed: refused) and the ack lands.
- **Set-difference apply (Tasks 1 and 2).** The provider reference, department, clinic timezone and templates are resolved first (all-or-nothing); `expand_templates` is re-run over clinic-local yesterday .. the local date of the latest slot; every future slot whose exact (start, end) is outside that set is stale. `available` stale slots are withdrawn with the existing conditional `withdraw_slot`; `booked` stale slots get their `confirmed` or `checked_in` appointment flagged by a conditional UPDATE (set once, history note `schedule_changed:<reason>`, status/slot/version untouched); `held` slots wait for pass 2. For an active provider the not-yet-existing future candidates are then inserted (`ON CONFLICT DO NOTHING`), so an edit replaces slots. One transaction, one commit; then one best-effort notification intent per newly flagged appointment and the audit entry last (`{workflow_id}:apply:{pass}`).
- **Staff actions on a flagged booking (Task 2).** `AppointmentOut` carries `schedule_change_flagged` / `schedule_change_reason`; `GET /api/appointments?flagged=true` uses the unchanged scope rules. Rescheduling clears the flag. Cancelling or rescheduling a flagged booking now WITHDRAWS its stale slot instead of freeing it (see Deviations 1).
- **Workflow and proofs (Task 3).** `ScheduleChangeWorkflow` = apply, durable sleep, apply, summed counts; `ReferenceInvalid` ends it before pass 2. Stub-activity tests prove the order, the single timer, the retry budget and the early stop; a history recorded through the whole chain replays and a timer-less variant without a patch fails replay.
- **Real stack.** After rebuilding scheduling, scheduling-worker and provider, the poller Schedule registered on the Compose Temporal, and a deactivation through the gateway withdrew the slots and flagged the booking within a second.

## Deviations from Plan

**1. [Rule 2 - Missing critical functionality] Cancel and reschedule of a flagged appointment withdraw the stale slot**
- **Found during:** Task 2 design
- **Issue:** the plan leaves a flagged appointment's slot `booked`; when staff then cancel it, `cancel_appointment` (and `swap_slot` for the old slot) release the slot to `available`, which makes a slot the provider no longer works bookable again, undoing the withdrawal M2 exists to deliver. No second apply would run to catch it.
- **Fix:** both repository functions read `schedule_change_flagged_at IS NOT NULL` under the row lock they already take and set the freed slot to `cancelled` instead of `available` when it is set (unflagged appointments behave exactly as before; the existing cancel and reschedule suites pass unchanged). The waitlist advance after a cancel already answers `slot_gone` for a non-available slot.
- **Files modified:** `services/scheduling/repository/appointment_repo.py`; two tests in `test_schedule_change.py`.
- **Commit:** `1c1d571`

**2. [Interpretation] The audit entry and the notification intents are best effort**
- The plan says "audit LAST" and "a failure of that write is logged and never fails the activity" only for the notification. The apply's own audit is also best effort here (logged as `audit.write_failed`, ids and exception type only), following plan 02.1-07's S3 reasoning: the slots, flags and history notes are already committed, and a fatal audit failure would end the workflow before its second pass.

**3. [Interpretation] Small shape differences**
- `build_activities` in `worker.py` now takes the Temporal client and returns a three-tuple (it has a single caller); the plan told me to check before changing its signature.
- The candidate window starts at clinic-local yesterday (not today) as a clock-skew margin, and regeneration inserts only candidates whose start is in the future, so the first apply cannot create already-started slots.
- Extra files not in the plan's list: `tests/scheduling/schedule_feed.py` (the feed drain helpers shared by two test modules) and the `schedule_changes` fixture plus `build_schedule_change_activities` in `tests/temporal_fixtures.py` (that file was in the list).
- The three replay tests are named `..._committed_...` instead of `..._recorded_...` so the plan's `-k record` verify command selects only the recorder (with `recorded` in their names it ran the replay tests first and failed on the missing file).
- The TDD red/green split was not committed separately; each task's tests and code are one commit, with the mutation checks above standing in for a red phase.

**Total deviations:** 1 Rule 2 addition, plus interpretation notes. **Impact:** none on the plan's acceptance criteria; all met.

## Not Run / Open Risks

- **The live poller on the Compose stack is PAUSED.** After the real-stack check I paused the Temporal Schedule `scheduling-schedule-change-poller` (note set on it). Reason: with a running poller (every 15 s) acknowledging Provider's events and applying changes to test providers' slots in the same databases, the tests that read the feed right after a change (`tests/provider/test_schedule_change_feed.py`, `tests/scheduling/test_schedule_change.py`) become flaky. The scheduling, scheduling-worker and provider images ARE rebuilt from this branch. To resume the poller: `handle = (await Client.connect("localhost:7233")).get_schedule_handle("scheduling-schedule-change-poller"); await handle.unpause()` (a worker restart does not change it: an existing Schedule is left as it is).
- **A slot still `held` at pass 2 is not seen again.** If a hold is older than the TTL but the reaper has not run when pass 2 executes, the slot is skipped and no third pass follows; once the reaper frees it the stale slot is bookable until the next apply. The reconciler (02.1-11) or a later event closes it (apply is idempotent and state-based).
- **Slots not derivable from the templates are stale by definition**, including any slot inserted by another path (tests insert some by SQL). The application has no other path.
- **An unknown or deleted provider withdraws all its future available slots** (empty candidate set), as the plan specifies.
- **Waiting waitlist entries of a deactivated provider are not touched** (open risk from 02.1-05, unchanged).
- **The flag stays on a cancelled appointment** (history, and the flagged list then includes it); callers narrow with `?status=confirmed&flagged=true`. The history note is idempotent per (reason, actor), so re-flagging with the same reason after a reschedule sets the flag without a second note.
- **One sleeping workflow per event for about 11 minutes**; a large backlog (the first poll after a long outage reads 100 at a time) starts many sleeping workflows. Bounded by event rate; no cleanup of closed ones beyond Temporal retention.
- **Semgrep not run** (not installed in this environment). New surface: two outbound calls to Provider's existing internal routes with Scheduling's own `aud=provider` service token; no new inbound route.
