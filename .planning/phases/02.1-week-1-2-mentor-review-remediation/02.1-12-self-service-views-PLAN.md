<objective>
Carry-over C4: the provider role cannot view its own appointments, and patients cannot view their own profile.

Claim verification (done while planning, reproducible): `services/scheduling/api/appointments.py` declares `BOOKING_ROLES = (PATIENT, FRONT_DESK, ADMIN)` and uses it for the read routes too, so a PROVIDER token is 403 on `GET /api/appointments` and `/{id}`; `services/patient/api/patients.py` guards every route (including reads) with `require_role(FRONT_DESK, ADMIN)` and has no self route. Both claims are real.

Design (planner discretion, called out): the patient route is `GET /api/patients/me` (no id in the URL, identity only from the token's `sub` and clinic); the provider reads reuse the existing appointment endpoints with the provider's ownership resolved through Provider's existing internal by-user lookup (`/internal/providers/by-user/{user_id}`, already open to Scheduling), because that is the same rule Visit uses for provider ownership; a provider's reads are scoped by that provider id rather than by the token's clinic claim, so a provider login without a clinic claim still works and never sees another provider's data. Write routes keep `BOOKING_ROLES`.

Output: the self-profile route, the provider read access, and tests proving isolation and non-regression.
</objective>
