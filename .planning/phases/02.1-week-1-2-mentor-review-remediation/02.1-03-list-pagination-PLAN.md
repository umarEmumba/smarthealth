<objective>
Close carry-over C5: the patient, provider and clinic list endpoints return every row. Add `limit`/`offset` pagination with a stable order and a total-count header to all three, following the convention Visit's list already established (limit 1..200, default 50, offset) so the platform has one pagination style.

Claim verification (done while planning, reproducible): `patient_repo.list_patients`, `provider_repo.list_providers` and `org_repo.list_clinics` return `list(result.scalars().all())` with no LIMIT, and their routes take no paging parameters. The claim is real.

Purpose: an unbounded list is a latency and memory hazard in a multi-clinic platform and a contract gap the mentor flagged.

Output: shared `page_params` dependency, paginated repositories and routes for the three lists, `X-Total-Count`, and tests. Existing list tests are adapted to find rows by paging (a long-lived dev database accumulates clinics, so "first page" can no longer be assumed to contain a row created by the test).

Decision honoured: C5 (CONTEXT). Planner discretion (called out): response stays a plain JSON array (backward compatible with current clients and with Visit's list); the total comes in an `X-Total-Count` header; the department list inside one clinic is not named in the review and is left unchanged.
</objective>
