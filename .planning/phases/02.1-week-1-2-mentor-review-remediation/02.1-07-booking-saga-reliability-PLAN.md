<objective>
Fix four reliability defects in the booking saga and its neighbours, each reproducible in code, without breaking any in-flight workflow: S3 (failures after commit corrupt the outcome), S5 (a freed slot is not re-offered when a direct booker fails), S6 (past slots can be booked) and S7 (notification requested before confirm).

Claim verification (done while planning, reproducible):
- S7: `workflows/booking.py` runs `ACT_NOTIFY` before `ACT_CONFIRM`; `confirm` can still raise `ConfirmLostHold`. The README says the notification "fires only after the last fallible step", which the code does not do.
- S3: `SchedulingActivities.confirm` commits and then awaits `_audit(...)`; if that raises, the activity fails, Temporal retries then gives up, the saga's `except ActivityError` runs `void_billing` (which has no state check) on the now-confirmed appointment, then `release_slot` (a no-op) and `mark_failed` (conditional on pending, a no-op), and returns `failed` for a confirmed booking with its billing voided. `cancel_appointment` and `swap_slot` have the same post-commit audit shape (a failed audit makes the workflow report a refusal for a change that committed).
- S5: `WaitlistAdvanceWorkflow` is started only by cancel and reschedule; when a direct booker holds the freed slot the advance ends `slot_gone`, and when that booking later fails `release_slot` frees the slot with nothing left to offer it to the waitlist.
- S6: `create_appointment` checks scope and slot status but never the slot's start time; only the reschedule route and the waitlist claim reject past slots.
All four are real.

Design (planner discretion, called out): (1) both workflow changes are `workflow.patched` with new replay histories, per project convention; the guards for S3 live in activities (no command-sequence change, so no patch); (2) the failure re-offer starts only when the booking runs top-level (`workflow.info().parent is None`), because a booking started by a waitlist advance already has its parent loop deciding the next entry, and only when the slot hold was reached and the reason is not a lost race (a lost race means someone else owns the slot); (3) S3 uses a non-fatal audit write rather than an outbox: the transition is already durable in `appointment_status_history` in the same transaction as the state change, and Phase 3's transactional outbox is the general mechanism, so a local outbox now would be thrown away; (4) S6 returns 422 (a validation failure) at the API and the non-retryable `SlotInPast` reason in the saga; (5) history fixtures use the suffix p21 instead of a version number.

Output: patched `BookingWorkflow`, state-guarded compensations, best-effort post-commit audits, past-slot rejection, corrected docs, new replay fixtures and proof suites.
</objective>
