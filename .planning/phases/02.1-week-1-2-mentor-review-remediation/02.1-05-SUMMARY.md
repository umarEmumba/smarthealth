# Phase 02.1 Plan 05: Provider Schedule-Change Feed Summary

**Provider now writes one durable `schedule_change_events` row in the same transaction as every template edit that changes a schedule-affecting field, every template deactivation and every provider deactivation (and none for a no-op), and exposes the undelivered rows to Scheduling through `GET /internal/schedule-changes` with an idempotent `POST .../ack`, restricted to a Scheduling service token or an admin.**

## Performance

- **Duration:** about 25 min
- **Tasks:** 2 of 2 (2 task commits)
- **Files:** 2 created, 5 modified

## Accomplishments

- **Claim verified (as planned).** Before this plan, editing or deactivating a template and deactivating a provider only flipped rows in `provider_db`; nothing told Scheduling, whose on-demand slots stay as generated. The mentor's claim holds; the Scheduling side (withdraw slots, flag bookings) is plan 02.1-08.
- **Outbox in Provider's own database.** `provider_0002` creates `schedule_change_events` with the change-type CHECK and a partial index on undelivered rows. The downgrade drops the index then the table; upgrade, downgrade and upgrade were run against the live database and `alembic check` is clean.
- **Atomic by construction.** `record_schedule_change` only adds and flushes. The three repository functions that already own the commit call it before their `db.commit()`, so a failed commit leaves neither the change nor an event (proved with a session whose `commit` raises, then a fresh session). Routers and schemas are untouched.
- **No-op suppression.** `update_availability_template` compares each supplied value with the stored one before assigning; `deactivate_*` only records when the row is being flipped from active.
- **Feed and ack.** Ids, change type and a timestamp only (no names, no PHI). `limit` is 1..200 (422 outside). The ack is a conditional `UPDATE ... WHERE delivered_at IS NULL RETURNING`: first call `delivered`, repeats `already` (both 200), unknown id the identical 404. Logs carry the count or event id and outcome only.

**2. [Rule 3 - Blocking] Autouse feed drain in the new test module**
- **Found during:** Task 2 design

**3. Plan wording interpreted**
- The Billing and wrong-audience refusals use `create_service_token(...)` directly: Identity's mint will not issue a Billing token for audience `provider`, so a real mint is impossible for that case. The Scheduling and Visit tokens in the tracer and feed tests are real tokens minted through Identity's client-credentials endpoint.
- The plan's "empty PATCH" no-op is rejected by the router with 422 ("update body must include at least one field"), so that case asserts the 422 and no event instead of a 200.
- The TDD red/green split was not committed separately: Task 1's commit contains the template-deactivation hook (its tracer) and Task 2's commit contains the other two hooks together with their tests. A mutation check was run by hand (removing the compare-before-assign makes `test_patch_with_identical_values_writes_no_event` fail); a second mutation (committing inside `record_schedule_change`) did NOT fail the atomicity test, because the mocked `commit` raises on that earlier call too. The atomicity test therefore proves "no event survives a failed commit", not "an event can never be committed alone by a different mechanism" (for example a second session), which no test exercises.

## Notes for Downstream Plans

- **02.1-08 (schedule-change workflow, the consumer).** Contract: `GET {provider}/internal/schedule-changes?limit=N` with a Scheduling service token minted for audience `provider` returns `[{id, provider_id, change_type, template_id (null for provider_deactivated), created_at}]`, undelivered only, oldest first. Process each event, THEN `POST .../{id}/ack` (200 `{id, delivered: true}`; a repeat is also 200; 404 means the id is unknown). Acknowledge only after the effect is durable, so a crash re-delivers (at-least-once): the handler must be idempotent. There is no cursor or offset: keep reading from the start until the page is empty.
- `template_updated` and `template_deactivated` carry the `template_id`; `provider_deactivated` carries `template_id: null` and means every slot of the provider is affected.
- **Tests that read the feed need a drain.** The feed is global and capped at 200; other tests leave pending events in the shared database. Copy the autouse `_drain_feed` fixture from `tests/provider/test_schedule_change_feed.py` (acknowledge everything pending before the test) or the assertions will become flaky as events accumulate.
- A PATCH that changes nothing, and deactivating something already inactive, produce no event; do not rely on one event per API call.
- `provider_0002` must be applied to `provider_db` (`alembic -c services/provider/migrations/alembic.ini upgrade head`) before running anything that reads the feed; the live database used here is already at `provider_0002`. The Compose Provider image predates this change and needs a rebuild before the feed exists in a running stack.
- **02.1-13 (docs closeout).** `docs/erd.md` and `docs/erd.html` do not yet list `provider_db.schedule_change_events` (they hold unrelated uncommitted edits that were left alone); add the table, the `ck_schedule_change_events_type_valid` CHECK, the partial index, and an event-flow entry (Provider outbox -> Scheduling pull -> ack). Mention the outbox direction toward Phase 3 Kafka publishing.
