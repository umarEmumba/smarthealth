<objective>
Close the three Identity carry-overs from the Week 1 review: C1 (`/refresh` ignores the denylist and does not rotate, so tokens survive logout), C2 (bcrypt runs on the event loop and will stall logins under load) and C3 (email uniqueness is case-sensitive).

Claim verification (done while planning, reproducible): in `services/identity/api/auth.py` the `refresh` route decodes the refresh token and re-issues a pair with no Redis check, the old refresh token stays valid, and `logout` revokes only the access token's `jti`; `login`, `register` and `create_staff_user` call the synchronous `hash_password`/`verify_password` directly inside `async def` routes; the three lookups compare `User.email == payload.email` and the only constraint is the case-sensitive `users.email` UNIQUE. All three claims are real.

Purpose: tokens must stop working after logout, a login burst must not freeze the service (the reliability/scalability constraint), and `Alice@x` / `alice@x` must be one account.

Output: single-use refresh tokens with an access-token `rjti` claim, an async bcrypt wrapper on a bounded pool, normalized emails with a `lower(email)` unique index and a safe migration, and proof suites.

Decisions honoured: C1, C2, C3 (CONTEXT). Planner discretion (called out): rotation uses an atomic Redis `SET NX EX` claim (one operation both checks the denylist and consumes the jti, so a concurrent double-use yields exactly one 200); logout learns the paired refresh jti from a new access-token claim `rjti` (no client cooperation needed; access tokens minted before this change lack it and simply revoke only themselves); the email migration does NOT rewrite existing rows (existing mixed-case emails keep their casing and lookups use `lower(email)`), which keeps the migration fully reversible.
</objective>
