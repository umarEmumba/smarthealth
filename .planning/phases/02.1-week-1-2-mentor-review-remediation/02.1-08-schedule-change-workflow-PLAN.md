<objective>
Scheduling-side half of M2: when a provider's schedule changes, withdraw the slots that no longer exist and flag the bookings that sit on them. Plan 02.1-05 made every change a durable event in Provider; this plan consumes those events with a new Temporal workflow.

Claim verification (done while planning, reproducible): `services/scheduling/api/slots.py` generates slots on demand from the templates and `slot_repo.insert_generated_slots` never revisits an existing slot; nothing in Scheduling reacts to a template or provider change, so search keeps listing slots built from the old template. For a deactivated provider the booking is accepted (202) and only fails afterwards in the saga's validate step; for an edited template nothing checks the template at all. The claim is real.

Design (planner discretion, called out): the affected set is computed by SET DIFFERENCE, not by tracking which template made which slot: re-expand the provider's current templates over today .. the latest generated slot with the existing pure `expand_templates` and treat every future slot whose exact (start, end) is not in that set as stale (an inactive provider yields the empty set). This is idempotent, needs no slot-to-template link, and is DST-safe because it reuses the generator. Only `available` slots are withdrawn (via the existing conditional `withdraw_slot`); `booked`/`checked_in` slots get their appointment flagged; `held` slots belong to an in-flight booking and are left for a SECOND pass run after the hold TTL (a durable workflow timer), which catches a booking that confirms just after the change. For an active provider the same step also generates the new candidates (`ON CONFLICT DO NOTHING`), so an edit replaces slots instead of only removing them; a withdrawn slot keeps its key and is never resurrected (existing slot semantics). Ambiguity withdraws nothing: an unreachable owner is retried, a missing department or clinic reference raises a non-retryable error and leaves the slots alone. Flagged appointments stay `confirmed` and staff decide (cancel or reschedule); rescheduling clears the flag.

Output: migration `scheduling_0005`, the poller and the schedule-change workflows with their activities, Schedule registration, worker and test-harness wiring, flagged exposure in the appointment API, a recorded history and proofs.
</objective>
