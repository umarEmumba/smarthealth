# Phase 02.1 Plan 12: Self-service views Summary

**A patient can read their own profile with `GET /api/patients/me` (identity only from the token, one identical 404 for every miss), and a provider can list and read their own appointments through the existing GET routes (ownership through Provider's by-user lookup, foreign and missing are the identical 404, writes still 403), with the history tie from the reconciler fixed and everything proven through the gateway and on the rebuilt Compose stack.**

## Performance

- **Duration:** about 40 min (three regression runs of 5 to 7 minutes each, a Compose rebuild and a real-stack check)
- **Tasks:** 2 of 2 (2 task commits)
- **Files:** 2 created, 5 modified

## Accomplishments

- C4 is closed on both sides. The patient route takes no identifier at all, so there is nothing to tamper with; the provider reads reuse the appointment endpoints and decide ownership with the same Provider by-user rule Visit uses.
- No existence leak: the provider's own provider id is resolved before the appointment is read, so a foreign appointment, a missing id and a login without a provider profile give the same `404 {"detail":"not found"}`; the patient route gives one `patient profile not found` for every miss. Both are asserted equal, not just "also 404".
- Nothing else moved: front desk, admin and patient reads keep their exact code path and each has a non-regression assertion; the three write routes keep `BOOKING_ROLES` and refuse the provider with 403.
- The history tie noted by 02.1-11 is fixed where the views would show it: a note now follows the transition written with it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug, directed by the orchestrator] History ordering tie in `get_history`**
- **Found during:** carried over from 02.1-11 (rows written in one transaction share `created_at`, so a transition and its `billing_void_checked` note came back in either order)
- **Issue:** the self-service views show history, so the order must be deterministic.
- **Fix:** order by `created_at`, then notes (`from_status = to_status`) after transitions, then `id`. The test uses ids that sort the wrong way round and was confirmed to fail without the fix.
- **Files modified:** `services/scheduling/repository/appointment_repo.py`, `tests/scheduling/test_provider_appointments.py`
- **Commit:** `e4aad08`

**2. [Rule 1 - existing test encoded the defect] `test_appointment_reads_are_scoped`**
- **Found during:** the full scheduling run
- **Issue:** the test asserted the owning provider gets 403 on `GET /api/appointments/{id}`, which is exactly the C4 behavior being removed.
- **Fix:** the line now asserts 200 for the owner and adds a 403 for the same provider booking; the rest of the test (admin 200, other clinic 404, list scope) is unchanged. No test was weakened: foreign-provider isolation and write refusals are covered by the new suite.
- **Files modified:** `tests/scheduling/test_booking_api.py`
- **Commit:** `e4aad08`

## Open Risks and Notes for Plan 02.1-13

- **API overview and role matrix:** `GET /api/patients/me` (PATIENT) and the PROVIDER role on `GET /api/appointments` and `/{id}` (own appointments only, scoped by provider profile, not by clinic claim) should appear in the README/API overview and the access matrix; booking, cancel and reschedule stay PATIENT, FRONT_DESK and ADMIN.
- **Provider reads are not paginated:** the appointment list keeps its existing `limit` (default 100, max 200) and no `X-Total-Count`; a provider with more than 200 appointments in a window needs `start` and `end` to page through. A note for the docs, not a defect introduced here.
- **Provider read cost:** every provider read makes one service-token call to Provider (the same cost a patient read pays to Patient). A provider read with Provider down is a 503 by design.
- **Failure vocabulary is still raw:** a provider (and staff) now see `failed`/`workflow_lost` and `no_show` as stored; no patient-friendly wording was added (out of scope).
- **History order note:** `GET /api/appointments/{id}` history is now transition-then-note within a transaction; the docs can state history is ordered by creation time with notes after the transition written with them.
- **Compose:** `patient`, `scheduling` and `scheduling-worker` were rebuilt from this branch (the gateway was not: it routes by prefix and needed no change); the reconciler Schedule is live and `scheduling-schedule-change-poller` is still paused on purpose.
- **Test seeding reminder:** the live reconcilers run against the same databases; this plan's appointment rows are fresh (`confirmed_appointment`, slots a week beyond the generated ones) and are removed by provider id at teardown.
