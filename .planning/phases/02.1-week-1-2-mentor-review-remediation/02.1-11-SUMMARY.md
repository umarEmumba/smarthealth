# Phase 02.1 Plan 11: Scheduling reconciler Summary

**A `scheduling-reconciler` Temporal Schedule (60 s, overlap SKIP) now fails pending appointments whose booking workflow is gone (`workflow_lost`: void billing first, then release the hold and fail the appointment in one transaction), resolves waitlist entries stuck `matched`, voids billing orphans left by the hold reaper, marks overdue confirmed appointments `no_show` after Billing `no_refund`, and every slot it or the reaper frees is offered to the waitlist again, proven against real Postgres, Billing and Temporal and live on the Compose stack.**

## Performance

- **Duration:** about 35 min (a 13-minute full regression, a Compose rebuild and a live reconciler check)
- **Tasks:** 3 of 3 (3 task commits)
- **Files:** 5 created, 12 modified

## Accomplishments

- The reviewed defects are closed on the Scheduling side (S4/S5): a pending appointment whose workflow died no longer blocks its slot forever; a matched waitlist entry no longer waits for an operator; a hold the reaper expired no longer leaves the Billing record `verified`; freed slots go back to the waitlist; `no_show` is reachable and settles billing.
- The reconciler never touches a live booking: `describe()` RUNNING is skipped, an unreachable Temporal skips the step, and after the workflow is seen closed the appointment is re-read before billing is voided (the workflow's commits happen before its close), so billing is never voided for a booking that confirmed. The state change is a conditional update under a row lock; slot-then-appointment lock order matches the reaper.
- Convergence without new columns: a failed void leaves the appointment pending, a failed no-show state change leaves it confirmed, and both repeat idempotently; the only marker is the `billing_void_checked` history note.
- Real-stack check: seeded stuck rows in the Compose database were settled by the live Schedule within its first tick after the rebuild (pending to `workflow_lost`, overdue confirmed to `no_show`, stuck entry resolved), with a NOT_FOUND from the Compose Temporal as the liveness answer.

## Open Risks and Notes for Downstream Plans

- **Scheduling cancel and reschedule billing is still bounded (open, for the phase summary and 02.1-13):** `CancelWorkflow` and `RescheduleWorkflow` still give up after `FORWARD_ACTIVITY` and record `cancel_incomplete:billing_pending` style notes; this plan reconciles only booking, waitlist, reaper and no-show billing. BILL-02 is therefore not fully closed.
- **The schedule-change "held at pass 2" gap (02.1-08) is not closed here:** the plan does not cover it. `ScheduleChangeActivities.apply_schedule_change` is idempotent and state-based, so a future change can re-run it for a provider with a unique event id (`ScheduleChangeInput(event_id=<unique>, provider_id, change_type="template_updated")`); nothing triggers that today besides a later event.
- **Live reconciler vs. test data (for plans 12 and 13 and the verifier):** the Compose `scheduling-worker` now runs the reconciler against the same databases (pending after 10 minutes, matched after 15, no-show grace 30, lookback 24 h). Tests that seed an old pending row, an old matched entry or a confirmed appointment whose slot ended more than 30 minutes ago can be settled by it on a 60-second tick (the existing 02.1-01 no-show repo tests seed such rows and are only safe because they run in about a second). Seed fresh rows, reconcile with threshold 0, and for a no-show use a slot that ended a minute ago. The hold-reaper tests keep their pre-existing window (an expired hold can be reaped by the live reaper first, about 1 s per 60 s tick).
- **The reaper's waitlist offer runs on the live stack too:** an expired hold on a provider that has a waiting entry in the dev database is booked by the Compose workers, as designed.
- **History ordering tie:** `appointment_status_history` rows written in one transaction share `created_at`; the API's `get_history` orders by `(created_at, id)`, so the transition and the `billing_void_checked` note of a reconciled appointment can appear in either order. Cosmetic; fix by ordering notes after transitions or a statement timestamp if the self-service views (02.1-12) show history.
- **New failure vocabulary for the self-service views (02.1-12):** appointments can now be `failed` with `workflow_lost` and `confirmed` appointments can become `no_show` by automation; neither is patient-visible wording yet.
- **Fairness under a persistent single-row failure:** each list is oldest first with a limit of 50 (`reconcile_batch_limit`); more than 50 rows stuck for a retryable reason would starve newer ones (a Billing outage hits all rows equally; a per-row backoff column is the fix if it ever matters).
- **Patch ids and fixtures:** `ReconcilerWorkflow` has no patch marker. Any change to its command sequence needs `workflow.patched` and a newly recorded, distinctly named history next to `reconciler_p21.json` (never re-record it); the two reorder/removal tests in `test_replay_reconciler.py` bite on it.
- **Compose:** `scheduling` and `scheduling-worker` were rebuilt from this branch; `scheduling-reconciler` is live (not paused); `scheduling-schedule-change-poller` is still paused on purpose.
- **Docs (plan 02.1-13):** the Scheduling event flow should add the reconciler Schedule (stuck pending, stuck waitlist, billing lookback, no-show) and the reaper's waitlist offer; `workflow_lost` joins the failure reasons; no schema change in this plan.
