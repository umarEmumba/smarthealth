# Phase 02.1 Plan 04: NFR Targets and a Runnable k6 Load Test Summary

**The PRD now carries NFR-01..NFR-08 with justified numbers (25 booking requests per second sustained, 100 per second burst, 300 ms p95 accept latency, 99.9 percent availability, exactly-one-winner at 200-way contention) held in one `loadtest/nfr.json` that the k6 thresholds read and a test keeps equal to the PRD, plus a seed script and a pinned-image k6 runner that apply them; the docs say plainly these are targets and that measuring them is Phase 3.**

## Accomplishments

- **NFRs in the PRD (D1).** Eight checklist lines in the file's existing style, each with its justification; a "Demand model" paragraph (50,000 requests per day, 60 percent in a 2-hour peak is about 4.2 per second, 5x minute about 21 rounded to 25, 100 per second opening spike); a `key | value | unit` table; Traceability rows `NFR-01..08 | Phase 2.1 | Targets defined; measurement Phase 3`; the coverage footer says NFRs are counted separately from the 49 functional requirements. `Smart Health Requirements.md` is untouched.
- **Single source.** `loadtest/nfr.json` holds all thirteen numbers. `test_nfr_consistency.py` compares the PRD table and the `docs/nfr.md` table to it key for key, and checks the request counts follow from rate times duration.
- **Honest docs.** `docs/nfr.md` explains the demand model, lists each NFR with how it will be measured and its status, describes the four profiles, and has a section "What is verified and what is only a target": the local stack is expected to pass `smoke` and is not claimed to meet NFR-01/02; Phase 3 measures and sizes replicas.
- **Seed script.** `build_booking_plan` assigns each slot once with a rotating, busy-aware patient choice (zero overlap for any slot grid, distinct patients for simultaneous slots, deterministic). `build_world` creates the clinic, department, providers with 06:00-22:00 weekly templates, a front-desk user with a random password, M plus 200 patients in batches of 20, generates slots in windows of at most 28 days, lists them in 7-day windows, keeps the farthest slot out of the plan for contention, and renews tokens before the 15-minute expiry. CLI: admin credentials only from `LOADTEST_ADMIN_EMAIL` and `LOADTEST_ADMIN_PASSWORD` (exit 2 without), `plan.json` mode 0600, gitignored, counts-only stdout.
- **k6 script and runner.** `booking.js` runs one of four profiles chosen by `PROFILE`, with every rate, duration and threshold read from `nfr.json`; `setup()` logs in once; booking iterations take the next plan entry with a fresh `Idempotency-Key`, sample about 10 percent for a confirmation Trend (`booking_confirm_seconds`, in seconds) and about 20 percent for read traffic; the contention profile fires 200 single-iteration VUs at one slot with distinct patients, checks a same-key retry returns the same appointment, and `teardown()` fails the run unless exactly one active appointment exists. `run.sh` runs `grafana/k6:1.8.2` with the repo's `loadtest/` mounted read-only and exits with k6's code.
- **Verified the image.** `docker manifest inspect grafana/k6:1.8.2` succeeded on 2026-10-25; the image was pulled and `k6 version` reported v1.8.2. The tag and date are in `loadtest/README.md`.
- **Ran the script for real, against a mock.** Because the Compose stack was not up, the real pinned image was run through `run.sh` against a throwaway Python mock gateway: smoke passes (151 iterations, thresholds green), contention passes with one winner, shortened sustained (5 s) and burst (3 s) pass, a slow mock crosses the thresholds and exits 99, and a double-booking mock trips `contention_violations` and exits 99. This validated the script logic, the plan offsets, the teardown-metric-to-threshold path and the exit codes. It says nothing about real latency.

## Deviations from Plan

**1. [Rule 3 - Blocking] Seed default is 5 providers, not 4**
- **Found during:** Task 2
- **Issue:** the three profiles consume 150 + 15,000 + 6,000 = 21,150 plan entries; 4 providers x 192 slots x 28 days is at most 21,504, and today's already-past slots plus the contention slot leave fewer than 21,150, so one seed would not cover a smoke, sustained and burst run.
- **Fix:** default `--providers 5` (about 26,000 slots); the CLI prints a note when a plan is smaller than the sequence needs.
- **Files modified:** `scripts/loadtest_seed.py`, `loadtest/README.md`
- **Commit:** bf87936

**2. [Rule 1 - Bug avoided] Per-profile plan offsets**
- **Found during:** Task 3 design
- **Issue:** the plan said every booking iteration takes `scenario.iterationInTest`, which restarts at 0 for each run, so `sustained` would re-book the slots `smoke` just took and fail on 409.
- **Fix:** each profile starts at its own offset (smoke 0, sustained 150, burst 15,150) computed from `nfr.json`, with `PLAN_OFFSET` as an override and `run.sh` forwarding it.
- **Files modified:** `loadtest/booking.js`, `loadtest/run.sh`, `loadtest/README.md`
- **Commit:** 94a337f

**3. Plan wording interpreted**
- "Page `GET /api/slots`": that route is a window search (no limit/offset), so the seed lists each provider in 7-day windows. `GET /api/slots` over the last window does an on-demand extension that creates nothing (observed `created 0, considered 192`).
- "`http.setResponseCallback(expectedStatuses(202))`": a global callback would mark the 200 reads as failed, so the expected statuses are passed per request (`responseCallback`) for booking (202) and contention (202, 409).
- `run.sh` also passes `--user "$(id -u):$(id -g)"` because `plan.json` is mode 0600 and the k6 image's own user could not read a host-owned 0600 file on Linux. This was not exercised on Linux.

**Total deviations:** 2 auto-fixed (1 Rule 3, 1 Rule 1) plus 3 interpretation notes. **Impact:** none on scope; all acceptance criteria met.
