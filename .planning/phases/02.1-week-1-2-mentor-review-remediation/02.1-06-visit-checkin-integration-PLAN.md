<objective>
Visit-side half of M1: make a check-in actually change the appointment. Today Visit asks Scheduling "is it confirmed?" and then writes only its own visit row, so the appointment stays `confirmed`, cancel and reschedule keep working, and a refund can follow a patient who is already in the building. Plan 02.1-01 added Scheduling's internal check-in; this plan calls it.

Claim verification (done while planning, reproducible): `services/visit/api/visits.py::check_in` reads `get_appointment_ref`, requires `status == "confirmed"`, inserts the visit and returns; nothing is written to Scheduling. The claim is real.

Design (planner discretion, called out): Scheduling's transition is the gate and runs FIRST, because it enforces the window and is the only place the cancel race can be arbitrated (the transition and the cancel are both conditional on `confirmed` under one row lock). If the visit insert then fails, the appointment is `checked_in` with no visit; the repeat request finds Scheduling answering `already` and completes the visit, so the pair converges without a compensating call. Visit's public error details for the three refusals are a fixed set copied from Scheduling.

Output: one new reference-client function, a changed check-in route, test-harness support for the window, cross-service tests and the real-stack flow adapted to a slot inside the window.
</objective>
