<objective>
Provider-side half of mentor item M2: make every schedule-affecting change durable and observable by Scheduling. Plan 02.1-08 adds the Scheduling consumer that withdraws slots and flags bookings.

Claim verification (done while planning, reproducible): editing or deactivating an availability template (`provider_repo.update_availability_template`, `deactivate_availability_template`) and deactivating a provider (`deactivate_provider`) only flip rows in `provider_db`; Scheduling's `provider_slots` are generated on demand and never revisited, so search keeps returning slots built from the old template, and a booking for a deactivated provider is accepted with a 202 and only fails later in the saga's validate step (and a template edit is not checked at all). The claim is real.

Design (planner discretion, called out): an outbox-style event table in Provider's own database, written in the same transaction as the change, and read by Scheduling over a service-token internal API with an explicit acknowledgement. This avoids a push from Provider to Scheduling (a push is lost if Scheduling is down at the moment of the change) and a cursor over a sequence (rows can commit out of sequence order, so a cursor can skip an event); "pending until acknowledged" has neither failure. It also matches the transactional-outbox direction of Phase 3, so Phase 3 can publish the same rows to Kafka.

Output: migration `provider_0002`, `ScheduleChangeEvent` model, in-transaction hooks, and the internal feed with acknowledgement.

Decision honoured: M2 (CONTEXT). Not in scope (called out): waiting waitlist entries of a deactivated provider are not touched here; recorded as an open risk in the phase summary.
</objective>
