# Phase 02.1 Plan 02: Identity Carry-overs Summary

**Refresh tokens are now single-use and rotating (atomic Redis `SET NX EX` claim, fail-closed 503), logout kills the paired refresh token through a new `rjti` access-token claim, bcrypt runs on a bounded `bcrypt*` thread pool so a login burst cannot stall the event loop, and email identity is case-insensitive through input normalization, `lower(email)` lookups and a `uq_users_email_lower` unique index whose migration refuses over duplicates without ever printing an address.**

## Performance

- **Duration:** about 20 min (start 2026-10-24T17:06:45Z)
- **Tasks:** 3 of 3 (4 task commits)
- **Files:** 5 created, 9 modified

## Accomplishments

- **C1 refresh rotation.** `consume_token` issues one `SET revoked:{jti} 1 NX EX max(ttl,1)`; only the first claimer wins. `/api/auth/refresh` validates the token and the user first, then consumes the old jti, then issues a new refresh token and an access token carrying its `rjti`. Reuse logs `auth.refresh.reuse_refused` with the jti only. A `RedisError` is a 503 and leaves the token unconsumed. Logout revokes the access jti and, when the access token has `rjti`, the refresh jti with TTL `refresh_token_expire_days * 86400`.
- **C2 bcrypt off the loop.** `hash_password_async` / `verify_password_async` run the unchanged sync functions through `run_in_executor` on `ThreadPoolExecutor(max_workers=IDENTITY_BCRYPT_THREADS, thread_name_prefix="bcrypt")`. `register`, `create_staff_user` and `login` await them; login still verifies against `DUMMY_PASSWORD_HASH` for unknown users (constant-time rule intact).
- **C3 case-insensitive email.** One `normalize_email` (strip, lowercase, applied before `EmailStr`) on the three request models; the three lookups and `bootstrap_admin` use `func.lower(User.email)`. `identity_0002` preflights `count(*)` of duplicate `lower(email)` groups and raises with the count only; otherwise it creates `uq_users_email_lower`. No row is rewritten.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] RSA signing key was re-parsed from PEM on every token, stalling the loop**
- **Found during:** Task 2 (the plan's own loop-lag test failed at 209-463 ms even though bcrypt ran in the pool; a stack sampler showed `jose ... load_pem_private_key` on the loop thread)
- **Issue:** python-jose rebuilds the key object from PEM text on every `jwt.encode`; cryptography validates the RSA key each time, a few milliseconds of CPU per token, 16 tokens per 8-login burst, all on the event loop.
- **Fix:** `signing.py` builds the `jose` key object once per loaded key and passes it to `jwt.encode` (`_prepared_signing_key`). Same token output; the cache holds only the current key.
- **Files modified:** `services/identity/security/signing.py`
- **Commit:** `c279996`
- **Verification:** loop-lag test passes 5 of 5 repeated runs; mutation check (sync bcrypt in login) fails the same test at 601 ms.

**2. [Rule 1 - Bug] Existing JWKS tracer asserted the exact access-claim set**
- **Found during:** Task 2 full `tests/identity` run
- **Issue:** `tests/identity/test_rs256_jwks_tracer.py` asserts `set(claims) == {...}`; the plan adds `rjti` on purpose, so the exact-set assertion was stale.
- **Fix:** added `rjti` to the expected set with a comment; the assertion is still an exact-set check, not loosened to a subset.
- **Commit:** `c279996`

**3. [Rule 3 - Blocking] `alembic check` reported drift unrelated to the new index**
- **Found during:** Task 3 verification
- **Issue:** migration `identity_0001` creates `ix_users_clinic_id` but the model never declared it, so `alembic check` reported "remove_index" before and after this plan.
- **Fix:** declared `Index("ix_users_clinic_id", "clinic_id")` on `User.__table_args__`; no migration change.
- **Files modified:** `services/identity/repository/models.py`
- **Commit:** `b273391`

Test-data cleanup (not a code deviation).** My own RED run of the case-insensitivity tests (before the fix existed) legitimately registered case-variant duplicates in the live `identity_db`, which made the first `upgrade head` refuse (the preflight working as designed: 2 groups).
