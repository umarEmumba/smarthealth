# Phase 01.1 Plan 07: Provider service on provider_db with validated department and account references Summary

**The provider directory (providers, specialties, weekly availability templates) now lives in its own service and database (`provider_db`, no cross-service foreign keys, no slots table), reachable only through the gateway at the unchanged `/api/providers` paths. Creating a provider or an availability template validates the department with Organization (and the account link with Identity) before writing, fails closed with 422/503/409, never cascades from a deactivated department, and a new `/internal/providers/{id}` endpoint is ready for Scheduling's integrity checks.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Duplicate account link raised an unhandled unique violation**
- **Found during:** Task 2 RED (the duplicate-link test surfaced the database unique violation through the app instead of a response)
- **Issue:** `providers.user_id` is unique (one profile per account) and the Phase 1 code did not handle a second create with the same `user_id`, which is an HTTP 500; with D-05 validation now accepting any real account it is an easy path to trigger, and two racing creates hit the same constraint.
- **Fix:** `create_provider` catches `IntegrityError`, rolls the session back and (when a `user_id` was supplied) writes a failure audit and answers 409 "account is already linked to a provider profile"; an `IntegrityError` with no `user_id` is re-raised. The constraint stays the arbiter, no application lock was added.
- **Files modified:** services/provider/api/providers.py, tests/provider/test_department_validation.py
- **Verification:** `test_second_provider_for_same_account_is_409_and_not_written`
- **Committed in:** 7ad8b9d (test in c547209)

**2. [Rule 1 - Bug] Specialty get-or-create was a check-then-insert race that also committed mid-request**
- **Found during:** Task 1, while moving the repository (the plan's PPL-02 concurrency edge relies on the UNIQUE constraint, but the moved code would turn the race into an unhandled unique violation and committed each specialty before the provider existed)
- **Issue:** two concurrent creations introducing the same new specialty could both miss the SELECT, both INSERT, and one would fail with a unique violation (HTTP 500). A repeated name inside one request would also try to attach the same specialty to a provider twice (a duplicate association key).
- **Fix:** `get_or_create_specialty` uses `INSERT ... ON CONFLICT (name) DO NOTHING` followed by a SELECT and no longer commits; `_specialties_for` de-duplicates names preserving order. The specialties are committed together with the provider.
- **Files modified:** services/provider/repository/provider_repo.py, tests/provider/test_providers.py
- **Verification:** `test_existing_specialty_name_reuses_the_row`, `test_concurrent_creations_with_the_same_new_specialty_make_one_row` (six concurrent creates, one row)
- **Committed in:** 43d6380 (code), f1a9c66 (tests)
