## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Settings leaked an unprefixed DATABASE_URL**
- **Found during:** Task 1 (migration verification)
- **Issue:** The plan specified `populate_by_name=True` on `SharedSettings`. In pydantic-settings 2.15.0 that also reads the env var named after the field, so `IdentitySettings.database_url` picked up a stale bare `DATABASE_URL` instead of `IDENTITY_DATABASE_URL`. This is the exact hazard named in the plan's own assumption-delta decision and plan 01.1-02's `test_config`.
- **Fix:** `SharedSettings` uses `validate_by_name=False, validate_by_alias=True`. Added `tests/libs/test_shared_settings.py` (stale `DATABASE_URL` is ignored; `IDENTITY_DATABASE_URL` wins).
- **Files modified:** libs/config.py, tests/libs/test_shared_settings.py
- **Verification:** `DATABASE_URL=... python -c "from services.identity.config import settings"` resolves identity_db; 4 settings tests pass
- **Committed in:** 4865455 (config), e3788e1 (test)

**2. [Rule 3 - Blocking] `pip install -e '.[dev]'` verify step cannot run in this environment**
- **Found during:** Task 1 tracer verify
- **Issue:** pip crashes on start in this macOS runtime (`truststore/_macos.py: ValueError: invalid literal for int()`); `--no-index --no-build-isolation` fails the same way, and the venv has no setuptools.
- **Fix:** No package is added by this plan (plan threat T-01.1-SC). Validated instead that `pyproject.toml` parses with the new `[tool.setuptools.packages.find]` and `e2e` marker, and that `libs`/`services` import and test from the repo root via the existing editable install.
- **Files modified:** none
- **Verification:** tomllib parse plus the full pytest runs below
- **Committed in:** n/a

**3. [Rule 2 - Missing Critical] Hardening beyond the plan text**
- `get_current_user` uses `HTTPBearer(auto_error=False)` and raises 401 with `WWW-Authenticate` itself (FastAPI's own missing-credentials status is not guaranteed 401); a `RedisError` during the denylist check returns 503 (fail closed) rather than a 500.
- `keys.load_signing_key` also rejects RSA keys under 2048 bits, and `SigningKey.__repr__` redacts the private key so it cannot reach a traceback or log.
- The keypair script opens with `O_EXCL` when not forcing (race-free refusal) and `fchmod`s 0600 on overwrite.
- The HS256-with-public-key forgery test builds the token by hand: python-jose refuses to HMAC with a PEM, and a real attacker would not use it.
- **Committed in:** 4865455, c532973, e3788e1

## Issues Encountered

- **Stray objects in the legacy `smarthealth` database (needs a human decision).** Before deviation 1 was fixed, my first `alembic upgrade head` (run, then a downgrade/upgrade) followed the leaked bare `DATABASE_URL` and created an empty `users` table and an `alembic_version` row in the legacy `smarthealth` database rather than in `identity_db`. That database held no other tables. I tried to drop the two objects and the permission system denied it, so I left them. They are harmless to every service in this phase but will confuse a Phase 1 `alembic upgrade` against the legacy database. To remove them: `DROP TABLE users; DROP TABLE alembic_version;` in the `smarthealth` database.
