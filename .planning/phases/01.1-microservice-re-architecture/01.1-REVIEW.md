# Phase 01.1: Code Review Report

**Reviewed:** 2026-10-12

## Summary

Scope was `git diff --name-only 43a9a8d..HEAD -- libs services scripts infra tests pyproject.toml` (169 surviving files; 8 legacy monolith files were deleted and have no current content). All non-test source was read in full. The other 50 test files were only pattern-scanned (skips, xfails, fixtures) and not read line by line, so test-level findings are limited to `tests/conftest.py`. `.env*`, `infra/.env*` and `infra/secrets/*` were not read. I did not run the suite or a live stack. Items below were checked in code, and the three I could exercise offline (SQLAlchemy error rendering, redirect `Location` behaviour, python-jose `require_exp` default) are marked "reproduced".

What holds up:
- RS256 and `kid` are pinned in `decode_token`. A refresh token cannot authenticate an API call (`ACCESS_ONLY`).
- The denylist check fails closed on `RedisError`, and the JWKS client keeps stale keys through an Identity outage.
- Gateway path-safety rejects dot segments, encoded `/`, `.`, `\` and NUL, forwards the raw path, and has no `/internal` route.
- `/metrics` is decided by the listening socket port, not a client header.
- The register/specialty/user_id races are arbitrated by DB constraints.
- Cross-service reference checks map every non-200/404 outcome to 503, never 422 or success.

The two Critical issues are session termination and PHI reaching logs and traces. Most Warnings are design gaps the docs already acknowledge (no `aud`, no body cap, limiter fail-open, root containers). They are re-listed because each has a concrete failure path.

## Critical Issues

### CR-01: Logout does not terminate the session; refresh tokens are never revoked or checked

**File:** `services/identity/api/auth.py:384-421` (refresh), `:424-454` (logout, revoke at `:442`)
**Issue:** `logout` denylists only the *access* token's `jti`. `refresh` never consults the denylist, and the refresh token's `jti` is never stored or revoked. `refresh` also does not rotate: the old refresh token stays valid after use. `docs/architecture.md` (line 325) advertises this as "real logout".
**Failure scenario:** A clinician logs out of a shared workstation, or an admin logs a user out after a suspected compromise. The attacker, or the next person at the workstation, still holds the 7-day refresh token. `POST /api/auth/refresh` returns a fresh 15-minute access token and a fresh refresh token indefinitely, so the logged-out session is fully live. No test covers refresh-after-logout (`tests/identity/test_auth.py` only has `test_refresh_reissues_access_token`).
**Fix:**
```python
# logout: accept the refresh token (or look up the refresh jti) and revoke both
class LogoutRequest(BaseModel):
    refresh_token: str | None = None

# in logout():
if body.refresh_token:
    rclaims = await decode_token(body.refresh_token, expected_types=REFRESH_ONLY,
                                 resolver=local_key_resolver())
    if rclaims["sub"] == user.sub:
        await revoke_token(rclaims["jti"], int(float(rclaims["exp"]) - now), redis)

# in refresh(): after decode_token
if await is_revoked(claims["jti"], redis):
    raise HTTPException(401, "invalid or expired refresh token")
# rotation: denylist the presented refresh jti (TTL = remaining life) before issuing the new pair
```
Add a test that refresh after logout returns 401 and that a reused refresh token is rejected.

### CR-02: Patient PHI can reach stdout logs and trace exception events through SQLAlchemy error text

**File:** `libs/db/postgres.py:50` (engine built without `hide_parameters=True`); trigger site `services/patient/api/patients.py:207-212`
**Issue:** `create_async_engine(database_url, pool_pre_ping=True)` leaves SQLAlchemy's default of including `[parameters: (...)]` in `DBAPIError`/`IntegrityError` messages. I reproduced the message format: `[SQL: INSERT INTO patients (...)] [parameters: ('Jane Doe', '1990-01-01', '555-0100')]`.

Any unhandled DB error in Patient create/update therefore stringifies `full_name`, `date_of_birth`, `phone` and `address`. `patients.py:211-212` re-raises explicitly (`if payload.user_id is None: raise`), and nothing else maps DB errors to a handled response. The traceback is written by uvicorn and gunicorn to stdout. The ASGI/FastAPI OpenTelemetry instrumentation also normally records the exception message on the server span, and spans are exported to Jaeger.

Pydantic accepts NUL characters, which Postgres text columns reject. I did not run this against a live Postgres, so treat the NUL trigger as reasoned rather than reproduced. Deadlocks, serialization failures and connection resets mid-INSERT would also trigger it. The same applies to Identity (email and bcrypt hash in parameters).

This breaches the project's non-negotiable "Never log PHI" rule and the architecture doc's PHI-safe claim for logs and traces.
**Failure scenario:** A front-desk user submits `full_name: "A\u0000"` (or a transient DB fault hits the INSERT). The request returns 500 and the log and trace store receive the full patient record (name, DOB, phone, address).
**Fix:**
```python
engine = create_async_engine(database_url, pool_pre_ping=True, hide_parameters=True)
```
Also add an app-level `@app.exception_handler(Exception)` per service that logs only `type(exc).__name__` and returns a generic 500. Reject `\x00` in free-text PHI fields with a pydantic validator, and add a test asserting that a forced DB error produces no PHI in captured logs.

## Warnings

### WR-01: Gateway forwards redirects with the internal hostname in `Location`

**File:** `services/gateway/proxy.py:46` (`host` dropped), `:117-123`, `:131-136`
**Issue:** The gateway drops the client's `Host` header (so httpx sets `Host: organization:8000`) and returns upstream headers verbatim, including `Location`. Starlette's `redirect_slashes` builds the redirect URL from the Host it saw. I reproduced it: a request to `/api/clinics/` against an app serving `/api/clinics` at host `organization:8000` returns `307 Location: http://organization:8000/api/clinics`.
**Failure scenario:** An external client calling `GET /api/clinics/` is redirected to `http://organization:8000/...`. That is unresolvable and discloses the internal service name and port (an infrastructure detail), and the client breaks.
**Fix:** Preserve the original `Host` and `X-Forwarded-Host` for upstreams, or rewrite or strip `Location` when it points at an upstream base URL. Alternatively set `redirect_slashes=False` on the service apps so a trailing slash is a plain 404.

### WR-02: Service tokens bypass every internal role allowlist and carry no audience or scope

**File:** `libs/auth/internal.py:140-143` (service caller returned before the role check at `:145`); `services/identity/security/signing.py:70-87`
**Issue:** Any validly signed `type=service` token with a `service:`-prefixed `sub` is accepted by every `/internal/*` endpoint in every service. The per-endpoint role allowlists (e.g. Provider's ADMIN-only `/internal/providers/{id}`) apply to user callers only. The token has no `aud` or scope claim, so it is not bound to a target or operation. `clinic_scope_permits` also returns True for any service caller. The missing `aud` is acknowledged in the docs, but the allowlist bypass is not.
**Failure scenario:** The 60-second token Identity attaches to its Organization call during anonymous registration is replayable, within its lifetime, against Identity `/internal/users/{id}` (user id, role, clinic) and Provider `/internal/providers/{id}` by anything that can read that request: a compromised or logging Organization, or a proxy on the plain-HTTP internal network.
**Fix:** Add `aud` (target service) and `scope` claims in `create_service_token(service_name, audience, scope)`. In `require_internal_caller(..., service_scopes=...)`, require `aud` to equal this service and `scope` to be allowed for the endpoint. Use `jwt.decode(..., audience=...)` only for service tokens.

### WR-03: `exp` is not required when verifying tokens

**File:** `libs/auth/verification.py:100`
**Issue:** `jwt.decode(token, key, algorithms=[RS256])` uses python-jose defaults, where `require_exp` is `False` (confirmed in `jose/jwt.py:107`). A token signed with a valid key but lacking `exp` never expires. Identity always sets `exp`, so this is a defense-in-depth gap. It matters for any future signer, a key-reuse mistake, or a bug in a token factory.
**Failure scenario:** A token minted without `exp` (a future "long-lived integration token", or a bug) is accepted forever on every service and is revocable only via the denylist, which `revoke_token` skips when TTL <= 0.
**Fix:**
```python
claims = jwt.decode(token, key, algorithms=[JWT_ALGORITHM],
                    options={"require_exp": True, "require_iat": True})
```

### WR-04: Audit write happens after the DB commit and is not atomic with it

**File:** `services/identity/api/auth.py:170-202`, `:273-307`; `services/patient/api/patients.py:198-231`; same pattern in every mutating route (organization, provider)
**Issue:** The business write is committed, then `write_audit` does `insert_one` to Mongo with no error handling.
**Failure scenario:** Mongo is down or slow while a front desk creates a patient. The patient row is committed, `write_audit` raises, and the client gets a 500. The PHI mutation has no audit record, which is an IAM-04 gap. For registration the client retries and gets a spurious 409 "email already registered". The `bootstrap_admin.py` script has the same shape (creates the admin, then fails and exits 1).
**Fix:** Pick a policy and implement it explicitly:
- (a) Write an outbox row in the same Postgres transaction and ship it to Mongo asynchronously.
- (b) Write the audit first as `pending`, then finalize.
- (c) At minimum, catch audit failures, emit a structured error log with the ids, and return the real result. Do not let a committed mutation turn into a 500.

### WR-05: Specialty get-or-create can deadlock under concurrent provider creation

**File:** `services/provider/repository/provider_repo.py:49-59`
**Issue:** `_specialties_for` inserts new specialty names in the caller's order (`dict.fromkeys(names)`) inside one transaction. `ON CONFLICT DO NOTHING` waits on another transaction's uncommitted row for the same name.
**Failure scenario:** Admin A creates a provider with `["cardiology", "neurology"]` and admin B with `["neurology", "cardiology"]`, both introducing new names at the same time. Each holds one uncommitted unique-index entry and waits on the other. Postgres aborts one with a deadlock error and the request returns 500 (unhandled `DBAPIError`, see CR-02 for what that does to the logs).
**Fix:** Process names in a deterministic order, e.g. `for name in sorted(set(names))`, or insert all names in one statement: `pg_insert(Specialty).values([...]).on_conflict_do_nothing()`, then `select ... where name in (...)`.

### WR-06: Specialty names are not validated (length, blank, normalization)

**File:** `services/provider/api/providers.py:59`; `services/provider/domain/schemas.py:25`; column `String(255)` at `repository/models.py:96`
**Issue:** `list[str] = Field(min_length=1)` constrains the list length, not the items. `""` and `"   "` are accepted. A name longer than 255 characters passes pydantic and fails at INSERT with a 500. Case and whitespace variants (`"Cardiology"` vs `"cardiology "`) create distinct specialties.
**Failure scenario:** `POST /api/providers` with `"specialties": ["x" * 300]` returns 500 (plus the CR-02 log exposure path). `[""]` creates a blank specialty permanently.
**Fix:** Use `list[Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=255)]]`, normalize case (e.g. `.casefold()` stored alongside the display name), and cap the list size.

### WR-07: `provider_slots` exclusion constraint is bypassed by zero-length slots and nothing enforces `end_time > start_time`

**File:** `services/scheduling/repository/models.py:65-77`; `services/scheduling/migrations/versions/scheduling_0001_provider_slots.py:60-76`
**Issue:** The constraint is `EXCLUDE ... tstzrange(start_time, end_time) WITH &&`. If `start_time == end_time` the range is empty, and an empty range overlaps nothing. There is no `CHECK (end_time > start_time)`. `end_time < start_time` raises a range error at insert instead of a clean validation failure.
**Failure scenario:** Phase 2 slot generation, or a buggy caller, inserts two zero-length slots for the same provider and instant. Both succeed, and the "load-bearing" double-booking guarantee does not hold for them. Every later query that assumes non-empty ranges is wrong.
**Fix:** Add `CheckConstraint("end_time > start_time", name="ck_provider_slots_time_order")` to the model and a new migration. The baseline revision is already applied wherever the stack has run.

### WR-08: Infrastructure ports are published on all interfaces with default credentials; the isolation story is moot from the host

**File:** `infra/docker-compose.yml:55-56` (Postgres 5433), `:95-96` (Mongo), `:112-113` (Redis), `:128-130` (RabbitMQ + UI), `:160-161` (Kafka), `:184-185` (Schema Registry), `:211-212` (Temporal), `:228-229` (Temporal UI), `:233-236` (Jaeger), `:243` (Prometheus), `:252-253` (Grafana). Defaults at `:53`, `:80-85`, `:126-127`, `:249`, `:270` etc.
**Issue:** Only the application services are un-published. Every data store is bound to `0.0.0.0` with no auth for Mongo, Redis, Kafka and Schema Registry, and with `changeme-*` fallback passwords elsewhere. The Postgres superuser is `smarthealth` / `changeme-local-dev-only` unless `.env` overrides it (compose fallback syntax `${VAR:-default}`).
**Failure scenario:** On a developer laptop on a shared network, or a lab or CI box, anyone who can reach the host connects to Postgres as superuser and reads every `*_db` including `patient_db` PHI. Per-service roles and `REVOKE ... FROM PUBLIC` do not matter to a superuser. Unauthenticated Redis lets them delete `revoked:*` denylist keys or reset `ratelimit:*`, and unauthenticated Mongo lets them edit `audit_log`. Redis is the only revocation store.
**Fix:** Bind host ports to loopback (`"127.0.0.1:${POSTGRES_HOST_PORT:-5433}:5432"`, and the same for every infra port) or move them behind a `docker-compose.override.yml` for dev. Require secrets with `${POSTGRES_PASSWORD:?set in infra/.env}` rather than defaulting. Set a Redis `requirepass` and Mongo auth, since CLAUDE.md itself calls for a Redis password "to mirror prod hygiene".

### WR-09: `env_file: .env` injects the whole `.env` into every container

**File:** `infra/docker-compose.yml:265-267`, `:285-287`, `:299-301`, `:313-315`, `:331-334`, `:362-365`
**Issue:** Each application service (including the gateway, which needs none of it) loads the full `infra/.env` via `env_file`, in addition to the per-service `environment:` block. I did not read `.env`. If it holds the Postgres superuser password, other services' DB passwords or the `BOOTSTRAP_ADMIN_*` values (as `.env.example` suggests for local dev), every container receives credentials it must not have. That defeats the database-per-service and "only Identity holds secrets" design (D-01, STRIDE T-01.1-03).
**Failure scenario:** An RCE or `/proc/self/environ` read in the gateway or scheduling container yields the Postgres superuser password and every other service's DB password, even though the compose `environment:` blocks are carefully scoped.
**Fix:** Drop `env_file` from application services and pass only the variables each needs through `environment:` interpolation (Compose reads `infra/.env` for interpolation already). Verify the contents of `.env` after the change.

### WR-10: Rate limiter fails open for the credential endpoints too, and login has no per-account throttle

**File:** `services/gateway/ratelimit.py:112-117`
**Issue:** On any Redis error `check_rate_limit` returns `allowed=True` for every group, including `auth` (`/api/auth/login`, `/register`, `/refresh`). Identity has no per-account lockout or backoff. Redis outage is exactly when an attacker benefits. Denylist checks already fail closed on Redis loss, so the platform is simultaneously "down" for authenticated routes and "wide open" for password guessing. The fail-open choice is documented, but the failure mode for `auth` is not defensible.
**Failure scenario:** Redis is unreachable or restarting (or an attacker with the unauthenticated Redis from WR-08 flushes it). The 20/min cap disappears and credential stuffing against `/api/auth/login` runs at line rate against bcrypt.
**Fix:** Fail closed (429/503) for `group == "auth"`, or fall back to a small in-process per-IP limiter. Add a per-email counter in Identity.

### WR-11: Gateway buffers whole request bodies before any auth

**File:** `services/gateway/proxy.py:121`; `services/gateway/app.py:99-105`
**Issue:** `content=await request.body()` reads the entire body into memory for any proxied method, unauthenticated, with no size limit (acknowledged in `docs/architecture.md:277`). The rate limiter bounds request count, not size.
**Failure scenario:** One client posts a multi-GB body to `/api/auth/login` and each of the few allowed requests holds that body in a gateway worker. Two workers per container run out of memory.
**Fix:** Enforce a `Content-Length` cap (e.g. 1 MiB) before reading, and a streaming byte-count guard for chunked uploads, returning 413. Alternatively stream the body to upstream.

### WR-12: Prometheus metrics are per-worker, so scrapes are inconsistent under `gunicorn -w 2`

**File:** `services/gateway/Dockerfile:30` and the matching `CMD` in every service Dockerfile (`-w ${WEB_CONCURRENCY:-2}`); `libs`/service `Instrumentator().instrument(app).expose(app)`; `services/gateway/app.py:51-58`; `services/gateway/ratelimit.py:58` (`gateway_ratelimit_fail_open_total`)
**Issue:** Each gunicorn worker has its own `prometheus_client` default registry, and `PROMETHEUS_MULTIPROC_DIR` is not configured anywhere. Each scrape of `:8000/metrics` or `gateway:9100/metrics` lands on one arbitrary worker and returns only that worker's counters.
**Failure scenario:** Request and error counters appear to jump up and down between scrapes, and rate(...) is wrong. A fail-open event recorded in worker 1 is invisible when worker 2 answers the scrape, so the limiter degradation signal the code promises can be missed.
**Fix:** Set `PROMETHEUS_MULTIPROC_DIR` (a tmpfs path), use `MultiProcessCollector` in the metrics endpoint, and add `child_exit` to gunicorn config. Alternatively run one worker per container and scale replicas.

### WR-13: Clinic `timezone` is documented as IANA but never validated

**File:** `services/organization/api/clinics.py:45`; `services/organization/domain/schemas.py:24`
**Issue:** `timezone: str = Field(min_length=1, max_length=64)`. `"Mars/Phobos"` or `"EST5EDT garbage"` is accepted and persisted. Phase 1 Pitfall 3 and the availability docs say naive template times are resolved against this value.
**Failure scenario:** An admin typos the zone. Phase 2 slot generation hits `ZoneInfoNotFoundError` or, worse, silently falls back to UTC, producing slots at the wrong wall-clock hours for a clinic.
**Fix:** Add a validator: `ZoneInfo(v)` in a `try/except ZoneInfoNotFoundError`, in both `ClinicCreate` and `ClinicUpdate`.

### WR-14: Per-request Redis client has no socket timeouts, so a hung Redis hangs every authenticated request

**File:** `libs/db/redis.py:17`
**Issue:** `Redis.from_url(shared_settings.redis_url, decode_responses=True)` has no `socket_connect_timeout` or `socket_timeout`. `get_current_user` fails closed only on `RedisError`, not on a stalled connection. (The gateway's own limiter client does set 0.5 s.)
**Failure scenario:** Redis is paused, or a network blackhole drops packets. Each authenticated request blocks in `EXISTS revoked:<jti>` until the gateway's 10 s upstream timeout returns 504, while the service workers pile up blocked coroutines. The "fail closed with 503" design degrades to latency and exhaustion.
**Fix:** `Redis.from_url(url, decode_responses=True, socket_connect_timeout=1.0, socket_timeout=1.0)`, and consider a shared pooled client created at lifespan.

### WR-15: All containers run as root and keep the compiler toolchain

**File:** `services/*/Dockerfile` (no `USER`; `build-essential` installed at line ~14-16 and never removed from the final image); `docs/architecture.md:280` (acknowledged)
**Issue:** Gateway, Identity (which holds the RSA key via the secret mount) and Patient (PHI) all run as uid 0 with gcc available. A compromise of any worker has root in the container and can compile payloads.
**Failure scenario:** RCE in a dependency yields root inside the Identity container, where `/run/secrets/jwt_private.pem` is readable. Non-root plus a read-only rootfs would limit what an attacker can do next.
**Fix:** Multi-stage build (compile wheels in a builder stage, copy a venv into a clean `python:3.12-slim`), add `RUN useradd -r app && USER app`, and mount the secret with a group readable by that user. Use `read_only: true` and `cap_drop: [ALL]` in compose.

## Info

### IN-01: Cross-service account links do not check the linked account's role or clinic

**File:** `services/patient/api/patients.py:156-166`; `services/provider/api/providers.py:131-144`; `libs/service_client.py:200-212`
**Issue:** `validate_user` only checks that the id exists, and `UserRef` carries `role` and `clinic_id` that are ignored. A patient profile can be linked to an admin or provider account, a provider profile to a patient account, and a patient in clinic A to a user whose `clinic_id` is null or from another clinic.
**Fix:** Require `role == "patient"` or `"provider"` as appropriate, and require `user.clinic_id in (None, profile_clinic_id)`. Do this before Phase 2 grants "own profile" access via `user_id`.

### IN-02: Email handling: registration enumerates accounts, and uniqueness is case-sensitive

**File:** `services/identity/api/auth.py:145-160`; `services/identity/repository/models.py:54`
**Issue:** The login path was hardened against enumeration (constant-time dummy bcrypt), but `/register` returns 409 "email already registered". `EmailStr` lowercases only the domain, and `users.email` is a case-sensitive unique column, so `Alice@x.com` and `alice@x.com` become two accounts.
**Fix:** Store and look up `lower(email)` (a unique index on `lower(email)`), and consider a generic registration response.

### IN-03: `bootstrap_admin.py` has no password policy and no clean failure if the audit write fails after commit

**File:** `scripts/bootstrap_admin.py:152-153`, `:120-133`
**Issue:** The API enforces `min_length=8`, but the script accepts any non-empty `BOOTSTRAP_ADMIN_PASSWORD`, so the highest-privilege account can be created with `"a"`. A Mongo failure after the commit leaves the admin created but exits 1 (see WR-04), and the script's own docstring says the creation is audited. The documented unverified creation branch (`docs/architecture.md:281`) is also untested.
**Fix:** Enforce the same minimum (preferably 12+) and a common-password check. Write the audit entry inside a try/except that prints a warning with the user id.

### IN-04: Test fixtures can pollute real stores

**File:** `tests/conftest.py:258-264`, `:269-278`, `:285-307`
**Issue:**
- `redis_client` calls `flushdb()` on `REDIS_URL` db 0, which is the same Redis the dev compose stack uses for the denylist and rate-limit counters.
- `mongo_client` drops `{mongo_db_name}_test`, but `write_audit` writes to `mongo_db_name` itself (`libs/audit/writer.py:67`), so the drop cleans up nothing.
- `insert_admin_user` commits admin accounts with the known password `correct-horse-battery` into whatever `IDENTITY_DATABASE_URL` points at and never cleans them up.

Pointing the suite at a shared or staging database leaves permanent known-password admins.
**Fix:** Use a dedicated Redis db index and Mongo database name for tests (override `shared_settings` in conftest), and delete the seeded users in fixture teardown or use unique per-run databases.

### IN-05: Stale docstrings reference files that no longer exist

**File:** `libs/auth/denylist.py:7-8` (cites `services/identity/security/current_user.py::get_current_user`); `services/identity/security/__init__.py:1-5` (describes `current_user` and `rbac` modules); `libs/observability/__init__.py:3` (cites `services/identity/app.py`)
**Issue:** `services/identity/security/current_user.py` appears in the phase diff as deleted and is absent from the tree. The real implementation is `libs/auth/current_user.py`.
**Fix:** Update the docstrings to the `libs/auth` locations.

### IN-06: Availability templates have no upper bound on duration and no overlap guard

**File:** `services/provider/api/availability.py:84`; `services/provider/domain/schemas.py:45`
**Issue:** `slot_duration_minutes: int = Field(gt=0)` has no upper bound. One minute yields up to 1,440 slots per day per template, and `100000` is accepted. Overlapping templates for the same provider and day are allowed (noted in the docs as awaiting mentor confirmation), and the window need not be a multiple of the duration.
**Fix:** Add `le=480` (or a sensible clinic cap) and a check that the window is divisible by the duration. Add an overlap check on create and update.

### IN-07: Model and migration disagree on `users.clinic_id` index

**File:** `services/identity/repository/models.py:60`; `services/identity/migrations/versions/identity_0001_accounts.py` (`op.create_index("ix_users_clinic_id", ...)`)
**Issue:** The migration creates `ix_users_clinic_id` but the model does not declare `index=True`, so `alembic revision --autogenerate` would propose dropping the index.
**Fix:** Add `index=True` to the `clinic_id` column in the model (the other services' models match their migrations).

### IN-08: Departments can be created under an inactive clinic

**File:** `services/organization/repository/org_repo.py:99-107`
**Issue:** `create_department` only checks that the clinic exists, not that `is_active` is true. D-06 says there is no cascade, but creating new children under a deactivated parent is a write-time integrity gap. Provider creation later rejects the department only if the department itself is inactive.
**Fix:** Return None (or raise) when `clinic.is_active` is false, and map it to a 422 in the router.

### IN-09: PATCH cannot clear optional fields

**File:** `services/patient/repository/patient_repo.py:102-105`; `services/provider/repository/provider_repo.py:269-272`
**Issue:** The repositories treat `None` as "unchanged", so `phone`, `address` and `effective_to` can never be cleared once set, even though `model_fields_set` shows the client sent `null` explicitly. The audit entry then lists a field as changed that was not.
**Fix:** Drive updates from `payload.model_dump(exclude_unset=True)` and apply explicit nulls.

### IN-10: `clinic_scope_permits` is fail-open for a missing clinic claim, unlike Patient's fail-closed rule

**File:** `libs/auth/internal.py:173-174`; compare `services/patient/api/patients.py:105-111`
**Issue:** A non-admin user token with no `clinic_id` claim (FRONT_DESK or PROVIDER accounts can be created clinic-less) is treated as unscoped by every `/internal/*` lookup. A target with no clinic is likewise visible to all. `_assert_clinic_scope` in Patient treats the same caller as 403. No exploit path exists today because `/internal` is unreachable from outside and the public routes gate first, but the two rules diverge and a later caller that skips the public gate inherits the open default.
**Fix:** Make `clinic_scope_permits` return False for non-admin user callers with no clinic claim and a clinic-bound target, and rely on the service-caller branch for unscoped internal calls.
