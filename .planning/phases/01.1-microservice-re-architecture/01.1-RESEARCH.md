# Phase 01.1: Microservice Re-architecture - Research

**Researched:** 2026-09-30
**Domain:** Monolith→microservices decomposition of an existing FastAPI/SQLAlchemy/Postgres/Mongo/Redis system — service boundaries, database-per-service, RS256/JWKS auth, API gateway, synchronous cross-service integrity checks, distributed tracing across HTTP hops.
**Confidence:** HIGH for the mechanics verified directly against this repo's code and against live registries/official docs this session; MEDIUM/LOW (tagged inline) for a few library-selection and test-strategy judgment calls that are this phase's genuine open design space.

## Summary

Phase 1 delivered one FastAPI monolith (`services/identity`) with all data in one Postgres database, RBAC via HS256 JWTs, and a shared audit/observability layer. This phase does not add functionality — it re-delivers the *same* IAM/PPL/ORG/OBS-04/DASH-01/02 requirements as six independently deployable services (API Gateway, Identity, Organization, Provider, Patient, Scheduling-skeleton), each with its own Postgres database, own Dockerfile, own Alembic migration history, and its own `/metrics`/tracing identity. Every mechanism this split needs already has a proof-of-concept in the existing codebase: `setup_tracing(app, service_name=...)` already takes a per-service name parameter (`libs/observability/otel.py:58`), `ensure_audit_indexes()` is already idempotent and safe to call from six processes concurrently (`libs/audit/mongo_indexes.py:11`), and `smarthealth/db.py`'s loop-aware engine/client singletons are already a reusable pattern — they just need to stop reading one hardcoded global `Settings` object and instead take a `database_url` per service.

The two genuinely new capabilities this phase must build are (1) RS256 signing + a JWKS endpoint on Identity, with every other service fetching and caching that JWKS locally (never calling Identity per-request to verify a token — that would silently reintroduce a synchronous hard dependency on every protected request across the whole system), and (2) a thin FastAPI gateway that proxies `/api/*` to the owning service over `httpx.AsyncClient` and applies Redis-backed rate limiting, while every service still independently verifies JWTs and enforces RBAC (defence in depth, required by SC3). Cross-service foreign keys become synchronous REST validation calls at write time (D-05) — this is the one place genuinely new failure modes are introduced (upstream-unavailable failures, defined error mapping), and it is the most consequential judgment call between "convenient to build in 3 weeks" and "textbook microservices" that the roadmap explicitly wants the dashboard to defend.

**Primary recommendation:** Keep one root `pyproject.toml`/dependency manifest (all six services already agree on the same pinned stack — no reason to fragment it), give each service its own `services/<name>/` directory + `Dockerfile` + `migrations/` + fresh single-baseline Alembic revision, move the *code* of `smarthealth/db.py`'s loop-aware singleton pattern into `libs/db/` parameterized by a URL, split `libs/auth` into a signing half (Identity-only, needs the private key) and a verification half (every service, JWKS-based, no private key), and test the whole stack two ways: fast in-process multi-app tests using `httpx.AsyncClient(mounts={...ASGITransport...})` (verified pattern, no real network, no Docker required) for the daily loop, plus a smoke suite that runs against `docker compose up`'s published gateway port for the SC5 acceptance check.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Service cut**
- **D-01:** Full cut — six deployables: **API Gateway** (edge routing + rate limiting), **Identity** (`users`, login/register/refresh/logout, token issuance, Redis denylist), **Organization** (`clinics`, `departments`), **Provider** (`providers`, `specialties`, provider↔specialty link, `availability_templates`), **Patient** (`patients` — only service holding patient PHI), **Scheduling (skeleton)** (see D-03). Organization and Provider are deliberately separate even though providers→departments and availability→departments become cross-service checks. Reversibility: costly.
- **D-02:** Audit stays a shared library (`libs/audit`, `write_audit()`) this phase — no dedicated Audit service yet (Phase 3). PHI-safe document shape unchanged. Keep the call signature stable so Phase 3 can swap internals for a Kafka producer without touching callers.
- **D-03:** Create a minimal Scheduling service skeleton now. It owns `provider_slots` together with `btree_gist`, the `ex_provider_slots_no_overlap` exclusion constraint, and the existing constraint test. Own database, migration, Dockerfile, Compose entry, health endpoint. `provider_slots.provider_id` becomes a plain UUID with no foreign key.
- **D-04:** Identity owns accounts only (credentials, role, `clinic_id`). Patient/Provider profiles store `user_id` as a plain UUID with no foreign key; the owning service validates the ID through an Identity API call when linking. PHI never enters Identity; credentials never enter Patient/Provider. Profile creation does NOT create the login account — they stay separate operations.

**Cross-service integrity**
- **D-05:** References are checked with a synchronous REST call to the owning service at write time. Missing/inactive target → 422. Owning service unreachable → the write fails. Applies to: `users.clinic_id`→Organization, `patients.clinic_id`→Organization, `patients.user_id`→Identity, `providers.user_id`→Identity, `providers.department_id`→Organization, `availability_templates.department_id`→Organization. Validate at write time, never join at read time.
- **D-06:** Deactivating a referenced record is allowed and does not cascade. Existing references keep their IDs; only new creates/updates pointing at an inactive target are rejected (422). No reverse call, no distributed transaction.
- **D-07:** Reads return IDs only. Each service returns its own data plus foreign IDs; clients combine data themselves. No service enriches reads by calling other services; the gateway does not aggregate (no BFF). Keep Phase 1 response shapes wherever they already return IDs.
- **D-08:** Kafka and the outbox stay in Phase 3. No event publishing, no outbox tables this phase. Dashboard must record why integrity checks are synchronous now and move to events later.

### Claude's Discretion
- **API gateway implementation:** Default = thin FastAPI gateway (httpx proxying, Redis rate limiting) — shows understanding for the graded review. Self-hosted Traefik/Nginx acceptable alternative if justified. Every service verifies the JWT itself regardless (defence in depth); gateway may also reject early. Do not recommend Zoho or other SaaS gateways.
- **Repo and data layout:** Default = monorepo, `services/<name>/` each with `app.py`, `api/`, `domain/`, `repository/`, migrations dir, Dockerfile, tests. Shared `libs/` becomes infra-only (token verification/JWKS client, audit writer, OTel/structlog setup, db/session helpers) — never domain models. Default DB layout = separate Postgres databases on one Postgres container for local dev, one database + one DB role per service, no cross-service DB access. Mongo audit collections per-service or shared per D-02 — planner decides and documents.
- **Service-to-service auth:** Default = forward the caller's JWT on internal calls so the callee re-applies RBAC/clinic scope. Internal-only endpoints (e.g. `/internal/departments/{id}`) are not routed by the gateway. A service token is acceptable if a call has no user context.
- **Token signing:** RS256 with a JWKS endpoint on Identity (roadmap-mandated). Only Identity holds the private key. Key-loading mechanism for local dev (file mounted from Compose secrets, or env var) is the planner's choice. Key must never be committed.
- **Internal call behaviour:** `httpx.AsyncClient` with explicit timeouts + bounded retry for idempotent GETs only. Trace context must propagate across internal calls (OTel `httpx` instrumentation) so one request is a single connected trace in Jaeger.
- **Migration strategy:** Planner chooses extract-in-place vs. rewrite-per-service. Phase 1 behaviour tests must be re-pointed at the gateway and stay green. Alembic history splits per service with a fresh baseline per service database; planner decides whether to keep the existing `0001`/`0002` revisions.

### Deferred Ideas (OUT OF SCOPE)
- Dedicated Audit service consuming a Kafka audit topic, replacing direct library writes (Phase 3).
- Local copies of reference data kept current by events (e.g. Provider caching departments), removing the availability coupling of synchronous checks (Phase 3, needs Kafka/outbox first).
- Cascading deactivation (e.g. department cascading to its providers) via events/orchestration — not planned; revisit only if a requirement appears.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Edge routing, rate limiting, TLS termination (future) | API / Backend (Gateway) | — | Gateway is the single ingress; owns per-route rate limits and forwards to the owning service. No aggregation (D-07 — not a BFF). |
| Token issuance, RS256 signing, JWKS publication | API / Backend (Identity) | — | Only Identity holds the private key (locked decision). |
| Token verification, RBAC enforcement | API / Backend (every service) | — | "Every other service verifies tokens locally" (SC3) — defence in depth, not gateway-only. |
| Clinic/department data + validation | API / Backend (Organization) | Database / Storage (Organization's own Postgres DB) | Organization owns the org hierarchy; other services call it read-only for reference validation (D-05). |
| Provider/specialty/availability-template data | API / Backend (Provider) | Database / Storage (Provider's own Postgres DB) | Kept separate from Organization per explicit user preference for finer bounded contexts (D-01). |
| Patient PHI | API / Backend (Patient) | Database / Storage (Patient's own Postgres DB) | Sole PHI-holding service; Identity/Organization/Provider never see PHI fields. |
| `provider_slots` + exclusion constraint | API / Backend (Scheduling skeleton) | Database / Storage (Scheduling's own Postgres DB) | Isolated now so Phase 2 never moves this table between service databases (D-03). |
| Audit trail writes | API / Backend (every service, via shared `libs/audit`) | Database / Storage (shared Mongo `audit_log`) | D-02: stays a library, not a service, this phase. Mongo is cross-cutting infra, not one of the six "service databases" under the no-cross-service-DB-access rule. |
| Token revocation (denylist) | API / Backend (every service, via shared `libs/auth/denylist`) | Database / Storage (shared Redis) | Redis is cross-cutting infra like Mongo — not subject to D-01's per-service Postgres isolation. |
| Distributed tracing / metrics | API / Backend (every service) | CDN/Static N/A | Each service sets its own OTel `service_name` and exposes its own `/metrics`; Prometheus/Jaeger aggregate centrally. |

### Pattern 1: RS256 Signing + JWKS Publication (Identity) / Local Verification (everyone else)

**What:** Identity signs access/refresh tokens with an RSA private key (`RS256`) and publishes the public key as a JWKS document. Every other service fetches that JWKS once at startup (cached in memory, refreshed on a `kid` cache-miss or a timer), and verifies incoming tokens **locally** — no network call per request.
**When to use:** Any time a token issuer and token verifiers are different deployables (this is the standard OIDC/JWKS pattern — `[CITED: RFC 7517 — JSON Web Key]`, and the same shape used by every OIDC provider's `/.well-known/jwks.json`).
**Example (verified this session against `python-jose==3.5.0` in a real interpreter, not from memory):**
```python
# libs/auth/signing.py — Identity-only (holds the private key)
from cryptography.hazmat.primitives.asymmetric import rsa
from cryptography.hazmat.primitives import serialization
from jose import jwt

private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
priv_pem = private_key.private_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PrivateFormat.PKCS8,
    encryption_algorithm=serialization.NoEncryption(),
).decode()

# kid identifies which key signed this token — required for JWKS rotation support.
token = jwt.encode({"sub": user_id, "role": role}, priv_pem, algorithm="RS256",
                    headers={"kid": "smarthealth-identity-2026-09"})
```
```python
# libs/auth/jwks_client.py — every service, published-key half
from jose import jwk

def public_pem_to_jwk_dict(pub_pem: str, kid: str) -> dict:
    public_jwk = jwk.construct(pub_pem, algorithm="RS256")
    d = public_jwk.to_dict()          # -> {"kty": "RSA", "n": "...", "e": "AQAB"}
    d.update(kid=kid, use="sig", alg="RS256")
    return d

# GET /.well-known/jwks.json on Identity returns: {"keys": [public_jwk_dict, ...]}
```
```python
# every verifying service, at startup + on kid cache-miss:
from jose import jwt

def verify(token: str, jwks_by_kid: dict[str, dict]) -> dict:
    unverified_header = jwt.get_unverified_header(token)
    key = jwks_by_kid[unverified_header["kid"]]     # the JWK dict from the cached JWKS
    return jwt.decode(token, key, algorithms=["RS256"])   # verified locally, no network call
```
**Verified fact (this session, real interpreter run, `python-jose==3.5.0`):** `jwk.construct(pub_pem, algorithm="RS256").to_dict()` returns exactly `{"alg": "RS256", "kty": "RSA", "n": "<base64url modulus>", "e": "AQAB"}`, and `jwt.decode(token, that_dict, algorithms=["RS256"])` successfully verifies a token signed with the matching private PEM via `jwt.encode(..., algorithm="RS256")`. This is the exact code path the pattern above depends on.

### Pattern 2: Synchronous Reference Validation (D-05)

**What:** Instead of a Postgres foreign key, the writing service calls the owning service's `/internal/<resource>/{id}` endpoint before committing. Missing or `is_active=false` → 422. Network/5xx failure from the owning service → the write fails (502/503), not a silent success.
**When to use:** Every cross-service reference this phase (`users.clinic_id`, `patients.clinic_id`, `patients.user_id`, `providers.user_id`, `providers.department_id`, `availability_templates.department_id`).
**Example:**
```python
# libs/service_client.py
import httpx
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

class ReferencedResourceInvalid(Exception):
    """Maps to 422 in the caller's router."""

class UpstreamServiceUnavailable(Exception):
    """Maps to 503 in the caller's router."""

@retry(
    retry=retry_if_exception_type(httpx.TransportError),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=0.1, max=1.0),
)
async def _get(client: httpx.AsyncClient, url: str, *, bearer_token: str) -> httpx.Response:
    return await client.get(url, headers={"Authorization": f"Bearer {bearer_token}"}, timeout=2.0)

async def validate_department(client: httpx.AsyncClient, department_id, bearer_token: str) -> None:
    try:
        resp = await _get(client, f"http://organization:8000/internal/departments/{department_id}",
                           bearer_token=bearer_token)
    except httpx.TransportError as exc:
        raise UpstreamServiceUnavailable("organization service unreachable") from exc

    if resp.status_code == 404 or (resp.status_code == 200 and not resp.json()["is_active"]):
        raise ReferencedResourceInvalid(f"department {department_id} is missing or inactive")
    if resp.status_code >= 500:
        raise UpstreamServiceUnavailable(f"organization returned {resp.status_code}")
```
The retry is scoped to *transport* errors only (connection refused/timeout), never retrying a 422/404 business rejection — retrying an idempotent GET is safe; the bounded `stop_after_attempt(3)` keeps the p99 latency impact small and finite (CONTEXT.md's "bounded retry for idempotent GETs only").

### Pattern 3: Testing Multiple Services Without a Live Network (fast dev-loop tests)

**What:** `httpx.AsyncClient` supports mounting a different transport per URL/host — including `ASGITransport` instances pointed at *different* in-process FastAPI apps. This lets the existing test suite's in-process style (no Docker required) extend across service boundaries.
**When to use:** Fast per-plan/per-commit test runs (see Validation Architecture). Not a substitute for the docker-compose smoke suite (SC5's actual acceptance check).
**Example** `[CITED: python-httpx.org/advanced/transports — official httpx docs, "Mounting Transports"]`:
```python
import httpx
from services.gateway.app import create_app as create_gateway_app
from services.identity.app import create_app as create_identity_app
from services.organization.app import create_app as create_organization_app

async def build_test_client() -> httpx.AsyncClient:
    return httpx.AsyncClient(
        base_url="http://gateway",
        transport=httpx.ASGITransport(app=create_gateway_app()),
        mounts={
            "http://identity":     httpx.ASGITransport(app=create_identity_app()),
            "http://organization": httpx.ASGITransport(app=create_organization_app()),
        },
    )
```
The gateway's own `httpx.AsyncClient` (used to proxy) must be constructed the same way in tests — point its base URLs at `http://identity`, `http://organization`, etc., and mount the corresponding ASGI apps, so a full gateway→service round-trip runs in-process with zero real sockets.

### Pattern 4: Per-Service Alembic (fresh baseline)

**What:** Each service gets its own `migrations/` directory + `alembic.ini`, its own `env.py` importing *only that service's* SQLAlchemy models, and a single fresh `0001_initial_schema.py` reflecting only the tables it owns — not a replay of the monolith's `0001_initial_schema.py` + `0002_soft_delete_columns.py` (those touched every table across every future service).
**When to use:** This phase, for all five data-owning services (Gateway has no database).
**Example directory contract:**
```
services/organization/migrations/
├── alembic.ini            # sqlalchemy.url points at ORGANIZATION_DATABASE_URL
├── env.py                 # target_metadata = OrganizationBase.metadata (NOT the
│                           #   old shared smarthealth.db.Base — see Common Pitfalls)
└── versions/
    └── 0001_initial_schema.py   # clinics + departments only, incl. soft-delete columns
                                   #   from day one (no need to replay 0002 separately)
```
`[CITED: sqlalchemy/alembic GitHub Discussions #1618, #1522 — "separate migration directories... configure alembic.ini to specify migration paths for each service"]` — this is the documented community pattern for exactly this situation (multiple independently-versioned schemas in one monorepo), not a novel invention.

### Anti-Patterns to Avoid

- **One shared `Base.metadata` across services:** The current `smarthealth/db.py:29` defines a single `class Base(DeclarativeBase)` that every Phase-1 model attaches to. If services keep importing this same `Base`, every service's `alembic revision --autogenerate` sees every *other* service's tables too (they're all registered on one `MetaData` object), producing migrations that try to create tables the running service doesn't own and doesn't have permission to touch under its own DB role. **Do this instead:** each service declares its own `class Base(DeclarativeBase)` (or its own `MetaData()` instance) in its own `repository/models.py`; nothing shares Base/metadata across service boundaries — only the *engine/session factory pattern* (the code in `libs/db/postgres.py`) is shared, parameterized per service.
- **Verifying tokens by calling Identity synchronously on every request:** This is the single most likely way to accidentally violate "verifies tokens locally" (SC3) while still technically working in a demo — it silently makes Identity a hard dependency for every protected request on every other service, exactly the kind of availability coupling the dashboard is supposed to flag as a *deliberate, contained* tradeoff (D-05's reference checks), not an *accidental* one baked into auth itself.
- **Gateway aggregating responses (BFF-style):** D-07 explicitly forbids this. The gateway proxies one route to one service and returns that service's response unmodified (aside from stripping hop-by-hop headers) — it never fans out to multiple services and merges results.
- **Publishing `/internal/*` routes on the gateway's route table:** Even though network isolation (no host port published for non-gateway containers) already blocks external access, defense-in-depth means the gateway's own routing table must not contain `/internal/*` prefixes at all — not "allowed but unreachable," genuinely absent from the proxy's route map.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| RSA keypair generation / PEM encoding | A custom ASN.1/PEM encoder | `cryptography.hazmat.primitives.asymmetric.rsa.generate_private_key()` + `.private_bytes()`/`.public_bytes()` (already a transitive dependency of `python-jose[cryptography]`, verified installed and working this session) | Key format bugs are exactly the kind of subtle, hard-to-test-for-yourself mistake a security review would catch — `cryptography` is the industry-standard, audited library for this. |
| JWKS document construction | Hand-built base64url modulus/exponent encoding | `jose.jwk.construct(pem, algorithm="RS256").to_dict()` (verified this session to produce a spec-correct `{kty, n, e}` triple that round-trips through `jwt.decode`) | Getting base64url *without* padding wrong, or getting big-endian modulus encoding wrong, produces a JWKS entry that looks plausible but fails verification for every client — a very hard bug to notice locally. |
| Atomic Redis rate-limit counters | Two separate `INCR` + `EXPIRE` Redis calls from Python | A single Lua script (`EVAL`) wrapping both, OR the fixed-window pattern Redis's own docs describe | `[CITED: redis.io/docs/latest/develop/use-cases/rate-limiter/]` — two separate round-trips have a race window where a key's TTL is never set (a crashed/interleaved request leaks a permanent counter key), which is exactly the kind of concurrency bug that won't show up in a single-user local demo but appears under the project's own "peak booking window" load-testing goals. |
| Cross-service distributed transactions for D-05/D-06 | A 2PC/saga coordinator for reference checks | Plain synchronous REST validation + 422/503 (as locked in D-05/D-06) | Explicitly out of scope this phase — Kafka/outbox/compensation belongs to Phase 2/3; building a transaction coordinator now would be solving a problem the roadmap has deliberately deferred. |
| W3C trace-context propagation across `httpx` calls | Manually reading/writing `traceparent` headers on every internal call | `HTTPXClientInstrumentor().instrument()` (same OTel auto-instrumentation family already used for FastAPI) | Once instrumented, every `httpx.AsyncClient` call automatically carries the active span's trace context — hand-writing this is easy to get subtly wrong (e.g., forgetting propagation on a retried request) and there's no reason to when the same vendor's contrib package already solves it. |

**Key insight:** Every "don't hand-roll" item above already has an existing, already-installed, already-verified-this-session library backing it (`cryptography`, `jose.jwk`, `HTTPXClientInstrumentor`) or an explicit locked decision (D-05/D-06) — this phase's actual new-code surface is thin: wiring, not cryptography or distributed-systems primitives.

## Common Pitfalls

### Pitfall 1: Verifying tokens "locally" but still calling Identity synchronously
**What goes wrong:** A service's JWT-verification dependency is written to call `GET http://identity:8000/verify` on every request "just to be safe," instead of caching Identity's JWKS.
**Why it happens:** It's the simplest thing to write first, and it works fine in a single-request manual test — the failure mode (Identity becomes a hard dependency for every request on every service, and a slow/down Identity now cascades everywhere) only shows up under load or during an Identity outage, neither of which is visible in a quick manual demo.
**How to avoid:** Fetch and cache the JWKS at service startup (and on a `kid` cache-miss, with a short negative-cache backoff to avoid hammering Identity if a `kid` is genuinely bogus); verify every subsequent token against the cached key material only.
**Warning signs:** Grep for any `httpx` call to the Identity service inside a request-scoped auth dependency (as opposed to a startup/background-refresh task) — that call site is the bug.

### Pitfall 2: Sharing one Alembic `Base`/metadata across services
**What goes wrong:** New services keep importing `smarthealth.db.Base` (the existing shared declarative base) for convenience. `alembic revision --autogenerate` for, say, Organization's migration then "sees" Patient's and Provider's tables too (they're all on the same `MetaData` object) and may try to generate DDL for tables Organization's database doesn't have and Organization's DB role has no permission to create.
**Why it happens:** It's the path of least resistance when copy-pasting Plan 01-02's existing model file into new services — the import already works, so there's no visible error until the first `alembic revision --autogenerate` run against a scoped-permission role.
**How to avoid:** Each service defines its *own* `class Base(DeclarativeBase)` and its own `env.py`'s `target_metadata = <ServiceName>Base.metadata`. See Architecture Patterns → Anti-Patterns.
**Warning signs:** An autogenerated migration file mentions a table name that doesn't belong to the service you're migrating.

### Pitfall 3: Postgres init scripts only run once, on an empty data directory
**What goes wrong:** The planner adds a `docker-entrypoint-initdb.d` shell script to create five new databases + roles, runs `docker compose up`, and nothing happens — the existing `postgres_data` named volume already has data from Phase 1, so Postgres skips all init scripts on every subsequent boot.
**Why it happens:** `[CITED: Docker official postgres image documentation]` — init scripts under `/docker-entrypoint-initdb.d` are explicitly documented to run "only run if you start the container with a data directory that is empty" — this is correct, well-documented Postgres-image behavior, not a bug, but it's easy to forget when a volume from a previous phase is still sitting on disk.
**How to avoid:** Document explicitly (dashboard + a README note) that this phase requires `docker compose down -v` (drop volumes) before the new multi-database init script will run, consistent with the Runtime State Inventory's "stored data" recommendation to treat existing dev data as disposable.
**Warning signs:** New services fail to connect with "database does not exist" even though the init script file is present and correctly mounted.

### Pitfall 4: Rate-limiting mid-tier failures silently "fail open" or "fail closed" without a decision
**What goes wrong:** The Redis connection used by the gateway's rate limiter goes down (e.g., during a demo, or a container restart race), and the gateway either (a) rejects every request with 500 (fail-closed, taking down the whole system for a rate-limiter outage) or (b) silently lets everything through with no logging (fail-open, invisible).
**Why it happens:** Neither behavior is wrong per se, but *not deciding* — leaving whatever `try/except` shape falls out of the first implementation attempt — means the dashboard can't honestly describe the gateway's failure mode, which a mentor review is likely to probe.
**How to avoid:** Explicitly choose fail-open (log a warning, skip rate limiting, let the request through) for a local-dev/graded-assignment context, since availability of the core booking-adjacent flows matters more than strict rate-limit enforcement, and document that choice in the dashboard next to the gateway decision card.
**Warning signs:** No test exercises "Redis is down" as an explicit gateway rate-limiter test case.

### Pitfall 5: `deactivated_at`/`is_active` checks skipped in the D-05 validation call
**What goes wrong:** The owning service's `/internal/departments/{id}` endpoint returns 200 for any row that exists, regardless of `is_active`, so a caller creating a provider against a *deactivated* department succeeds when D-06 requires it to be rejected (422) for new writes.
**Why it happens:** The existing `get_department()` repository function (`services/identity/repository/org_repo.py:125-137`) is an id-only lookup with no active-status filtering built in — it was designed for internal chain-resolution (provider→department→clinic), not as a security/integrity boundary; reusing it as-is for the new `/internal/` endpoint silently drops the D-06 "inactive target rejected" requirement.
**How to avoid:** The `/internal/<resource>/{id}` endpoint must explicitly check `is_active` and return either a 404-shaped response or an explicit `is_active: false` field the caller checks, mirroring the Pattern 2 code example above (`resp.json()["is_active"]`).
**Warning signs:** A test that deactivates a department and then successfully creates a provider under it (should be 422, per D-06) passes when it shouldn't.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | yes | RS256 JWT via `python-jose`, JWKS-based verification (Pattern 1) |
| V3 Session Management | yes | Existing Redis jti-denylist (`libs/auth/denylist.py`), now consulted by every service, not just Identity |
| V4 Access Control | yes | `require_role()` RBAC guard, re-applied independently in every service (defence in depth per SC3) |
| V5 Input Validation | yes | Pydantic v2 schemas, unchanged pattern from Phase 1 |
| V6 Cryptography | yes | RSA-2048 keypair via `cryptography` (never hand-rolled — see Don't Hand-Roll); private key never leaves Identity's process/container |
| V13 API and Web Service | yes (new this phase) | Gateway is the sole ingress; `/internal/*` endpoints excluded from the gateway's route table AND not published to the host (network-level isolation, defense in depth per Anti-Patterns) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| A compromised non-Identity service forging tokens for other roles | Spoofing / Elevation of Privilege | RS256 (asymmetric) instead of HS256 (symmetric) — only Identity's process holds the private key; every other service can only *verify*, never *sign* (this is the core security win of this phase's auth redesign, not just an architecture one). |
| A revoked token still accepted by a non-Identity service that forgot to check the denylist | Elevation of Privilege | Every service — not only Identity — must call `is_revoked()` against the shared Redis denylist on every request (explicit locked recommendation in this research, resolving the CONTEXT.md-flagged open discretion item). |
| Enumeration via the D-05 internal validation endpoints (e.g., probing `/internal/departments/{id}` for existence across clinics) | Information Disclosure | `/internal/*` endpoints are unreachable from outside the Compose network (no published host port) AND excluded from the gateway's route table — combined with the existing Phase-1 clinic-scoping discipline already enforced at the repository layer. |
| Gateway rate-limiter failure silently disabling protection (or silently blocking all traffic) | Denial of Service | Explicit fail-open decision + logged warning (Common Pitfalls #4) — not left as an accidental default. |
