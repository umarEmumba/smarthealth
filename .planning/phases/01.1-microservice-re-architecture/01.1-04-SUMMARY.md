# Phase 01.1 Plan 04: Trace propagation, vetted dependencies and gateway rate limiting Summary

**One request through the gateway is now one connected trace across gateway, Organization and Identity (W3C context injected via the propagator API on every internal hop, audit trace ids matching), and the gateway rate-limits per client IP with an atomic Redis Lua window, 429 + Retry-After, and a Redis-outage fail-open that always logs and counts itself.**

## Accomplishments

- **Trace propagation (Task 1).** `libs/http.outgoing_headers` is the only place trace headers are produced. `services/gateway/proxy.py` drops any inbound `traceparent`/`tracestate` and re-injects the gateway span's own context (a client cannot splice a foreign parent), and `JwksClient.refresh` sends `outgoing_headers()` on the JWKS GET. The e2e tests select finished SERVER spans by `http.route`, assert one shared trace_id, and check the audit document's `trace_id` equals it.
- **Package legitimacy gate (Task 2).** See Authentication Gates below.
- **httpx client spans (Task 3).** `instrument_httpx_client_spans()` guards `HTTPXClientInstrumentor().instrument()` with a module flag and is called from `setup_tracing`; no request/response hooks are registered, so no headers or bodies reach a span.
- **Rate limiter (Task 3).** `FIXED_WINDOW_LUA` does INCR, PEXPIRE only when the count is 1, and PTTL in one EVAL. Budgets come from `GATEWAY_RATE_LIMIT_AUTH_PER_MINUTE` (20) and `GATEWAY_RATE_LIMIT_DEFAULT_PER_MINUTE` (300). The key is `ratelimit:{group}:{client_ip}` from the socket peer. Redis timeouts are 0.5 s. `Retry-After` is the remaining TTL rounded up and clamped to 1..60.

## Harness change made in Task 1 (the e2e tests depend on it)

`tests/conftest.py` gained `_NetworkHopTransport`, and `mesh` now mounts every service app behind it. Each mesh hop runs the inner ASGI transport in its own task created with an EMPTY `contextvars.Context`. Reason: awaiting the callee's ASGI app directly shares the caller's contextvars (including the active OpenTelemetry span), which would make a trace look connected even if no `traceparent` header were ever sent. Over a real network the callee inherits nothing and learns the trace only from the header, so the isolation is what makes the connected-trace assertion meaningful. Any later plan that adds a service to `HARNESS_SERVICES` inherits this behaviour; reverting it would let a missing-header regression pass silently. This file's Task 3 change is separate: two `os.environ.setdefault` lines lifting both gateway budgets to 100000.

## Deferred Issues

- **Gateway request-body size cap (carry-over threat flag `unbounded-request-body` from 01.1-03): NOT addressed here.** `proxy.forward` still does `await request.body()` with no limit. A correct cap needs a streaming read that counts bytes (a `Content-Length` check alone is bypassed by chunked bodies), a new setting and its own tests; it is not in this plan's requirements or threat register, so it was left out rather than half-done. Suggested owner: plan 01.1-09 together with the edge hardening, or a small follow-up plan. The rate limiter bounds request COUNT per IP, not request SIZE, so it does not mitigate this.
- **`/metrics` unauthenticated on the public ingress (threat flag from 01.1-03):** unchanged, owned by plan 01.1-09. It is also exempt from rate limiting by design here, so it should be restricted at the network or listener level there.
- No tenacity code exists yet; it is pinned so plan 01.1-05's reference checks can import it.
