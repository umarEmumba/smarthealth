# Phase 01.1: Microservice Re-architecture - Context

**Gathered:** 2026-09-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Re-deliver the completed Phase 1 monolith (`services/identity`, one FastAPI app on one Postgres database) as a true microservice architecture, following the week-1 mentor review. Every Phase 1 behaviour must keep working end-to-end: IAM, RBAC, clinic/department/patient/provider/availability CRUD with PATCH and soft-delete, the audit trail, and PHI-safe logging and tracing. After the split, each service is independently deployable and owns its own data.

**In scope:** splitting services, database-per-service, removing cross-service foreign keys, an API gateway, RS256/JWKS token verification, per-service Dockerfile/migrations/tests, Compose wiring, and the dashboard update (service map plus rationale for the monolith→microservices decision).

**Out of scope:** any new functional capability. Appointments, booking saga, waitlist, visits and billing belong to Phase 2. Kafka, outbox, Celery, analytics and the dedicated Audit service belong to Phase 3.

</domain>

<decisions>
## Implementation Decisions

### Service cut
- **D-01:** The **full** cut was chosen over the lean one. Six deployables:
  - **API Gateway:** edge routing and rate limiting.
  - **Identity:** `users` table, login/register/refresh/logout, token issuance, Redis denylist.
  - **Organization:** `clinics`, `departments`.
  - **Provider:** `providers`, `specialties`, the provider↔specialty link, `availability_templates`.
  - **Patient:** `patients`. This is the only service holding patient PHI.
  - **Scheduling (skeleton):** see D-03.

  Organization and Provider are deliberately separate, even though providers→departments and availability→departments therefore become cross-service checks. The user preferred finer boundaries over the merged "Provider Directory" option. — **Reversibility:** costly — merging or splitting later means moving tables between service databases and rewriting the internal calls between services.
- **D-02:** **Audit stays a shared library** (`libs/audit`, `write_audit()`) in this phase. Each service writes its own audit records through the library, and the locked PHI-safe document shape is unchanged. A dedicated Audit service fed by a Kafka audit topic is Phase 3 work. Keep the library's call signature stable so Phase 3 can swap its internals for a Kafka producer without touching the services that call it.
- **D-03:** Create a **minimal Scheduling service skeleton now**. It owns `provider_slots` together with its `btree_gist` extension, the `ex_provider_slots_no_overlap` exclusion constraint and the existing constraint test. It also has a health endpoint, its own database, migration, Dockerfile and Compose entry. Phase 2 adds appointments, waitlist and the saga to this service. The goal is never having to move a table between services later. `provider_slots.provider_id` becomes a plain UUID with no foreign key.
- **D-04:** **Identity owns accounts only** (credentials, role, `clinic_id`). Patient and Provider profiles store `user_id` as a plain UUID with no foreign key. When a profile is linked to an account, the owning service validates the ID through an Identity API call. PHI never enters Identity, and credentials never enter Patient or Provider. Profile creation does **not** create the login account; the two stay separate operations.

### Cross-service integrity
- **D-05:** **References are checked with a synchronous REST call to the owning service at write time.** For example, Provider calls Organization's internal department lookup before committing a provider or availability row. If the referenced record is missing or inactive, the request returns **422**. If the owning service is unreachable, the write fails. The same pattern applies to every foreign key that now crosses services:
  - `users.clinic_id` → Organization
  - `patients.clinic_id` → Organization
  - `patients.user_id` → Identity
  - `providers.user_id` → Identity
  - `providers.department_id` → Organization
  - `availability_templates.department_id` → Organization

  In short, validate at write time and never join at read time.
- **D-06:** **Deactivating a referenced record is allowed and does not cascade.** Existing references keep their IDs, and only new creates/updates pointing at an inactive target are rejected (422). This extends the Phase 1 soft-delete semantics. There is no reverse call such as Organization asking Provider whether references exist, and no distributed transaction.
- **D-07:** **Reads return IDs only.** Each service returns its own data plus foreign IDs (`department_id`, `clinic_id`, `user_id`), and clients combine data themselves. No service enriches reads by calling other services, and the gateway does not aggregate responses in the backend-for-frontend (BFF) style. Phase 1 response shapes should be kept wherever they already return IDs.
- **D-08:** **Kafka and the outbox stay in Phase 3.** This phase introduces no event publishing and no outbox tables. The dashboard must record why integrity checks are synchronous now and move to events later.

### Claude's Discretion
These areas were not discussed. Use the recommended defaults below unless research shows a strong reason to deviate, and record each choice in the dashboard:
- **API gateway implementation:**
  - Default is a thin FastAPI gateway (proxying with `httpx`, rate limiting on Redis), because it shows understanding for the graded review. A self-hosted Traefik or Nginx is an acceptable alternative if justified.
  - Every service verifies the JWT itself (defence in depth). The gateway may also reject requests early.
  - Do not recommend Zoho or other SaaS gateways.
- **Repo and data layout:**
  - Default is a monorepo with `services/<name>/`, each service having its own `app.py`, `api/`, `domain/`, `repository/`, migrations directory, Dockerfile and tests.
  - Shared `libs/` becomes an installable internal package limited to infrastructure: token verification/JWKS client, audit writer, OTel/structlog setup, and database/session helpers. It never shares domain models.
  - Default database layout is **separate Postgres databases on one Postgres container** for local dev, one database and one DB role per service, with no service granted access to another service's database. Mongo audit collections are per service or share one audit database per D-02; the planner decides and documents it.
- **Service-to-service authentication:**
  - Default is to forward the caller's JWT on internal calls, so the callee re-applies RBAC and clinic scope.
  - Internal-only endpoints (e.g. `/internal/departments/{id}`) are not routed by the gateway.
  - A service token is acceptable if a call has no user context.
- **Token signing:** move from HS256 to **RS256 with a JWKS endpoint on Identity**, as the roadmap success criteria require. Only Identity holds the private key. How keys are loaded for local dev (a file mounted from Compose secrets or an environment variable) is the planner's choice. The key must never be committed.
- **Internal call behaviour:** use `httpx.AsyncClient` with explicit timeouts and a bounded retry for idempotent GETs only. Trace context must propagate across internal calls (OTel `httpx` instrumentation) so one request shows up as a single connected trace in Jaeger.
- **Migration strategy:** the planner chooses between extracting the code in place and rewriting per service. Phase 1 behaviour tests must be re-pointed at the gateway and keep passing. Alembic history splits per service with a fresh baseline per service database; the planner decides whether to keep the existing `0001`/`0002` revisions.

<code_context>
## Existing Code Insights

### Reusable Assets
- `services/identity/api/*.py` (auth, clinics, departments, patients, providers, availability, admin_ping): these routers move almost as-is into their owning services.
- `services/identity/repository/org_repo.py` → Organization; `people_repo.py` splits into Patient and Provider.
- `services/identity/repository/models.py`: 8 ORM models get distributed by owner. `ProviderSlot` and its `ExcludeConstraint` move to Scheduling.
- `services/identity/security/current_user.py` and `rbac.py`: become the shared token-verification/RBAC dependency in `libs/`, switched to RS256/JWKS verification.
- `libs/auth` (jwt, passwords, denylist): the signing half and passwords stay with Identity. Denylist checks are needed by every verifier; the planner decides whether a Redis check applies to every service or only to Identity and the gateway.
- `libs/audit`, `libs/observability`: reused unchanged as shared infrastructure libraries.
- `smarthealth/db.py` (loop-aware engine and Mongo singletons) and `smarthealth/config.py` (pydantic-settings): become per-service config on top of a shared db helper.
- `infra/migrations/versions/0001_initial_schema.py`, `0002_soft_delete_columns.py`: split per service database.
- `tests/` (test_auth, test_rbac, test_clinics, test_departments, test_patients, test_providers, test_availability, test_audit, test_models, …): the behaviour suite to keep green through the gateway.
- `docs/architecture-dashboard.html`: the dashboard to update with the service map and decision cards.

### Established Patterns
- Fully async: asyncpg plus `AsyncMongoClient`, `httpx` only, no sync I/O in routes.
- Every lookup is scoped to a clinic (enumeration defence). This must hold in every service, including internal endpoints.
- Soft-delete only (`is_active=false` plus `deactivated_at`). Deactivating something already inactive returns 200 as a no-op.
- Audit documents contain field names only, never PHI values, and carry a `trace_id`.
- One commit per request; routers call repositories and never write ORM queries inline.

### Integration Points
- `infra/docker-compose.yml`: add one container per service, a Postgres init script creating a database and role per service, health checks, and the gateway as the only published API port.
- Prometheus scrape config (`infra/prometheus.yml`): one target per service.
- The OTel service name is set per service so Jaeger shows separate services joined into a single trace.

</code_context>

<specifics>
## Specific Ideas

- Motivation to record in the dashboard: the week-1 mentor review asked for a *true* microservice architecture. The dashboard's decision record should present the move as a response to that review, with the tradeoffs (network hops, availability coupling of sync checks, no distributed transactions) stated explicitly.
- Preferring Organization and Provider as separate services over the merged option shows the user values clear bounded contexts, even at the cost of some extra calls between services.

</specifics>

<deferred>
## Deferred Ideas

- Dedicated **Audit service** consuming a Kafka audit topic, replacing direct library writes (Phase 3).
- **Local copies of reference data kept current by events** (e.g. Provider caching departments) to remove the availability coupling of synchronous checks, once Kafka and the outbox exist (Phase 3).
- Cascading deactivation (e.g. a department cascading to its providers) via events or orchestration. Not planned; revisit only if a requirement appears.

</deferred>
