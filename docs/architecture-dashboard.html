01

What SmartHealth Part A is

A production-grade, distributed backend for hospital and clinic operations: patient/provider management, appointment scheduling, visit workflows, billing pre-checks, notifications, and operational analytics. Part A is graded on architecture clarity, tradeoff reasoning, correct use of the mandated stack, reliability, and observability — so the reasoning below is a first-class deliverable, not documentation after the fact.

The one thing that must hold

Booking, updating, and completing an appointment is reliable and consistent under load. A partial failure never corrupts scheduling state, and every operational data model stays accurate, durable, and queryable. Every design decision on this page is justified against that sentence.

System architecture

Phase 1.1 re-delivered the Phase 1 monolith as independently deployable services after the week-1 mentor review. Phase 2 turns Scheduling into a real service and adds Visit and Billing: an API Gateway at the edge, seven FastAPI services each with its own PostgreSQL database and role, and two Temporal worker containers (scheduling-worker, visit-worker) that execute the sagas. Tokens are RS256 and verified locally against Identity's JWKS; workers call other services with short-lived, audience-scoped service tokens. MongoDB (audit_log) and Redis are shared cross-cutting infrastructure. Temporal is live; Kafka + Schema Registry and Celery + RabbitMQ still run only as healthy containers until Phase 3. Each layer is marked wired or scaffolding only.

Clients
Patient / Front-desk / Provider / Admin
Role-scoped API consumers (patient, provider, front-desk, admin). They only ever talk to the gateway.

Edge — wired, Phase 1.1
API Gateway
FastAPI + httpx proxy · the only published application port
Route table: /api/auth, /api/admin, /.well-known/jwks.json → Identity; /api/clinics → Organization; /api/providers → Provider; /api/patients → Patient; /api/slots, /api/appointments, /api/waitlist → Scheduling; /api/visits → Visit; /api/billing → Billing. /internal/* and unsafe paths (dot segments, encoded slashes, NUL) answer 404 — there is no internal route to block. Per-IP fixed-window rate limits in Redis (auth endpoints 20/min, everything else 300/min) that fail open on a Redis outage, visibly (warning log + counter). Upstream failures map to 503/504. It does not verify JWTs and does not aggregate responses.

Cross-service contracts — wired, Phase 1.1
Three contracts hold the services together
1. Token verification: every service verifies the RS256 signature itself from a cached JWKS (kid-selected, 300 s TTL, 30 s backoff on an unknown kid) and checks the shared Redis denylist; no per-request call to Identity. 2. Synchronous reference checks (D-05): at write time the owning service is asked with a GET to its /internal endpoint, forwarding the caller's JWT — Identity→Organization (clinic), Patient→Organization (clinic) and Patient→Identity (user), Provider→Organization (department) and Provider→Identity (user). Missing or inactive → 422; owner unreachable or erroring → 503 with nothing written; no cascade on deactivation. 3. Trace propagation: W3C traceparent on every hop (OpenTelemetry propagator + httpx client spans) so one request is one connected trace.

Logs
structlog JSON
Every log line carries trace_id/span_id; identifiers only, no PHI field values — enforced by a dedicated test, not just convention.
Ownership rule of thumb: anything the saga must reason about for correctness (patients, providers, appointments, slots, billing, the outbox) lives in PostgreSQL — now in the database of the service that owns it; everything append-heavy or schema-flexible (audit, visit records, notification logs, analytics projections) lives in MongoDB.
Modeling assumption — accounts vs. profiles (D-04): login accounts live in Identity (users: email, password hash, role, clinic_id); operational profiles live in Patient and Provider. A profile stores user_id as a plain nullable UUID (no foreign key), validated against Identity at write time. This lets front-desk/admin create a patient with no login (walk-in, phone-booked) while self-registering patient accounts (IAM-01) still work, and it keeps PHI out of Identity and credentials out of Patient and Provider. Creating a profile never creates the account.
Interim mechanisms — Phase 3 replaces them. Phase 2 ships deliberate stand-ins, each labelled: (1) the pending-booking starter and the visit downstream sweeper recover a workflow start lost between a database commit and start_workflow — Phase 3 replaces them with a transactional outbox; (2) notification, follow-up and analytics steps are stubs (a PHI-free log line plus an audit entry) — Phase 3 replaces them with Celery jobs and Kafka events; (3) clients poll status URLs — Phase 3 replaces polling with events; (4) Temporal runs from the auto-setup image — the production topology is temporalio/server with a separate schema job. Also open: workers expose no metrics; Mongo audit is written after the Postgres commit and is not atomic with it (WR-04); the waitlist tries at most 5 entries per freed slot and has no priority.
Phase 2.1 — what is only a target, what is interim, what is open. Targets, not results: NFR-01..08 and a runnable k6 load test exist, but they are not yet measured — the smoke profile crossed its latency thresholds in both runs against the real stack in plan 02.1-13 (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; every accepted booking still confirmed; two uncontrolled runs on a heavily loaded laptop with no Jaeger collector) and sustained and burst have never run, and the local single-instance stack is not claimed to meet NFR-01 or NFR-02 (Phase 3 measures). Interim: audit writes after a committed step are non-fatal (an entry can be lost if Mongo is down at that instant; the transition is durable in appointment_status_history) until the Phase 3 outbox; schedule changes (15 s) and reconcilers (60 s) are polled, not event-driven. Open risks: cancel and reschedule billing is still bounded (*_incomplete:billing_pending, for an operator) — only visit billing retries open-endedly; a slot still held at the schedule-change second pass gets no third pass; reconcilers are oldest-first with a batch cap and no per-row backoff; waitlist entries of a deactivated provider are untouched; delivered change events are never purged; no_show is automated only and pre-2.1 visits settle as not_checked_in with no backfill; refresh tokens are single-use, so clients must store the rotated token; the full load profiles (sustained, burst) have never run, and smoke crossed its latency thresholds on the real stack.
Open deferrals and recorded risks carried from Phase 1.1 (none of these is hidden; all are in deferred-items.md and the Phase 1.1 summaries): (1) the gateway buffers whole request bodies with no size cap — the rate limiter bounds request count, not size; (2) one shared Redis holds both the denylist and rate-limit counters — a Redis outage fails the limiter open and token verification closed (503), and a flush would drop revocations; (3) service tokens carried no aud claim — closed in Phase 2: tokens are now audience-scoped and every internal route names its allowed callers; (4) application containers run as root; (5) real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, a human look at the Jaeger UI, and the bootstrap_admin.py admin-creation branch (only its no-op path is tested) have not been verified; (6) three flagged assumptions await mentor confirmation: the provider→department→clinic scope chain holds only through write-time validation (ORG-03), overlapping availability templates remain allowed (PPL-03), and a client combining services may briefly see stale cross-service state (PPL-04). Nothing here is claimed as production-hardened.

Technology decisions

Each card states what was chosen, what else was on the table, why this won against the core value, and what it costs. The confidence chip reflects how settled the decision is.

high confidence to confirm in build alternatives considered

Why Temporal, not Celery, for the saga

high
Temporal workflows per aggregate owner; Celery keeps single-step jobs (Phase 3)

AlternativesCelery chains/chords · a hand-rolled database state machine with a poller · choreography over Kafka events

Why thisDurable execution: a booking is five steps across three services; if a worker dies mid-saga the workflow resumes on another worker from its recorded history (proven by the worker-crash test on the Compose Temporal). Replay: workflow code is deterministic and replay-tested against recorded histories, and changes go behind workflow.patched. Compensation is ordinary code in the workflow (reverse order, forward transitions) instead of callbacks spread over tasks. Retries and timeouts are per-activity policies, with business outcomes marked non-retryable. Schedules replace cron for the hold reaper, the pending-booking starter and the visit sweeper. Celery would need all of this built by hand on top of at-least-once tasks.

TradeoffOne more runtime with its own determinism discipline (no wall clock, randomness or I/O in workflow code; a sandbox enforces it) and a versioning discipline for in-flight histories. The namespace keeps closed workflows for 24 h only, so the database — not the workflow id — is the long-term idempotency arbiter. Celery still gets the discrete jobs (send a reminder, run a follow-up) in Phase 3; in Phase 2 nothing is delegated to it yet.

PlacementA workflow lives with the service that owns its aggregate (D-05): booking/cancel/reschedule/waitlist in Scheduling on scheduling-tq, visit completion in Visit on visit-tq; Billing has no workflow. One worker container per service, so activities touch only their own database.

Layered idempotency

high
Database arbiters first, workflow id second, idempotent activities throughout

AlternativesRedis idempotency cache only · rely on Temporal workflow-id dedup alone · client-side retry discipline

Why this1. Database arbiters: the partial unique index uq_appointments_active_slot (one active appointment per slot), the idempotency_keys row keyed by (caller, key) with a SHA-256 of the body (a replay returns the original appointment; a different body is 422), conditional updates (UPDATE … WHERE status = expected) for every transition, and history uniques (uq_visit_history_visit_to, uq_billing_history_record_key). 2. Workflow id: deterministic ids (booking-<id>, visit-completed-<id>, …) started with use-existing / reject-duplicate, so a second start is a no-op. 3. Activities: every Billing call carries an Idempotency-Key, and every audit write a dedupe_key, so Temporal’s at-least-once retries are safe.

TradeoffKeys live in Postgres, not Redis, so they survive a cache flush, at the cost of a write per booking. Workflow-id dedup is bounded by the 24 h namespace retention; beyond that only the database rules hold — which is why they come first.

Audit after commit: non-fatal now, outbox later

Phase 2.1 · S3
A failed audit write after a committed step is logged, never fatal

AlternativesFail the request or workflow when the audit write fails · a local outbox table in each service · the Phase 3 transactional outbox to Kafka only

Why thisThe transition is already durable in appointment_status_history in the same transaction as the state change. Failing the request or the workflow after the commit would tell the caller a lie (a 500 for a booking that confirmed) or end a workflow before its second pass. Compensations also read the appointment’s state and do nothing for a committed booking, so a late failure can never undo a confirm. A local outbox would be a second mechanism that Phase 3 replaces anyway.

TradeoffIf Mongo is down at that instant the audit entry can be lost for good (audit.write_failed is logged with ids and exception type); nothing backfills it. The transactional outbox in Phase 3 is the general fix.

Schedule-change delivery: poll an outbox, do not push

Phase 2.1 · M2
Provider writes schedule_change_events atomically; Scheduling polls and acknowledges

AlternativesProvider calls Scheduling directly after the change · Provider starts a Temporal workflow · wait for the Phase 3 Kafka event

Why thisA push is lost if Scheduling or Temporal is down at the moment of the change, and Provider must not call another service’s write path. The row commits with the change, stays pending until acknowledged, and a crash between “start the workflow” and “acknowledge” simply re-delivers (the start is idempotent). No cursor, because rows can commit out of order. Phase 3 can publish the same rows to Kafka.

TradeoffUp to one poll interval (15 s) of delay; delivered rows are never purged; a polling Schedule to run and keep paused during feed tests.

Which slots are stale: set difference

Phase 2.1 · M2
Re-expand the current templates; any future slot not in that set is stale

AlternativesRecord which template produced each slot · invalidate slots by template id and date range · regenerate everything

Why thisIt is idempotent, needs no slot-to-template link, and reuses the tested, DST-safe generator, so the candidate set cannot drift from what generation would produce. Available stale slots are withdrawn; a stale booked slot flags its appointment instead of cancelling it (staff decide); held slots wait for a second pass after the hold TTL. Ambiguity withdraws nothing.

TradeoffA slot that cannot be derived from the templates is stale by definition (the application has no other path to create one); a slot still held at pass 2 gets no third pass.

Reconciler mechanism: one Schedule per service

Phase 2.1 · S4
Temporal Schedule (overlap SKIP) running one idempotent reconciler workflow

AlternativesA cron or sweeper loop inside the API · one more bespoke poller per stuck state · waiting for Phase 3 events

Why thisSame pattern as the hold reaper and the pending starter, visible in the Temporal UI. It re-derives outcomes from the database (a pending booking whose workflow is gone, a waitlist entry stuck matched, billing never voided, a no-show, a visit with an unsettled marker) with conditional updates, asks Temporal before touching a pending row, and re-reads before any Billing call, so a live booking is never failed and a committed one never voided.

TradeoffPolling (60 s); lists are oldest first with a cap (50 / 100) and no per-row backoff, so a persistent failure beyond the cap could starve newer rows; cancel and reschedule billing is not covered.

Single-use refresh tokens

Phase 2.1 · C1
Rotating refresh with an atomic Redis claim and an rjti claim on the access token

AlternativesReusable refresh tokens with a denylist check only · a refresh-token family table in Postgres · shorter-lived refresh tokens

Why thisOne SET NX EX both checks and consumes the refresh jti, so concurrent reuse yields exactly one winner, and it runs after the token and user validate so a bad token burns nothing. The access token names its paired refresh token, so logout revokes both without client cooperation. A used and a revoked token are deliberately indistinguishable (401). Redis down is 503 and the token is not consumed (fail closed, like the access path).

TradeoffClients must store the rotated token; access tokens issued before the change have no rjti and revoke only themselves; a Redis outage blocks refresh. Alongside it: bcrypt on a bounded thread pool, and case-insensitive email through a lower(email) unique index without rewriting existing rows.

Load test and NFRs: k6, one source of numbers

Phase 2.1 · D1, D2
k6 from a pinned Docker image; targets in loadtest/nfr.json

AlternativesLocust or a hand-written asyncio script (adds a dependency) · numbers copied into the PRD, docs and thresholds separately

Why thisNo package is added to the project (only Docker), and a test fails if the PRD table, docs/nfr.md or the k6 thresholds drift from the JSON. The numbers come from a stated demand model (50,000 requests a day, 60 percent in a 2-hour peak, a 5x peak minute rounded up to 25 per second, a 100 per second opening burst).

TradeoffThe targets are not yet measured: the smoke profile crossed its latency thresholds in both runs against the real stack in plan 02.1-13 (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; every accepted booking still confirmed; two uncontrolled runs on a heavily loaded laptop with no Jaeger collector) and sustained and burst have never run. The local single-instance stack is not claimed to meet NFR-01 or NFR-02. Phase 3 observability measures them.

Monolith → microservices

high
Full cut — six independently deployable services, one database each

AlternativesKeep the Phase 1 modular monolith · lean cut with a merged Provider Directory (Organization + Provider in one service) · full cut (chosen)

Why thisThe week-1 mentor review asked for a true microservice architecture, so Phase 1.1 re-delivers the working monolith as gateway + Identity + Organization + Provider + Patient + Scheduling (D-01). The boundaries are clear bounded contexts — the Organization/Provider split was a deliberate preference for finer boundaries over fewer calls. It buys independent deployment and scaling per service, confines PHI to one service and one database (Patient), and a compromised non-Identity service can no longer mint tokens because only Identity holds the signing key. Phase 1 behaviour was carried over and re-tested, with one deliberate change: a provider under a missing department now returns 422 (was 404) per D-05.

TradeoffThe costs are real and accepted: extra network hops on every write that crosses a boundary; availability coupling from synchronous checks — a provider write needs Organization (and Identity) up and otherwise fails closed with 503; no distributed transactions and no cascading deactivation (D-06), so deactivating a clinic leaves existing references in place and only blocks new ones; clients must combine id-only reads themselves (D-07) because no service enriches another's data; and about six more containers to run locally. Eventual-consistency work that would remove the coupling (event-fed local copies) is deferred to Phase 3 (D-08).

ReversibilityCostly — merging or splitting services later means moving tables between service databases and rewriting the internal calls between them.

Verification statusBehaviour is covered by in-process suites across all services plus a real-stack smoke test through the published gateway port. Not yet verified: how the synchronous checks behave when a real container goes down mid-request, a cold start from an empty volume, and a person viewing the connected trace in the Jaeger UI.

API gateway

high
Thin FastAPI + httpx proxy, per-IP Redis rate limits

AlternativesSelf-hosted Traefik or Nginx · managed/SaaS API gateways · no gateway (clients call each service directly)

Why thisA thin FastAPI proxy is the most reviewable choice: the whole routing knowledge is a short Python route table with tests, in the same stack and language as the services, with no extra configuration dialect to defend. The table maps /api/auth, /api/admin and /.well-known/jwks.json to Identity, /api/clinics to Organization, /api/providers to Provider and /api/patients to Patient — and deliberately has no /internal prefix, so internal lookup endpoints are absent from the edge rather than routed-then-blocked. Unsafe paths (dot segments, encoded slashes, NUL) are refused before routing, hop-by-hop headers are stripped, upstream failures map to 503/504, and the gateway never retries (a retried POST could double-apply a write). Limits are per client IP in fixed one-minute windows — a stricter 20/min budget for login/register/refresh, 300/min for everything else — counted by one atomic Lua script, keyed on the socket peer address only (a client-supplied X-Forwarded-For is never trusted). The limiter deliberately fails open when Redis is unreachable, never silently: a warning log and the gateway_ratelimit_fail_open_total counter (RESEARCH A1 — a counter store must not take the whole platform down). The gateway does not verify JWTs (every service verifies for itself, so no service trusts the edge) and does not aggregate responses (D-07).

TradeoffLess capable than Traefik/Nginx: it buffers the whole request body with no size cap yet (open deferral — the limiter bounds request count, not size) and does not stream. Fixed windows allow a burst across a window boundary. While Redis is down the edge has no rate protection (fail-open is a chosen availability-over-protection tradeoff). It is a single local ingress and a single point of failure, and if it were ever placed behind another proxy the peer address it limits on would be that proxy’s. Its /metrics is served only on an internal listener (:9100, not published).

Cross-service integrity

high
Synchronous owner check at write time now; event-fed local copies in Phase 3

AlternativesCross-database foreign keys (not possible across databases) · event-fed local copies of reference data · sagas / distributed transactions

Why thisOnce tables live in different databases a foreign key can no longer express "this clinic exists". Kafka and the outbox do not exist until Phase 3 (D-08), so the simplest correct option today is a synchronous GET to the owning service’s /internal endpoint at write time (D-05), forwarding the caller’s JWT so the callee re-applies RBAC and clinic scope (a 60 s service token is used only where there is no user context). The edges are Identity→Organization (clinic), Patient→Organization (clinic) and Patient→Identity (user), Provider→Organization (department) and Provider→Identity (user). A missing or inactive target is 422; an owner that is unreachable or answers 401/403/5xx is 503 — so an auth misconfiguration is never mistaken for a missing record — and in both cases nothing is written (fail closed). Retries are bounded to three attempts with backoff, GET only, transport errors only. Deactivation never cascades (D-06): existing references keep their ids and only new writes pointing at an inactive target are refused. Reads return ids only (D-07); clients combine them.

TradeoffWrites depend on the owner’s availability: a provider write needs Organization and Identity up. Each cross-boundary write pays extra latency. The check happens once, at write time, so a department deactivated afterwards leaves existing providers pointing at it, and a client combining services may briefly see stale state — both are flagged assumptions awaiting mentor confirmation (ORG-03, PPL-04). Phase 3 removes the availability coupling with event-fed local copies, at the price of an eventual-consistency window. Not yet verified: behaviour against a genuinely failing container (the suites simulate an unreachable owner with a transport that raises ConnectError).

Database per service

high
One Postgres container, one database and one role per service

AlternativesOne container per database · one shared database with a schema per service · keep the single Phase 1 database

Why thisIsolation is enforced by the server, not by convention: each service role can connect only to its own database (PUBLIC connect is revoked), and a live test shows all 20 cross-role connections refused with “permission denied”. Invariant tests also assert that no foreign key crosses a service, no service imports another, PHI columns exist only in Patient and the private key is loaded only by Identity. One container keeps local resource use tractable. An idempotent db-init job creates roles and databases (an init script would silently do nothing on an existing volume); each service has its own migrations directory with a fresh Alembic baseline. The legacy smarthealth database is left untouched and not migrated — dev data is treated as disposable (RESEARCH A2) and dropping it is an operator decision. MongoDB audit_log and Redis stay shared as cross-cutting infrastructure, not service databases (D-02).

TradeoffOne container is one failure domain and one connection budget — max_connections had to be raised to 300 because Temporal plus six application pools exhausted the default 100 — so this is the local shape, not production isolation. There are no cross-database joins by design. The shared Mongo and shared Redis remain coupling points (a recorded risk). The legacy database still contains stray empty objects from an early migration run.

Scheduling skeleton now

high
A health-only Scheduling service that already owns provider_slots

AlternativesCreate the service only in Phase 2 · keep provider_slots in Provider (or Identity)

Why thisprovider_slots, the btree_gist extension and the ex_provider_slots_no_overlap exclusion constraint were recreated in scheduling_db verbatim from Phase 1 minus the foreign key, so Phase 2 never has to move a table between services (D-03). The constraint is proven live there: overlapping non-cancelled slots for one provider are rejected by Postgres, while a cancelled overlap, another provider and back-to-back slots are accepted; creating availability templates materializes no slots. provider_id is a plain UUID that Phase 2 will validate against Provider’s /internal/providers/{id} (D-05).

TradeoffA service with no public routes cost a container, an image, a migration and a Compose entry for a phase. It paid off in Phase 2: slots, appointments and the saga were added without moving a table, and the service-token aud claim was added (plan 02-01) before Scheduling started calling Provider. Slot generation tolerates overlapping templates with ON CONFLICT (provider_id, start_time) DO NOTHING.

Workflow orchestration

high
Temporal

AlternativesCelery chains only · hand-rolled DB state machine · AWS Step Functions

Why thisBooking is a multi-step transaction (validate → reserve hold → billing pre-check → confirm → notification intent). Temporal makes it durable and resumable, and models failure recovery as first-class compensation — directly satisfying "partial failures never corrupt scheduling state." See Why Temporal, not Celery above for the Phase 2 rationale as built.

TradeoffAnother infra component + a determinism discipline (no wall-clock/random in workflow code). Worth it for the graded reliability core.

Auth & session model

high
RS256 access + refresh JWT, JWKS verification in every service, Redis jti-denylist

AlternativesA shared symmetric secret distributed to every service · per-request token introspection at Identity · opaque tokens · access-only JWT with no refresh or revocation list

Why thisIdentity alone holds the RSA private key and signs tokens with kid smarthealth-identity-1; the public key is published at /.well-known/jwks.json. Every service verifies signatures locally against a cached JWKS (300 s TTL, 30 s backoff after an unknown kid), so there is no per-request call to Identity and a compromised non-Identity service cannot forge tokens — which a shared symmetric secret would allow for any holder. The access token (~15 min: sub/role/clinic_id/jti/rjti/type=access) is validated on every protected request; the refresh token (~7 days: sub/jti/type=refresh only) re-derives role and clinic from the current account row, so a role change takes effect on next refresh, and is single-use (see Single-use refresh tokens). Logout writes the jti to a Redis denylist (revoked:{jti}, TTL = remaining token life) that every service checks, failing closed with 503 if Redis is unreachable. Calls with no user context use 60 s service tokens minted only by Identity. The private key is generated by scripts/generate_jwt_keypair.py, gitignored, and delivered only to the Identity container as a Compose secret; Identity refuses to start without it.

TradeoffKey-file management: the key must be generated before the first docker compose up and never committed. Rotation is mechanically supported by kid but has not been exercised. A service may use a stale JWKS for up to the cache TTL. One Redis round-trip per authenticated request in every service. Service tokens carried no aud claim in Phase 1.1; Phase 2 (plan 02-01) made them audience-scoped, with a per-service client secret delivered as a Compose secret and an explicit allowed-caller set on every internal route.

Availability & slot model

high

AlternativesGenerate concrete bookable slot rows in Phase 1 (e.g. next 90 days materialized) · free-text working hours (unstructured) · concrete slots only, no template

Why thisPPL-03 ("configure availability windows") is a configuration requirement, not a booking-generation requirement — a weekly availability_templates row (day_of_week/start_time/end_time/slot_duration/effective dates) satisfies it without deciding a materialization horizon that has no consumer until Phase 2's booking saga exists. provider_slots is created now (since Phase 1.1 in the Scheduling service’s own scheduling_db) but left empty — its EXCLUDE USING gist (provider_id WITH =, tstzrange(start_time,end_time) WITH &&) WHERE (status <> 'cancelled') constraint (btree_gist extension) is live and proven by an integration test today, so Phase 2's double-booking guarantee is inherited as a tested invariant, not a Phase-2 to-do under saga-implementation pressure.

TradeoffPhase 1 shipped no bookable slots (by design). Phase 2 materializes slots on demand over a rolling 28-day horizon from the templates, in the clinic’s IANA timezone, and adds the appointment-level arbiter uq_appointments_active_slot on top of the slot exclusion constraint.

04

The three responsibility split & consistency patterns

The most-asked evaluation question is "why do you have Temporal and Kafka and Celery?" They solve different problems, and three patterns keep the system consistent under failure.

Who does what

TemporalMulti-step orchestration with compensation — the booking / cancel / reschedule / waitlist / visit-completion workflows (live since Phase 2). Knows the whole transaction.

KafkaDurable facts that already happened — broadcast to independent consumers (analytics, audit, notifications). Replayable.

CeleryDiscrete single-step jobs, usually triggered by a Temporal activity or a Kafka consumer — send an email, compute a projection.

Three patterns that keep state honest

Transactional outbox (Phase 3)Business row + event row commit in one Postgres transaction; a relay publishes to Kafka after. No dual-write gap. Until then the commit-then-start gap is covered by the pending-booking starter and the visit sweeper.

Layered idempotencyPostgres arbiters first (partial unique index, idempotency-key row, conditional updates), Temporal workflow-id dedup second, idempotent activities throughout. At-least-once delivery becomes effectively-once.

Saga compensationOn failure, run forward transactions (release slot, reverse billing, notify) — never a hard delete or silent rollback. Audit history stays intact.

05

Core flows

As built in Phase 2. Every multi-step change is a Temporal workflow in the service that owns the aggregate (scheduling-tq for appointments and the waitlist, visit-tq for visits), executed by its own worker container. Each step is an idempotent activity that writes one audit entry; failures compensate with forward state transitions and nothing is ever deleted. Clients poll a status URL. Phase 2.1 adds three flows below the visit lifecycle: the check-in window, the provider schedule change and the reconcilers.

Appointment booking saga

POST /api/appointments (with Idempotency-Key) writes the appointment as pending in the same transaction as the idempotency row, starts booking-<appointment id> and answers 202. The appointment is confirmed at step 4; the notification intent (step 5) follows only after confirm.

  1. Validate
    Patient, provider and clinic exist, are active and belong together — checked through their owners’ /internal routes with Scheduling’s aud-scoped service token. A missing reference is a business failure (ReferenceInvalid), an unreachable owner is retried.
  2. Reserve hold
    Slot available → held with held_until (10 min) and the appointment id, by a conditional update. Conflicts were already closed when the request was accepted: uq_appointments_active_slot lets exactly one active appointment exist per slot.
  3. Billing pre-check
    Billing creates the record pending and resolves it verified or failed with a deterministic rule (a coverage_ref starting DENY- is denied). Idempotency-Key on every call, so a retry never double-applies.
  4. Confirm
    One transaction: slot held → booked, appointment pending → confirmed, a history row and an audit entry. A lost hold (reaper got there first) is ConfirmLostHold and compensates.
  5. Notification intent (best-effort)
    Requested only after confirm succeeds. A stub activity writes a PHI-free log line and a notification.requested audit entry. It retries, but its failure never fails or compensates the booking. Phase 3 replaces its body with outbox + Celery.
  6. Compensate, in reverse order (on any failure)
    Void billing (failed/verified → voided) → release the hold (held → available) → mark the appointment failed with the error type as a machine-readable reason. Forward transitions only, one audit entry per step (dedupe_key = <workflow id>:<step>), so a failed booking is fully reconstructable from audit plus the Temporal history. A top-level booking that had taken the hold and did not lose the race then starts a waitlist advance, so the freed slot is offered again.
Deviation from SCHED-02, on purpose (D-09 as built, S7): the implemented order is validate, hold, billing pre-check before notification, then confirm, then a best-effort notification intent; SCHED-02 lists “schedule notifications → billing pre-check”. The notification intent is requested after confirm, so a booking that fails at confirm sends no notification and a patient is never told about a booking that is then compensated. The order change and the waitlist re-offer after a failed direct booking are workflow.patched and replay-tested. SCHED-02’s “prevent conflicts” step is not a separate activity: it is the reserve step’s database constraints (uq_appointments_active_slot, ex_appointments_patient_no_overlap).
Evidence: the concurrency suites fire parallel bookings at one slot against real Postgres and assert exactly one active appointment; scripts/demo_concurrent_booking.py shows it live through the gateway (50 parallel requests → 1 × 202, 49 × 409, one confirmed appointment). A deliberately denied booking ends failed with the slot re-offered and billing voided, in-process and on the deployed Compose stack.

Cancel

CancelWorkflow · cancel-<id>-<version> · 202 from the API.

  1. Cancel + release slot
    One transaction: appointment confirmed → cancelled, its current slot back to available.
  2. Billing refund state
    More than 24 h ahead: refund_pending → refunded; inside the cutoff: no_refund. Staff may waive the cutoff (patients may not). Decided in the API request, never in the workflow.
  3. Notification intent
    Separate best-effort activity.
  4. Advance the waitlist
    Starts waitlist-advance-<cancel workflow id> as an abandoned child for the freed slot.

Reschedule

RescheduleWorkflow · reserve-then-swap, never cancel-then-rebook.

  1. Hold the new slot
    Same provider only; a taken slot fails here and nothing changes.
  2. Swap in one transaction
    Release the old slot, book the new one, repoint the appointment. A rejected swap releases the new hold.
  3. Re-link billing
    The verified record follows the appointment (history row rescheduled).
  4. Notify, then advance the waitlist
    The old slot is offered to the waitlist.

Waitlist advance

WaitlistAdvanceWorkflow · FIFO per provider, optional time window.

  1. Claim
    The oldest matching waiting entry, claimed with FOR UPDATE SKIP LOCKED so two advances never take the same entry.
  2. Book as a child saga
    A normal BookingWorkflow for that patient on the freed slot — the same constraints and compensation apply.
  3. Resolve
    Confirmed → entry booked. Booking failed → entry failed, try the next (at most 5). Slot lost to a faster booker → entry back to waiting.

Visit lifecycle

Visit service · commit first, downstream after.

  1. Check in
    Front-desk/admin, only for a confirmed appointment inside the check-in window: Visit asks Scheduling to move it to checked_in first, then inserts the visit. One visit per appointment; a repeat returns the existing visit.
  2. Start
    The visit’s own provider (or staff); conditional update, repeats are no-ops, skipping a state is 409.
  3. Complete, then fan out
    The transition commits with downstream_started_at NULL; then visit-completed-<id> starts and the marker is set. Billing finalize (open-ended retry), completing the appointment, the follow-up intent and the analytics intent run as independent branches on visit-worker. A lost start is picked up by the sweeper Schedule (every 60 s) and an unsettled step by the visit reconciler. The 200 never waits on any of it.

Check-in window and appointment states (Phase 2.1)

Mentor item M1 · Scheduling decides, Visit asks.

  1. Window by the database clock
    Check-in opens 60 minutes before the slot starts and closes when it ends (both configurable). The decision is made in the same locking SELECT that reads the row, with the database’s now(), so there is no clock skew between services.
  2. Scheduling first, visit second
    Visit calls Scheduling’s internal check-in (confirmed → checked_in, one history row), then inserts the visit. Refusals reach the client as three 409 strings: appointment not confirmed, check-in window not open, check-in window closed. A crash between the two converges on the next request (Scheduling answers 200 “already”).
  3. Refuse what it would corrupt
    Cancel and reschedule are 409 from checked_in onward, so a patient who is in the building can no longer be refunded or rebooked. checked_in, completed and no_show still hold their slot: the unique index and the patient-overlap exclusion cover them (scheduling_0004).
  4. Complete, or no-show
    Visit completion completes the appointment (a fourth workflow branch). A confirmed appointment whose slot ended more than 30 minutes ago becomes no_show through the reconciler sweep; there is no manual staff action.

Provider schedule change (Phase 2.1)

Mentor item M2 · Provider writes the fact, Scheduling pulls it.

  1. Outbox row with the change
    Editing or deactivating a template, or deactivating a provider, writes a schedule_change_events row in the same transaction (ids and a change type only; a change that alters nothing writes none).
  2. Poll, start, acknowledge
    A Schedule (every 15 s) reads the pending events over Provider’s internal feed with Scheduling’s service token, starts schedule-change-<event id> for each, and only then acknowledges, so a crash re-delivers.
  3. Apply: set difference
    The provider’s current templates are re-expanded; every future slot not in that set is stale. Available stale slots are withdrawn; stale booked slots flag their appointment (it stays confirmed, staff cancel or reschedule); missing future slots are inserted for an active provider.
  4. Second pass after the hold TTL
    A durable timer (hold TTL plus one minute), then the same apply again, so a booking that confirmed just after pass 1 is flagged rather than missed. A slot still held at pass 2 gets no third pass (open risk). Staff worklist: GET /api/appointments?flagged=true&status=confirmed.

Reconcilers (Phase 2.1)

Mentor item S4 · one Temporal Schedule per service, overlap SKIP, idempotent, batch-capped, oldest first. They re-derive outcomes from the database and never guess.

  1. Stuck pending bookings (Scheduling, every 60 s)
    A pending appointment older than 10 minutes blocks its slot forever. If Temporal says booking-<id> is gone, the appointment is re-read, billing voided, the hold released and the appointment failed with workflow_lost, then the slot is offered to the waitlist. If Temporal cannot answer, nothing is touched.
  2. Billing lookback, stuck waitlist entries, no-shows
    Bookings failed by the reaper or the reconciler in the last 24 hours get their billing voided if it was not; a waitlist entry stuck matched for 15 minutes is resolved from its appointment; a confirmed appointment past slot end plus grace gets Billing no_refund and then no_show.
  3. Visit reconciler (every 60 s)
    A completed visit whose billing or appointment settlement marker is still empty after 10 minutes is settled by the same step bodies and idempotency keys as the workflow, so the two can race without a double effect. Billing finalize now retries without a time limit instead of skipping.
Still open: cancel and reschedule billing steps that exhaust their bounded budget are recorded as *_incomplete:billing_pending for an operator; only a failed booking’s billing, the no-show refund state and visit billing are reconciled.

06

Anticipated evaluation questions

Prepared, defensible answers to the questions a mentor is most likely to ask, mapped to the graded criteria: architecture clarity, reliability & failure handling, correct tool use, observability.

Why Temporal instead of just Celery for booking?

Celery runs discrete jobs; it doesn't own a multi-step transaction or model compensation. Booking is a saga — validate, reserve a hold, billing pre-check, confirm, notification intent — where a failure at the billing step must undo the hold cleanly and in order. Temporal gives durable execution (the workflow survives a worker crash and resumes), deterministic replay, per-activity retry policies and first-class compensation, plus Schedules for the reaper and sweepers.

In Phase 2 nothing is delegated to Celery yet: the notification step is a stub activity, and that activity is the seam where Phase 3 hands single-step work (send a reminder) to Celery. They're complementary, not competing.

Why do you run both Kafka and RabbitMQ?

Kafka is a durable, replayable log of facts — many independent consumers (analytics, audit, notification triggers) read the same AppointmentBooked event, and a new consumer can replay history. RabbitMQ + Celery is a work queue for discrete jobs with per-task retry and a dead-letter path.

Using Kafka as a task queue loses per-message retry/ack semantics; using RabbitMQ as an event log loses replay and multi-consumer fan-out. Each tool does the job it's good at.

How do you prevent double-booking under concurrency?

In the database. A partial unique index, uq_appointments_active_slot (UNIQUE (slot_id) WHERE status IN ('pending','confirmed')), means two active appointments for one slot simply cannot both commit; the loser gets a 409 before any workflow starts. Underneath, ex_provider_slots_no_overlap keeps a provider’s slots from overlapping and ex_appointments_patient_no_overlap keeps a patient from being double-booked across providers.

This is deliberately not "check-then-insert in application code," which races. Proof: concurrency tests fire parallel bookings at one slot through raw SQL and through the HTTP API and assert exactly one active appointment, and scripts/demo_concurrent_booking.py shows it live on the deployed stack (50 parallel requests → one 202, 49 × 409, one confirmed appointment).

How is an event never lost after a database commit?

The transactional outbox pattern. The business row and an outbox row are written in the same Postgres transaction, so they commit or fail together — no dual-write gap where the DB commits but the Kafka publish is lost. A separate relay reads the outbox and publishes to Kafka; if it crashes mid-publish, it retries from the outbox, and consumers are idempotent so a re-publish is harmless.

How do you handle duplicate / at-least-once delivery?

Layered idempotency, database first. A retried POST /api/appointments with the same Idempotency-Key finds the (caller, key) row in Postgres and returns the original appointment; the same key with a different body is a 422. Workflows have deterministic ids, so a second start attaches to or is rejected by the existing run. Activities are idempotent by construction: conditional state updates, an Idempotency-Key on every Billing call (a repeat is a no-op), and an audit dedupe_key per workflow step. Visit transitions are conditional updates with a unique history row per state, so ten concurrent “complete” calls produce one transition.

Why PostgreSQL and MongoDB, rather than one database?

Split by consistency need. Data the saga must reason about for correctness — patients, providers, appointments, slots, billing, the outbox — needs transactions and constraints, so it lives in Postgres. Append-heavy, schema-flexible data — audit trail, visit records, notification logs, analytics projections — fits a document model, so it lives in MongoDB. Forcing either into the other's model is where teams get burned.

How does a partial failure not corrupt scheduling state?

Saga compensation as forward transitions. If billing denies the booking after the slot is held, the workflow runs the compensations in reverse order — void the billing record, release the hold, mark the appointment failed with a machine-readable reason — with one audit entry per step and nothing deleted. A hold whose workflow died is released by the reaper Schedule. The appointment is never left half-confirmed; this was proven in-process and on the deployed stack (forced DENY- coverage reference → failed, slot available again, billing pending → failed → voided).

How do you trace a request across async boundaries?

OpenTelemetry context is propagated explicitly across every hop — HTTP headers into the API, Temporal interceptors into workflow/activity spans, Kafka message headers, and Celery task headers. The goal (a Phase 3 success criterion) is that one booking request shows up in Jaeger as a single connected trace across HTTP → Temporal → Kafka → Celery, not disconnected fragments. Auto-instrumentation alone only covers HTTP/DB, so the async hops are verified with a deliberate end-to-end trace test.

Why are reference checks synchronous instead of event-driven?

Because the event infrastructure does not exist yet. Kafka and the transactional outbox are Phase 3 scope (D-08), and the simplest correct thing today is to ask the owning service at write time: GET /internal/…, caller’s JWT forwarded, three bounded attempts on transport errors, then 422 if the target is missing or inactive and 503 if the owner cannot answer — nothing is written either way.

The cost is stated plainly: writes depend on the owner’s availability. Phase 3 replaces the check with event-fed local copies, which removes that coupling and introduces an eventual-consistency window instead. Deactivation never cascades (D-06) and reads return ids only (D-07).

What happens when Organization is down during a provider write?

The Provider service cannot confirm the department, so the request fails closed with 503 after its bounded retries; no provider row is written and the failed attempt is audited. The trace for that request shows the failed Provider→Organization hop, and the gateway’s own timeout mapping would return 504 if the whole call stalled.

Honest status: this is covered by in-process tests with a simulated unreachable owner. It has not been exercised against a real container going down mid-request.

How does a service verify a token without calling Identity?

Tokens are RS256. Each service fetches Identity’s public keys from /.well-known/jwks.json, caches them (300 s TTL), picks the key by the token’s kid, and verifies the signature and claims locally. An unknown kid triggers one refresh with a 30 s backoff so a flood of bad tokens cannot hammer Identity. Revocation is the one shared lookup: every service checks the Redis denylist for the token’s jti.

Only Identity holds the private key, so no other service can mint a token. Key rotation is supported through kid but has not been exercised yet.

What happens if a worker dies mid-booking?

Nothing is lost. The workflow’s progress is in Temporal’s history, not in the worker. When an activity’s worker dies, the server times the attempt out and retries it on another worker; because every activity is idempotent, a step that had already half-run is safe to repeat. A test does exactly this against the Compose Temporal: worker A hangs inside the billing step and stops polling, worker B picks up the retry after the 10 s timeout, and the booking ends confirmed with one scheduled billing activity on attempt 2.

Two Schedules cover the gaps around a crash: the hold reaper releases holds that outlived their workflow, and the pending-booking starter starts workflows for appointments committed as pending whose start call never happened. In Compose the worker containers restart automatically and report health through a heartbeat file.

What stops a patient who has checked in from cancelling and being refunded?

The appointment state machine (Phase 2.1, M1). An appointment now moves pending → confirmed → checked_in → completed, with no_show, cancelled and failed on the side. Visit moves it to checked_in through Scheduling’s internal check-in route, only inside a window around the slot judged by the database clock, and cancel and reschedule are 409 from checked_in onward at the API, the repository and the workflow activities. The three new states still hold their slot, because the unique index and the patient-overlap exclusion were widened to cover them, so the guarantee is in the database, not only in code.

A no_show is set only by the reconciler sweep, after the slot ended plus a 30-minute grace; there is no manual staff action yet, and visits created before Phase 2.1 have no checked-in appointment (they settle as not_checked_in, with no backfill).

What happens to slots and bookings when a provider changes their schedule?

The change writes an outbox row in Provider in the same transaction; Scheduling polls it (every 15 s), starts one ScheduleChangeWorkflow per event and acknowledges after the start. The workflow re-expands the provider’s current templates and treats every future slot not in that set as stale: available ones are withdrawn, booked ones flag their appointment (it stays confirmed, staff cancel or reschedule it, and cancelling withdraws the stale slot instead of freeing it), and slots held by an in-flight booking are re-checked in a second pass after the hold TTL.

Honest gaps: it is polled, not event-driven; a slot still held at the second pass gets no third pass; delivered events are never purged; waitlist entries of a deactivated provider are untouched.

What if something fails after the database commit?

Compensations read the appointment’s current state and do nothing for a committed booking, so a late failure can never void billing or release a slot of a confirmed appointment. The audit write after a committed confirm, cancel, swap, check-in, complete or schedule-change apply is non-fatal: it is logged as audit.write_failed and the outcome stands, because the transition is already durable in appointment_status_history.

The cost is stated plainly: if Mongo is down at that instant the audit entry can be lost and nothing backfills it. The general fix is Phase 3’s transactional outbox; a local outbox now would be a second mechanism that Phase 3 replaces.

How are stuck states recovered?

Two reconciler Schedules. Scheduling’s fails pending bookings whose workflow is gone (they would block the slot forever), voids orphaned billing, resolves waitlist entries stuck matched, and sweeps no-shows. Visit’s settles completed visits whose billing or appointment marker is still empty, and visit billing finalize now retries without a time limit instead of skipping. Both use conditional updates, ask Temporal before touching a pending row (an unreachable Temporal skips the step), reuse the workflows’ own idempotency keys, and are capped per run, oldest first.

Not covered: cancel and reschedule billing steps that exhaust their bounded budget are still recorded for an operator (*_incomplete:billing_pending), and there is no per-row backoff, so a persistent failure beyond the batch cap could starve newer rows.

Does it meet its load and availability targets?

Unknown, and the dashboard does not claim otherwise. Phase 2.1 defined NFR-01..08 from a stated demand model (50,000 booking requests a day, 25 per second sustained for 10 minutes, a 100 per second burst, p95 accept latency 300 ms, 99.9 percent availability) in one file that the PRD, docs/nfr.md and the k6 thresholds all derive from, and added a runnable k6 load test with a seed script. The targets are not yet measured: the smoke profile crossed its latency thresholds in both runs against the real stack in plan 02.1-13 (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; every accepted booking still confirmed; two uncontrolled runs on a heavily loaded laptop with no Jaeger collector) and sustained and burst have never run. The local single-instance stack is not claimed to meet NFR-01 or NFR-02. Phase 3 observability measures them and sizes replicas; what is verified today is the correctness under contention (the concurrency suites and the 50-way live demo).

What changed for clients in authentication?

Refresh tokens are single-use and rotated: /refresh returns a new pair and reusing the old refresh token is 401, so a client must store the new one (a Redis outage is 503 and the token is not consumed). Access tokens carry an rjti claim naming their refresh token, so logout revokes both. bcrypt runs on a bounded thread pool so a login burst cannot stall the event loop, and email is case-insensitive through a lower(email) unique index (existing rows are not rewritten). Lists of patients, providers and clinics are paginated (limit 1..200, X-Total-Count), and GET /api/patients/me plus provider reads of their own appointments exist.

What is not yet verified after Phase 2.1?

Phase 2: the interim mechanisms are labelled, not hidden (starter and sweeper until the Phase 3 outbox; notification/follow-up/analytics stubs; polling; auto-setup Temporal). Phase 2.1 delivered quantified NFR targets (NFR-01..08, docs/nfr.md) and a runnable k6 load test, but the targets are not yet measured: the smoke profile crossed its latency thresholds in both runs against the real stack in plan 02.1-13 (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; every accepted booking still confirmed; two uncontrolled runs on a heavily loaded laptop with no Jaeger collector) and sustained and burst have never run; the local single-instance stack is not claimed to meet NFR-01 or NFR-02, and the concurrency suites and the live demo remain the only load evidence until Phase 3 observability measures them. The 02-06 workflow trace is connected through the Temporal tracing interceptor in tests, but a person has not yet followed a booking end to end in the Jaeger UI. Workers expose no metrics, and Mongo audit writes are not atomic with the Postgres commit (WR-04). This is a local/dev system with synthetic data only: logout, PHI log-safety and database isolation are implemented and tested but not fully hardened.

Carried from Phase 1.1: no request-body size cap at the gateway; one shared Redis for the denylist and rate limits; containers running as root. Not yet verified: real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, a person viewing the connected trace in the Jaeger UI, and the bootstrap_admin.py admin-creation branch (only its no-op path is tested). Three assumptions await mentor confirmation: the provider→department→clinic scope chain relies on write-time validation (ORG-03), overlapping availability templates are still allowed (PPL-03), and clients combining services may briefly see stale state (PPL-04).

Is the local Docker Compose setup production-shaped?

Honestly: the local stack uses Temporal's auto-setup image and single-node Kafka and a single Postgres container (hosting all seven service databases) for developer convenience — that's labeled as dev-only, not a production deployment. Production-shaping (separate Temporal schema management, replicated brokers, a Postgres instance per service, non-root application containers, resource limits) is called out as a decision to document rather than something silently claimed. Being explicit about this is part of the reliability story, not a gap.
