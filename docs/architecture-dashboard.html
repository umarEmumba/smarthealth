01

What SmartHealth Part A is

A production-grade, distributed backend for hospital and clinic operations: patient/provider management, appointment scheduling, visit workflows, billing pre-checks, notifications, and operational analytics. Part A is graded on architecture clarity, tradeoff reasoning, correct use of the mandated stack, reliability, and observability — so the reasoning below is a first-class deliverable, not documentation after the fact.

The one thing that must hold

Booking, updating, and completing an appointment is reliable and consistent under load. A partial failure never corrupts scheduling state, and every operational data model stays accurate, durable, and queryable. Every design decision on this page is justified against that sentence.

System architecture

Phase 1.1 re-delivered the Phase 1 monolith as independently deployable services after the week-1 mentor review. Phase 2 turns Scheduling into a real service and adds Visit and Billing: an API Gateway at the edge, seven FastAPI services each with its own PostgreSQL database and role, and two Temporal worker containers (scheduling-worker, visit-worker) that execute the sagas. Tokens are RS256 and verified locally against Identity's JWKS; workers call other services with short-lived, audience-scoped service tokens. MongoDB (audit_log) and Redis are shared cross-cutting infrastructure. Temporal is live. Phase 3 wires Kafka + Schema Registry (with Debezium on Kafka Connect), Celery + RabbitMQ, an analytics service and per-process metrics: the outbox is relayed to Kafka by change data capture, three idempotent consumers drive notifications, visit follow-up and the projections, and every process is scraped by Prometheus. Each layer is marked wired with the phase that wired it.

Ownership rule of thumb: anything the saga must reason about for correctness (patients, providers, appointments, slots, billing, the outbox) lives in PostgreSQL — now in the database of the service that owns it; everything append-heavy or schema-flexible (the audit log and the notification delivery log) lives in MongoDB; the analytics projections are derived data in their own PostgreSQL database, analytics_db.
Modeling assumption — accounts vs. profiles (D-04): login accounts live in Identity (users: email, password hash, role, clinic_id); operational profiles live in Patient and Provider. A profile stores user_id as a plain nullable UUID (no foreign key), validated against Identity at write time. This lets front-desk/admin create a patient with no login (walk-in, phone-booked) while self-registering patient accounts (IAM-01) still work, and it keeps PHI out of Identity and credentials out of Patient and Provider. Creating a profile never creates the account.
Interim mechanisms after Phase 3. Phase 3 retired one Phase 2 stand-in and deliberately kept the rest, each for a stated reason: (1) the visit downstream sweeper is retired: visit.completed is committed with the transition and is the only downstream trigger (the visit worker deletes the Schedule at every start; the workflow class stays as a no-op tombstone so recorded histories still replay); (2) the pending-booking starter stays: it recovers a workflow start lost after the accept commit, and the accept path writes no outbox row (it must not gain work), so no event exists for a pending appointment; (3) the hold reaper stays: an expired hold is the absence of an event; (4) the Scheduling and Visit reconcilers stay: none of their triggers is an event (the no-show sweep itself emits appointment.no_show); (5) the Phase 2 notification, follow-up and analytics activities are still stubs that only log and audit (intent records); delivery is event-driven only, so nothing is sent twice; (6) clients still poll status URLs, because the 202 contract did not change; (7) the schedule-change poller stays paused on the live Temporal server by the user’s decision, and provider.schedule_changed is published but not consumed; (8) Temporal runs from the auto-setup image — the production topology is temporalio/server with a separate schema job. Also open: Mongo audit is written after the Postgres commit and is not atomic with it (WR-04; moving audit into the outbox was deferred and the user accepted that); the waitlist tries at most 5 entries per freed slot and has no priority.
Phase 2.1 — what is only a target, what is interim, what is open. Targets, not results: NFR-01..08 and a runnable k6 load test exist, but they are not yet measured. In plan 02.1-13 the smoke profile crossed its latency thresholds in both runs against the real stack (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; every accepted booking still confirmed; two uncontrolled runs on a heavily loaded laptop with no Jaeger collector); on the Phase 3 stack smoke passed every threshold (see the Phase 3 callout below), but sustained and burst have never run, and the local single-instance stack is not claimed to meet NFR-01 or NFR-02. Interim: audit writes after a committed step are non-fatal (an entry can be lost if Mongo is down at that instant; the transition is durable in appointment_status_history); moving audit into the Phase 3 outbox was deferred (the user accepted that); schedule changes (15 s) and reconcilers (60 s) are polled, not event-driven. Open risks: cancel and reschedule billing is still bounded (*_incomplete:billing_pending, for an operator) — only visit billing retries open-endedly; a slot still held at the schedule-change second pass gets no third pass; reconcilers are oldest-first with a batch cap and no per-row backoff; waitlist entries of a deactivated provider are untouched; delivered change events are never purged; no_show is automated only and pre-2.1 visits settle as not_checked_in with no backfill; refresh tokens are single-use, so clients must store the rotated token; the full load profiles (sustained, burst, contention) have never run.
Phase 3 — what was measured, what is only a target, what is open. Delivery: no loss, at-least-once on the wire, effect-level exactly-once. Duplicates on a topic are possible after a hard kill of Connect (measured: 5 duplicates of 11 messages in plan 03-05; 2 copies of one event id in plan 03-17) and every consumer absorbs them. Load: NFR-01..08 remain targets that are not yet measured. Only the k6 smoke profile ran: three runs on 10 and 11 November 2026 (a baseline before the producers, one after them, one on the finished stack) passed every threshold, with booking accept p95 of 21.8, 29.3 and 49.1 ms and saga completion p95 of about 0.52 s each time; the host load differed and accept latency crept up across the three runs, so it is the number to watch (the cause was not isolated). sustained, burst and contention were not run: the user deferred them until after Phase 3. Real provider: one send per dedupe key holds at the delivery log and at the fake provider’s idempotency store; a real SMS or email provider must accept an idempotency key for the same guarantee, otherwise a crash between the provider call and mark_sent can duplicate a send. Scope: “every state change” covers the ten D-07 event types only (billing transitions, waitlist changes, a visit moving to in-progress, and reconciler and hold-reaper actions are not evented); analytics start at cutover (D-13), so total_patients counts only patients registered after go-live and a rebuild replays everything still retained, including throw-away test events. Open: provider.schedule_changed is published but not consumed and the poller stays paused; the reminder’s later firing inside the same trace was not exercised (the trace is long-lived and can show a wide gap); nobody has looked at the dashboards in a browser or at the connected trace in the Jaeger UI; Schema Registry is a cached write-path dependency (a cold start during a registry outage cannot become ready); replication slots retain WAL while Connect is down (capped at 2 GB; the path after the cap is exceeded was not exercised); the outbox, Kafka topics, processed_events and the delivery log have no retention; Kafka, Schema Registry and the Connect REST API have no authentication on the dev network; auto-setup Temporal is non-production; application and Celery containers run as root (the Semgrep missing-user findings are accepted for now by the user); event-fed local copies were not built, so the synchronous reference checks still make a write depend on the owning service being up; the audit-via-outbox follow-up is deferred.
Open deferrals and recorded risks carried from Phase 1.1 (none of these is hidden; all are in deferred-items.md and the Phase 1.1 summaries): (1) the gateway buffers whole request bodies with no size cap — the rate limiter bounds request count, not size; (2) one shared Redis holds both the denylist and rate-limit counters — a Redis outage fails the limiter open and token verification closed (503), and a flush would drop revocations; (3) service tokens carried no aud claim — closed in Phase 2: tokens are now audience-scoped and every internal route names its allowed callers; (4) application containers run as root; (5) real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, a human look at the Jaeger UI, and the bootstrap_admin.py admin-creation branch (only its no-op path is tested) have not been verified; (6) three flagged assumptions await mentor confirmation: the provider→department→clinic scope chain holds only through write-time validation (ORG-03), overlapping availability templates remain allowed (PPL-03), and a client combining services may briefly see stale cross-service state (PPL-04). Nothing here is claimed as production-hardened.

Technology decisions

Each card states what was chosen, what else was on the table, why this won against the core value, and what it costs. The confidence chip reflects how settled the decision is.

high confidence to confirm in build alternatives considered

Why Temporal, not Celery, for the saga

high
Temporal workflows per aggregate owner and for reminders; Celery delivers the single-step jobs

AlternativesCelery chains/chords · a hand-rolled database state machine with a poller · choreography over Kafka events

Why thisDurable execution: a booking is five steps across three services; if a worker dies mid-saga the workflow resumes on another worker from its recorded history (proven by the worker-crash test on the Compose Temporal). Replay: workflow code is deterministic and replay-tested against recorded histories, and changes go behind workflow.patched. Compensation is ordinary code in the workflow (reverse order, forward transitions) instead of callbacks spread over tasks. Retries and timeouts are per-activity policies, with business outcomes marked non-retryable. Schedules replace cron for the hold reaper, the pending-booking starter and the reconcilers (the visit sweeper Schedule was retired in Phase 3). Celery would need all of this built by hand on top of at-least-once tasks.

TradeoffOne more runtime with its own determinism discipline (no wall clock, randomness or I/O in workflow code; a sandbox enforces it) and a versioning discipline for in-flight histories. The namespace keeps closed workflows for 24 h only, so the database — not the workflow id — is the long-term idempotency arbiter. Celery gets the discrete jobs: since Phase 3 it delivers every notification, enqueued by a Kafka consumer or by a Temporal reminder timer.

PlacementA workflow lives with the service that owns its aggregate (D-05): booking/cancel/reschedule/waitlist in Scheduling on scheduling-tq, visit completion in Visit on visit-tq; Billing has no workflow. One worker container per service, so activities touch only their own database.

Layered idempotency

high
Database arbiters first, workflow id second, idempotent activities throughout

AlternativesRedis idempotency cache only · rely on Temporal workflow-id dedup alone · client-side retry discipline

Why this1. Database arbiters: the partial unique index uq_appointments_active_slot (one active appointment per slot), the idempotency_keys row keyed by (caller, key) with a SHA-256 of the body (a replay returns the original appointment; a different body is 422), conditional updates (UPDATE … WHERE status = expected) for every transition, and history uniques (uq_visit_history_visit_to, uq_billing_history_record_key). 2. Workflow id: deterministic ids (booking-<id>, visit-completed-<id>, …) started with use-existing / reject-duplicate, so a second start is a no-op. 3. Activities: every Billing call carries an Idempotency-Key, and every audit write a dedupe_key, so Temporal’s at-least-once retries are safe.

TradeoffKeys live in Postgres, not Redis, so they survive a cache flush, at the cost of a write per booking. Workflow-id dedup is bounded by the 24 h namespace retention; beyond that only the database rules hold — which is why they come first.

Audit after commit: non-fatal, outbox deferred

Phase 2.1 · S3
A failed audit write after a committed step is logged, never fatal

AlternativesFail the request or workflow when the audit write fails · a local outbox table in each service · the Phase 3 transactional outbox to Kafka only

Why thisThe transition is already durable in appointment_status_history in the same transaction as the state change. Failing the request or the workflow after the commit would tell the caller a lie (a 500 for a booking that confirmed) or end a workflow before its second pass. Compensations also read the appointment’s state and do nothing for a committed booking, so a late failure can never undo a confirm. A local outbox would be a second mechanism; Phase 3 built the general one, but moving audit into it was deferred (the user accepted that), because it must not widen the booking accept path.

TradeoffIf Mongo is down at that instant the audit entry can be lost for good (audit.write_failed is logged with ids and exception type); nothing backfills it. Carrying audit in the outbox is the natural fix and is deferred.

Schedule-change delivery: poll an outbox, do not push

Phase 2.1 · M2
Provider writes schedule_change_events atomically; Scheduling polls and acknowledges

AlternativesProvider calls Scheduling directly after the change · Provider starts a Temporal workflow · wait for the Phase 3 Kafka event

Why thisA push is lost if Scheduling or Temporal is down at the moment of the change, and Provider must not call another service’s write path. The row commits with the change, stays pending until acknowledged, and a crash between “start the workflow” and “acknowledge” simply re-delivers (the start is idempotent). No cursor, because rows can commit out of order. Phase 3 also publishes the change as provider.schedule_changed, which nothing consumes; the pull feed stays the delivery path.

TradeoffUp to one poll interval (15 s) of delay; delivered rows are never purged; a polling Schedule to run (it is paused on the live Temporal server by the user’s decision, and was paused during feed tests).

Which slots are stale: set difference

Phase 2.1 · M2
Re-expand the current templates; any future slot not in that set is stale

AlternativesRecord which template produced each slot · invalidate slots by template id and date range · regenerate everything

Why thisIt is idempotent, needs no slot-to-template link, and reuses the tested, DST-safe generator, so the candidate set cannot drift from what generation would produce. Available stale slots are withdrawn; a stale booked slot flags its appointment instead of cancelling it (staff decide); held slots wait for a second pass after the hold TTL. Ambiguity withdraws nothing.

TradeoffA slot that cannot be derived from the templates is stale by definition (the application has no other path to create one); a slot still held at pass 2 gets no third pass.

Reconciler mechanism: one Schedule per service

Phase 2.1 · S4
Temporal Schedule (overlap SKIP) running one idempotent reconciler workflow

AlternativesA cron or sweeper loop inside the API · one more bespoke poller per stuck state · waiting for Phase 3 events

Why thisSame pattern as the hold reaper and the pending starter, visible in the Temporal UI. It re-derives outcomes from the database (a pending booking whose workflow is gone, a waitlist entry stuck matched, billing never voided, a no-show, a visit with an unsettled marker) with conditional updates, asks Temporal before touching a pending row, and re-reads before any Billing call, so a live booking is never failed and a committed one never voided.

TradeoffPolling (60 s); lists are oldest first with a cap (50 / 100) and no per-row backoff, so a persistent failure beyond the cap could starve newer rows; cancel and reschedule billing is not covered.

Single-use refresh tokens

Phase 2.1 · C1
Rotating refresh with an atomic Redis claim and an rjti claim on the access token

AlternativesReusable refresh tokens with a denylist check only · a refresh-token family table in Postgres · shorter-lived refresh tokens

Why thisOne SET NX EX both checks and consumes the refresh jti, so concurrent reuse yields exactly one winner, and it runs after the token and user validate so a bad token burns nothing. The access token names its paired refresh token, so logout revokes both without client cooperation. A used and a revoked token are deliberately indistinguishable (401). Redis down is 503 and the token is not consumed (fail closed, like the access path).

TradeoffClients must store the rotated token; access tokens issued before the change have no rjti and revoke only themselves; a Redis outage blocks refresh. Alongside it: bcrypt on a bounded thread pool, and case-insensitive email through a lower(email) unique index without rewriting existing rows.

Load test and NFRs: k6, one source of numbers

Phase 2.1 · D1, D2
k6 from a pinned Docker image; targets in loadtest/nfr.json

AlternativesLocust or a hand-written asyncio script (adds a dependency) · numbers copied into the PRD, docs and thresholds separately

Why thisNo package is added to the project (only Docker), and a test fails if the PRD table, docs/nfr.md or the k6 thresholds drift from the JSON. The numbers come from a stated demand model (50,000 requests a day, 60 percent in a 2-hour peak, a 5x peak minute rounded up to 25 per second, a 100 per second opening burst).

TradeoffThe targets are not yet measured: the smoke profile crossed its latency thresholds in both runs against the real stack in plan 02.1-13 (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; every accepted booking still confirmed; two uncontrolled runs on a heavily loaded laptop with no Jaeger collector) and sustained and burst have never run. The local single-instance stack is not claimed to meet NFR-01 or NFR-02. Phase 3 added the metrics and Grafana panels that can measure them, and the smoke profile passed every threshold on the Phase 3 stack in three runs, but sustained, burst and contention were deferred by the user until after Phase 3: nothing here claims a measured NFR.

Outbox relay: CDC with Debezium, not a polling publisher

Phase 3 · D-01
Debezium reads the Postgres write-ahead log; a service only inserts an outbox row

AlternativesA polling publisher in each service (same outbox table, a relay loop) · publishing to Kafka after the commit (a dual write with a gap)

Why thisThe user chose change data capture (D-01). No relay code lives in any service, ordering comes from the log, and there is no polling load on Postgres and no relay loop to make highly available. A service’s only job is to insert one outbox row in the same transaction as the state change, so the event exists exactly when the change committed. One connector per outbox database (scheduling, patient, provider, visit), each with its own replication slot and a least-privilege replication role.

Cost acceptedKafka Connect and logical replication must be operated: wal_level=logical (one Postgres restart, data survives), a replication slot per database that retains WAL while Connect is down (capped by max_slot_wal_keep_size=2GB; deleting a connector does not drop its slot), connector task state to watch, and delivery that is at-least-once on the wire. Reversing it later means writing a relay and removing the connector configs (costly).

Verification statusProven on the live stack: a Connect SIGKILL lost nothing (5 duplicates of 11 messages, all absorbed); a booking committed while Connect was stopped arrived once Connect was healthy. Not exercised: the path after a slot exceeds its WAL cap.

Kafka Connect image: Debezium, off the Confluent line (deviation)

Phase 3 · deviation, accepted
quay.io/debezium/connect:3.7.1.Final for Kafka Connect only; broker and Schema Registry stay on 7.6.13

Alternativescp-kafka-connect:7.6.13 with Debezium 3.x (cannot load it) · Debezium 2.x on that image (an end-of-life line) · a polling publisher, which needs no Connect at all

API gateway

high

AlternativesSelf-hosted Traefik or Nginx · managed/SaaS API gateways · no gateway (clients call each service directly)

Why thisA thin FastAPI proxy is the most reviewable choice: the whole routing knowledge is a short Python route table with tests, in the same stack and language as the services, with no extra configuration dialect to defend. Fixed windows allow a burst across a window boundary. While Redis is down the edge has no rate protection (fail-open is a chosen availability-over-protection tradeoff). It is a single local ingress and a single point of failure, and if it were ever placed behind another proxy the peer address it limits on would be that proxy’s. high

04

The three responsibility split & consistency patterns

The most-asked evaluation question is "why do you have Temporal and Kafka and Celery?" They solve different problems, and three patterns keep the system consistent under failure.

Who does what

TemporalMulti-step orchestration with compensation — the booking / cancel / reschedule / waitlist / visit-completion workflows (live since Phase 2) — and, since Phase 3, the per-appointment reminder timers. Knows the whole transaction.

KafkaDurable facts that already happened — broadcast to independent consumers (analytics projections, notification triggers, the visit follow-up). Replayable.

CeleryDiscrete single-step jobs, triggered by a Temporal reminder timer or a Kafka consumer — deliver a notification. Projections are not Celery tasks (the EVENT-04 deviation).

Three patterns that keep state honest

Transactional outbox (live since Phase 3)Business row + event row commit in one Postgres transaction; Debezium relays the row to Kafka from the write-ahead log, so no service holds a relay loop and there is no dual-write gap. Delivery on the wire is at-least-once; idempotent consumers make the effect exactly-once (effect-level). The pending-booking starter stays for the one gap the outbox does not cover (the accept path writes no outbox row); the visit sweeper is retired.

Layered idempotencyPostgres arbiters first (partial unique index, idempotency-key row, conditional updates), Temporal workflow-id dedup second, idempotent activities throughout. At-least-once delivery becomes effectively-once. Phase 3 adds a processed-event claim for database effects, deterministic ids for Temporal starts and a dedupe key for sends.

Saga compensationOn failure, run forward transactions (release slot, reverse billing, notify) — never a hard delete or silent rollback. Audit history stays intact.

05

Core flows

As built in Phase 2. Every multi-step change is a Temporal workflow in the service that owns the aggregate (scheduling-tq for appointments and the waitlist, visit-tq for visits), executed by its own worker container. Each step is an idempotent activity that writes one audit entry; failures compensate with forward state transitions and nothing is ever deleted. Clients poll a status URL. Phase 2.1 adds three flows below the visit lifecycle: the check-in window, the provider schedule change and the reconcilers. Phase 3 adds the event flows after the state machines (booking, cancel and reschedule, visit completion, notifications and reminders, analytics); the step lists above describe the workflows, which did not change shape.

Appointment booking saga

POST /api/appointments (with Idempotency-Key) writes the appointment as pending in the same transaction as the idempotency row, starts booking-<appointment id> and answers 202. The appointment is confirmed at step 4; the notification intent (step 5) follows only after confirm.

  1. Validate
    Patient, provider and clinic exist, are active and belong together — checked through their owners’ /internal routes with Scheduling’s aud-scoped service token. A missing reference is a business failure (ReferenceInvalid), an unreachable owner is retried.
  2. Reserve hold
    Slot available → held with held_until (10 min) and the appointment id, by a conditional update. Conflicts were already closed when the request was accepted: uq_appointments_active_slot lets exactly one active appointment exist per slot.
  3. Billing pre-check
    Billing creates the record pending and resolves it verified or failed with a deterministic rule (a coverage_ref starting DENY- is denied). Idempotency-Key on every call, so a retry never double-applies.
  4. Confirm
    One transaction: slot held → booked, appointment pending → confirmed, a history row, an audit entry and, since Phase 3, an appointment.booked outbox row. A lost hold (reaper got there first) is ConfirmLostHold and compensates.
  5. Notification intent (best-effort)
    Requested only after confirm succeeds. The activity is an intent record: it writes a PHI-free log line and a notification.requested audit entry and sends nothing. It retries, but its failure never fails or compensates the booking. Since Phase 3 the actual send is event-driven: the appointment.booked row committed at step 4 reaches the notification consumer and Celery (see the booking event flow below), and the workflow did not change shape.
  6. Compensate, in reverse order (on any failure)
    Void billing (failed/verified → voided) → release the hold (held → available) → mark the appointment failed with the error type as a machine-readable reason. Forward transitions only, one audit entry per step (dedupe_key = <workflow id>:<step>), so a failed booking is fully reconstructable from audit plus the Temporal history. A top-level booking that had taken the hold and did not lose the race then starts a waitlist advance, so the freed slot is offered again.
Deviation from SCHED-02, on purpose (D-09 as built, S7): the implemented order is validate, hold, billing pre-check before notification, then confirm, then a best-effort notification intent; SCHED-02 lists “schedule notifications → billing pre-check”. The notification intent is requested after confirm, so a booking that fails at confirm sends no notification and a patient is never told about a booking that is then compensated. The order change and the waitlist re-offer after a failed direct booking are workflow.patched and replay-tested. SCHED-02’s “prevent conflicts” step is not a separate activity: it is the reserve step’s database constraints (uq_appointments_active_slot, ex_appointments_patient_no_overlap).
Evidence: the concurrency suites fire parallel bookings at one slot against real Postgres and assert exactly one active appointment; scripts/demo_concurrent_booking.py shows it live through the gateway (50 parallel requests → 1 × 202, 49 × 409, one confirmed appointment). A deliberately denied booking ends failed with the slot re-offered and billing voided, in-process and on the deployed Compose stack.

Cancel

CancelWorkflow · cancel-<id>-<version> · 202 from the API.

  1. Cancel + release slot
    One transaction: appointment confirmed → cancelled, its current slot back to available.
  2. Billing refund state
    More than 24 h ahead: refund_pending → refunded; inside the cutoff: no_refund. Staff may waive the cutoff (patients may not). Decided in the API request, never in the workflow.
  3. Notification intent
    Separate best-effort activity.
  4. Advance the waitlist
    Starts waitlist-advance-<cancel workflow id> as an abandoned child for the freed slot.

Reschedule

RescheduleWorkflow · reserve-then-swap, never cancel-then-rebook.

  1. Hold the new slot
    Same provider only; a taken slot fails here and nothing changes.
  2. Swap in one transaction
    Release the old slot, book the new one, repoint the appointment. A rejected swap releases the new hold.
  3. Re-link billing
    The verified record follows the appointment (history row rescheduled).
  4. Notify, then advance the waitlist
    The old slot is offered to the waitlist.

Waitlist advance

WaitlistAdvanceWorkflow · FIFO per provider, optional time window.

  1. Claim
    The oldest matching waiting entry, claimed with FOR UPDATE SKIP LOCKED so two advances never take the same entry.
  2. Book as a child saga
    A normal BookingWorkflow for that patient on the freed slot — the same constraints and compensation apply.
  3. Resolve
    Confirmed → entry booked. Booking failed → entry failed, try the next (at most 5). Slot lost to a faster booker → entry back to waiting.

Visit lifecycle

Visit service · commit first, downstream after.

  1. Check in
    Front-desk/admin, only for a confirmed appointment inside the check-in window: Visit asks Scheduling to move it to checked_in first, then inserts the visit. One visit per appointment; a repeat returns the existing visit.
  2. Start
    The visit’s own provider (or staff); conditional update, repeats are no-ops, skipping a state is 409.
  3. Complete, then fan out
    The transition commits together with a visit.completed outbox row (downstream_started_at stays NULL) and the 200 returns; the API makes no Temporal call. The visit-downstream Kafka consumer then starts visit-completed-<id> and sets the marker. Billing finalize (open-ended retry), completing the appointment, the follow-up intent and the analytics intent run as independent branches on visit-worker. The Phase 2 sweeper is retired; an unsettled step is still picked up by the visit reconciler. The 200 never waits on any of it.

Check-in window and appointment states (Phase 2.1)

Mentor item M1 · Scheduling decides, Visit asks.

  1. Window by the database clock
    Check-in opens 60 minutes before the slot starts and closes when it ends (both configurable). The decision is made in the same locking SELECT that reads the row, with the database’s now(), so there is no clock skew between services.
  2. Scheduling first, visit second
    Visit calls Scheduling’s internal check-in (confirmed → checked_in, one history row), then inserts the visit. Refusals reach the client as three 409 strings: appointment not confirmed, check-in window not open, check-in window closed. A crash between the two converges on the next request (Scheduling answers 200 “already”).
  3. Refuse what it would corrupt
    Cancel and reschedule are 409 from checked_in onward, so a patient who is in the building can no longer be refunded or rebooked. checked_in, completed and no_show still hold their slot: the unique index and the patient-overlap exclusion cover them (scheduling_0004).
  4. Complete, or no-show
    Visit completion completes the appointment (a fourth workflow branch). A confirmed appointment whose slot ended more than 30 minutes ago becomes no_show through the reconciler sweep; there is no manual staff action.

Provider schedule change (Phase 2.1)

Mentor item M2 · Provider writes the fact, Scheduling pulls it.

  1. Outbox row with the change
    Editing or deactivating a template, or deactivating a provider, writes a schedule_change_events row in the same transaction (ids and a change type only; a change that alters nothing writes none).
  2. Poll, start, acknowledge
    A Schedule (every 15 s) reads the pending events over Provider’s internal feed with Scheduling’s service token, starts schedule-change-<event id> for each, and only then acknowledges, so a crash re-delivers.
  3. Apply: set difference
    The provider’s current templates are re-expanded; every future slot not in that set is stale. Available stale slots are withdrawn; stale booked slots flag their appointment (it stays confirmed, staff cancel or reschedule); missing future slots are inserted for an active provider.
  4. Second pass after the hold TTL
    A durable timer (hold TTL plus one minute), then the same apply again, so a booking that confirmed just after pass 1 is flagged rather than missed. A slot still held at pass 2 gets no third pass (open risk). Staff worklist: GET /api/appointments?flagged=true&status=confirmed.

Reconcilers (Phase 2.1)

Mentor item S4 · one Temporal Schedule per service, overlap SKIP, idempotent, batch-capped, oldest first. They re-derive outcomes from the database and never guess.

  1. Stuck pending bookings (Scheduling, every 60 s)
    A pending appointment older than 10 minutes blocks its slot forever. If Temporal says booking-<id> is gone, the appointment is re-read, billing voided, the hold released and the appointment failed with workflow_lost, then the slot is offered to the waitlist. If Temporal cannot answer, nothing is touched.
  2. Billing lookback, stuck waitlist entries, no-shows
    Bookings failed by the reaper or the reconciler in the last 24 hours get their billing voided if it was not; a waitlist entry stuck matched for 15 minutes is resolved from its appointment; a confirmed appointment past slot end plus grace gets Billing no_refund and then no_show.
  3. Visit reconciler (every 60 s)
    A completed visit whose billing or appointment settlement marker is still empty after 10 minutes is settled by the same step bodies and idempotency keys as the workflow, so the two can race without a double effect. Billing finalize now retries without a time limit instead of skipping.
Still open: cancel and reschedule billing steps that exhaust their bounded budget are recorded as *_incomplete:billing_pending for an operator; only a failed booking’s billing, the no-show refund state and visit billing are reconciled.

06

Anticipated evaluation questions

Prepared, defensible answers to the questions a mentor is most likely to ask, mapped to the graded criteria: architecture clarity, reliability & failure handling, correct tool use, observability.

Why Temporal instead of just Celery for booking?

Celery runs discrete jobs; it doesn't own a multi-step transaction or model compensation. Booking is a saga — validate, reserve a hold, billing pre-check, confirm, notification intent — where a failure at the billing step must undo the hold cleanly and in order. Temporal gives durable execution (the workflow survives a worker crash and resumes), deterministic replay, per-activity retry policies and first-class compensation, plus Schedules for the reaper, the starter and the reconcilers.

Since Phase 3 they are complementary in practice: Celery delivers every notification, and Temporal decides when a reminder fires (a durable timer per appointment) and then enqueues the same Celery task. The Phase 2 notification activities stayed as intent records, so no workflow changed shape and nothing is sent twice.

Why do you run both Kafka and RabbitMQ?

Kafka is a durable, replayable log of facts — many independent consumers (analytics projections, notification triggers, the visit follow-up) read the same appointment.booked event, and a new consumer can replay history. RabbitMQ + Celery is a work queue for discrete jobs with per-task retry and a dead-letter path.

Using Kafka as a task queue loses per-message retry/ack semantics; using RabbitMQ as an event log loses replay and multi-consumer fan-out. Each tool does the job it's good at.

As built, the notification consumer reads Kafka and enqueues one Celery task per dedupe key on RabbitMQ. The analytics projections do not use Celery at all (the EVENT-04 deviation, below).

How do you prevent double-booking under concurrency?

In the database. A partial unique index, uq_appointments_active_slot (UNIQUE (slot_id) WHERE status IN ('pending','confirmed')), means two active appointments for one slot simply cannot both commit; the loser gets a 409 before any workflow starts. Underneath, ex_provider_slots_no_overlap keeps a provider’s slots from overlapping and ex_appointments_patient_no_overlap keeps a patient from being double-booked across providers.

This is deliberately not "check-then-insert in application code," which races. Proof: concurrency tests fire parallel bookings at one slot through raw SQL and through the HTTP API and assert exactly one active appointment, and scripts/demo_concurrent_booking.py shows it live on the deployed stack (50 parallel requests → one 202, 49 × 409, one confirmed appointment).

How is an event never lost after a database commit?

The transactional outbox, relayed by change data capture. The business row and an outbox row are written in the same Postgres transaction, so they commit or fail together: there is no dual-write gap where the database commits and a publish is lost. No service publishes to Kafka. Debezium reads the Postgres write-ahead log and publishes each outbox row to the aggregate’s topic; the replication slot keeps WAL until Connect confirms it, so a Connect outage delays events and drops none.

Measured on the live stack: a worker killed right after a cancel committed still produced appointment.cancelled; a booking committed while Connect was stopped arrived once Connect was healthy; a visit completion followed by a Visit API kill, a stopped consumer and a stopped Connect still started exactly one downstream workflow. Limits: only the ten D-07 event types are evented (see “Does every state change become an event?”), and the path after a replication slot exceeds its WAL cap was not exercised.

How do you handle duplicate / at-least-once delivery?

Layered idempotency, database first. A retried POST /api/appointments with the same Idempotency-Key finds the (caller, key) row in Postgres and returns the original appointment; the same key with a different body is a 422. Workflows have deterministic ids, so a second start attaches to or is rejected by the existing run. Activities are idempotent by construction: conditional state updates, an Idempotency-Key on every Billing call (a repeat is a no-op), and an audit dedupe_key per workflow step. Visit transitions are conditional updates with a unique history row per state, so ten concurrent “complete” calls produce one transition. For Kafka events, see the next question.

Can an event be lost or duplicated?

No, and the dashboard does not claim it. The honest statement has three parts: no loss (an event exists exactly when its transaction committed, and the replication slot holds WAL until Connect confirms it), at-least-once on the wire (Debezium commits its position periodically, so a hard kill of Connect re-emits what it had sent since the last flush; the topic can carry a duplicate), and effect-level exactly-once, because every consumer is idempotent.

Measured: after a Connect SIGKILL, 11 messages for one aggregate carried 6 distinct event ids (5 duplicates of 11 messages, nothing lost); in another run one booking’s appointment.booked appeared 2 times with 1 distinct event id and the booking still had one delivery, one provider call, one reminder run and exactly one increment of appointments_booked; rewinding the offsets of all three consumer groups left every effect equal. A consumer that is not idempotent must not be added to these topics.

Why Debezium CDC instead of a polling publisher?

Decision D-01, chosen by the user. With CDC no service contains relay code: a service inserts an outbox row in the same transaction as the state change and Debezium relays it from the write-ahead log. Ordering comes from the log, and there is no polling load on Postgres and no relay loop to make highly available. A polling publisher would have meant a relay loop in four services and a query against each outbox table on an interval.

The cost accepted is operating Kafka Connect and logical replication: wal_level=logical (one Postgres restart), a replication slot per database that retains WAL while Connect is down (capped at 2 GB; deleting a connector does not drop its slot), connector task state to monitor, and at-least-once delivery on the wire. Reversing it later means writing a relay and removing the connector configs. Connect runs quay.io/debezium/connect:3.7.1.Final, a deliberate deviation from the same-Confluent-line rule for the Connect image only, accepted at plan 03-01 (“Accept all six (Recommended)”).

Why Temporal timers for reminders instead of Celery ETA or beat?

Decision D-02. A reminder is a per-appointment timer that must be cancelled when the appointment is cancelled and moved when it is rescheduled. A Temporal workflow is exactly that: durable, replay-tested, signal-interruptible, one deterministic id per appointment (reminder-<appointment id>). A Celery ETA message lives in the broker (lost with it, hard to cancel or move without revoke bookkeeping) and a beat schedule is a cron, not a per-appointment timer.

Temporal owns when, Celery owns delivery: when the timer fires, the activity enqueues the same notifications.send task the Kafka consumer uses. Cost: one idle workflow per active appointment. Not exercised: the later firing inside the same trace, which would take days.

How do you stop a notification being sent twice, and what if a real provider has no idempotency key?

Every send has a dedupe key (<type>:<appointment id>:<event id> for event sends, with the slot time and lead for reminders and the visit id for follow-ups). It is enforced at two layers: the delivery log (unique on the key) and the provider’s own idempotency store, where the insert is the delivery. Two guards stop late work from doing harm: a reminder for an appointment recorded as closed is skipped, and a booking, cancellation or reschedule event older than a day is recorded as stale instead of sent, so replaying history never sends old mail. It was proven with a real worker killed between the provider call and mark_sent: the message was redelivered, the provider answered from its store and held one call record.

Real-provider caveat: that guarantee holds because the fake provider honours an idempotency key. A real SMS or email provider must accept one for the same guarantee; with no idempotency key, each crash between the provider call and mark_sent can cause one duplicate send. No real provider is integrated (out of scope).

Do events and notifications carry PHI?

No. Event payloads carry ids and timestamps only: a test scans every .avsc for banned field names, and the producers’ tests check the payload bytes and the raw Kafka bytes for seeded PHI values. Celery task arguments are ids, a type, a dedupe key and a timestamp; a rejected message’s reason and the dead-letter headers carry the error type only, because a validation error’s text would echo the offending value. Run live, a booking’s trace id was found as a JSON log line in six containers and none of six seeded PHI values appeared in any of them. No real SMS or email provider is integrated, so no message leaves the system.

What happens when Kafka Connect, Schema Registry, RabbitMQ or Temporal is down? (outage behaviour)

Connect down: events are delayed, none are dropped, because the replication slot keeps WAL (capped at 2 GB). A consumer’s dependency down (Schema Registry, Postgres, Temporal, RabbitMQ): the offset is held and retried with capped backoff for up to the cap (10 attempts and 15 minutes), after which the message is dead-lettered as TransientExhausted and recovered by the visit reconciler, the analytics rebuild or the DLQ replay script. A message that can never succeed (undecodable, malformed, unknown id) is copied to the group’s dead-letter topic with the error type only, and an ordinary handler error is retried three times first. Celery worker dies mid-send: the unacknowledged message is redelivered and the provider answers from its idempotency store.

Schema Registry is a cached write-path dependency: producers warm their serializers at start-up, so an outage after warm-up does not affect writes, but a cold start during an outage cannot become ready. Not verified: the consumer’s decode-time registry-outage path has no automated test, a Kafka broker outage on its own was not exercised, and the path after a slot exceeds its cap was not exercised.

Can the analytics be rebuilt, and do they include history?

The projections are derived data in analytics_db. To rebuild: stop analytics-consumer, run services.analytics.rebuild (a dry run, then --apply, which truncates the projections and resets the group to the earliest retained offset), and start the consumer again; the tool refuses to run while the group has a live member. A rebuild replays everything still retained, including the throw-away test events the live consumer skipped at go-live, so the numbers can differ from the live ones by those events.

Analytics start at cutover (D-13): events are emitted only for new activity, so the five metrics count from Phase 3 go-live and total_patients counts only patients registered after it; earlier patients, appointments and visits are not backfilled into the stream (the only backfill is the completed-visit downstream one, whose dry run found 0 candidates). The metric definitions are written down: days are UTC days, cancellation rate is cancelled over booked in the window, average wait is check-in to visit start, and an empty denominator is no data, never 0.

The requirement says projections are Celery tasks. Why are they a Kafka consumer? (EVENT-04)

A deliberate deviation, accepted at plan 03-01 (“Accept all six (Recommended)”). A projection is a stateful upsert, and its idempotency claim must commit in the same database transaction as the effect; a Kafka consumer with a processed-event table gives that, a Celery task does not. Celery delivers notifications and follow-up sends. The wording of EVENT-04 in REQUIREMENTS.md is the user’s decision and was not edited, so the requirement text and the build disagree until it is.

Does every state change become an event?

No: “every state change” is scoped to the Phase 3 event set (decision D-07 of the Phase 3 context), ten types: appointment.booked, appointment.cancelled, appointment.rescheduled, appointment.checked_in, appointment.completed, appointment.no_show, visit.completed, patient.registered, patient.deactivated and provider.schedule_changed. Billing transitions, waitlist changes, a visit moving to in-progress and the reconciler and hold-reaper actions are not evented, so an analytics number or a notification reflects only those ten. provider.schedule_changed is published but not consumed: Scheduling still pulls schedule changes through the Phase 2.1 feed, and that poller is paused on the live server by the user’s decision.

Which Phase 2 interim mechanisms are gone, and which stay?

One is retired: the visit downstream sweeper. visit.completed is committed with the transition and a consumer starts the downstream workflow; the Schedule is deleted and the workflow class stays as a no-op tombstone so recorded histories replay. The replacement was proven by kill-between-commit-and-publish tests.

The others stay, because events do not subsume them: the hold reaper (an expired hold is the absence of an event), the pending-booking starter (the accept path writes no outbox row, so no event exists for a pending appointment), the Scheduling and Visit reconcilers (none of their triggers is an event), the notification stub activities (intent records), polling of status URLs, and Temporal’s auto-setup image (non-production).

Why PostgreSQL and MongoDB, rather than one database?

Split by consistency need. Data the saga must reason about for correctness — patients, providers, appointments, slots, billing, the outbox — needs transactions and constraints, so it lives in Postgres. Append-heavy, schema-flexible data — the audit trail and the notification delivery log — fits a document model, so it lives in MongoDB; the analytics projections are derived, relational data and live in their own Postgres database (analytics_db), rebuildable from the topics. Forcing either into the other's model is where teams get burned.

How does a partial failure not corrupt scheduling state?

Saga compensation as forward transitions. If billing denies the booking after the slot is held, the workflow runs the compensations in reverse order — void the billing record, release the hold, mark the appointment failed with a machine-readable reason — with one audit entry per step and nothing deleted. A hold whose workflow died is released by the reaper Schedule. The appointment is never left half-confirmed; this was proven in-process and on the deployed stack (forced DENY- coverage reference → failed, slot available again, billing pending → failed → voided).

How do you trace a request across async boundaries?

One booking is one connected trace. The W3C traceparent of the producing span is stored in the outbox row, carried by Debezium into the Kafka header, extracted by our own consumer base (about 30 lines; the OpenTelemetry confluent-kafka instrumentation is deliberately not installed, because it records a link to the producer rather than a parent, which would make two traces) and passed into Celery’s task headers by the Celery instrumentation; Temporal interceptors cover workflow and activity spans.

Measured: a booking sent with a known trace id produced one trace in Jaeger (e839d1a9ec7d48e435d09abb68881b00) with 57 spans across 12 services (gateway, Scheduling, the Scheduling worker, Billing, the notification consumer, the Celery worker, the notification Temporal worker and the analytics consumer), visible within 7 s and read through Jaeger’s HTTP API by an automated test. Honest limits: the reminder timer fires hours or days later, so that trace is long-lived and can show a wide gap, and the later firing inside the same trace was not exercised; nobody has yet looked at the trace in the Jaeger UI (the phase gate’s manual check).

Why are reference checks synchronous instead of event-driven?

Because the simplest correct thing is to ask the owning service at write time, and Phase 3 did not change that. Kafka and the transactional outbox exist now, but event-fed local copies of reference data were not built: GET /internal/…, caller’s JWT forwarded, three bounded attempts on transport errors, then 422 if the target is missing or inactive and 503 if the owner cannot answer — nothing is written either way.

The cost is unchanged and stated plainly: writes depend on the owner’s availability. Event-fed copies would remove that coupling and introduce an eventual-consistency window instead; that work is not done. Deactivation never cascades (D-06) and reads return ids only (D-07 of the Phase 1.1 context).

What happens when Organization is down during a provider write?

The Provider service cannot confirm the department, so the request fails closed with 503 after its bounded retries; no provider row is written and the failed attempt is audited. The trace for that request shows the failed Provider→Organization hop, and the gateway’s own timeout mapping would return 504 if the whole call stalled.

Honest status: this is covered by in-process tests with a simulated unreachable owner. It has not been exercised against a real container going down mid-request.

How does a service verify a token without calling Identity?

Tokens are RS256. Each service fetches Identity’s public keys from /.well-known/jwks.json, caches them (300 s TTL), picks the key by the token’s kid, and verifies the signature and claims locally. An unknown kid triggers one refresh with a 30 s backoff so a flood of bad tokens cannot hammer Identity. Revocation is the one shared lookup: every service checks the Redis denylist for the token’s jti.

Only Identity holds the private key, so no other service can mint a token. Key rotation is supported through kid but has not been exercised yet.

What happens if a worker dies mid-booking?

Nothing is lost. The workflow’s progress is in Temporal’s history, not in the worker. When an activity’s worker dies, the server times the attempt out and retries it on another worker; because every activity is idempotent, a step that had already half-run is safe to repeat. A test does exactly this against the Compose Temporal: worker A hangs inside the billing step and stops polling, worker B picks up the retry after the 10 s timeout, and the booking ends confirmed with one scheduled billing activity on attempt 2.

Two Schedules cover the gaps around a crash: the hold reaper releases holds that outlived their workflow, and the pending-booking starter starts workflows for appointments committed as pending whose start call never happened. In Compose the worker containers restart automatically and report health through a heartbeat file.

What stops a patient who has checked in from cancelling and being refunded?

The appointment state machine (Phase 2.1, M1). An appointment now moves pending → confirmed → checked_in → completed, with no_show, cancelled and failed on the side. Visit moves it to checked_in through Scheduling’s internal check-in route, only inside a window around the slot judged by the database clock, and cancel and reschedule are 409 from checked_in onward at the API, the repository and the workflow activities. The three new states still hold their slot, because the unique index and the patient-overlap exclusion were widened to cover them, so the guarantee is in the database, not only in code.

A no_show is set only by the reconciler sweep, after the slot ended plus a 30-minute grace; there is no manual staff action yet, and visits created before Phase 2.1 have no checked-in appointment (they settle as not_checked_in, with no backfill).

What happens to slots and bookings when a provider changes their schedule?

The change writes an outbox row in Provider in the same transaction; Scheduling polls it (every 15 s), starts one ScheduleChangeWorkflow per event and acknowledges after the start. The workflow re-expands the provider’s current templates and treats every future slot not in that set as stale: available ones are withdrawn, booked ones flag their appointment (it stays confirmed, staff cancel or reschedule it, and cancelling withdraws the stale slot instead of freeing it), and slots held by an in-flight booking are re-checked in a second pass after the hold TTL.

Honest gaps: it is polled, not event-driven (Phase 3 also publishes provider.schedule_changed, but nothing consumes it and the poller Schedule is paused on the live server by the user’s decision); a slot still held at the second pass gets no third pass; delivered events are never purged; waitlist entries of a deactivated provider are untouched.

What if something fails after the database commit?

Compensations read the appointment’s current state and do nothing for a committed booking, so a late failure can never void billing or release a slot of a confirmed appointment. The audit write after a committed confirm, cancel, swap, check-in, complete or schedule-change apply is non-fatal: it is logged as audit.write_failed and the outcome stands, because the transition is already durable in appointment_status_history.

The cost is stated plainly: if Mongo is down at that instant the audit entry can be lost and nothing backfills it. Carrying audit in the Phase 3 transactional outbox is the natural fix; it was deferred (the user accepted that), because it must not widen the booking accept path.

How are stuck states recovered?

Two reconciler Schedules. Scheduling’s fails pending bookings whose workflow is gone (they would block the slot forever), voids orphaned billing, resolves waitlist entries stuck matched, and sweeps no-shows. Visit’s settles completed visits whose billing or appointment marker is still empty, and visit billing finalize now retries without a time limit instead of skipping. Both use conditional updates, ask Temporal before touching a pending row (an unreachable Temporal skips the step), reuse the workflows’ own idempotency keys, and are capped per run, oldest first.

Not covered: cancel and reschedule billing steps that exhaust their bounded budget are still recorded for an operator (*_incomplete:billing_pending), and there is no per-row backoff, so a persistent failure beyond the batch cap could starve newer rows.

Does it meet its load and availability targets?

Unknown, and the dashboard does not claim otherwise. Phase 2.1 defined NFR-01..08 from a stated demand model (50,000 booking requests a day, 25 per second sustained for 10 minutes, a 100 per second burst, p95 accept latency 300 ms, 99.9 percent availability) in one file that the PRD, docs/nfr.md and the k6 thresholds all derive from, and added a runnable k6 load test with a seed script. The targets are not yet measured.

What ran: in plan 02.1-13 the smoke profile crossed its latency thresholds in both runs (booking accept p95 2.0 to 6.0 s against 300 ms, saga completion p95 16.7 to 28.5 s against 5 s; two uncontrolled runs on a heavily loaded laptop). Three later smoke runs on 10 and 11 November 2026 passed every threshold: booking accept p95 21.8 ms before Phase 3, then 29.3 ms and 49.1 ms, with saga completion p95 about 0.52 s each time. The host load differed and each run has about 151 booking samples, and accept latency crept up across the three, so it is the number to watch; the cause was not isolated (there was no A/B run).

Phase 3 added the Prometheus histograms and Grafana panels that can measure the targets (no panel exists for NFR-01, 06, 07 and 08, and docs/nfr.md says so). sustained, burst and contention were not run: the user deferred them until after Phase 3. The local single-instance stack is not claimed to meet NFR-01 or NFR-02; what is verified is correctness under contention (the concurrency suites and the 50-way live demo).

What changed for clients in authentication?

Refresh tokens are single-use and rotated: /refresh returns a new pair and reusing the old refresh token is 401, so a client must store the new one (a Redis outage is 503 and the token is not consumed). Access tokens carry an rjti claim naming their refresh token, so logout revokes both. bcrypt runs on a bounded thread pool so a login burst cannot stall the event loop, and email is case-insensitive through a lower(email) unique index (existing rows are not rewritten). Lists of patients, providers and clinics are paginated (limit 1..200, X-Total-Count), and GET /api/patients/me plus provider reads of their own appointments exist.

What is not yet verified after Phase 3?

Load: NFR-01..08 are targets that are not yet measured; only the smoke profile ran (it passed in three runs and accept latency crept up), and sustained, burst and contention are deferred until after Phase 3. Traces and dashboards: one booking is one Jaeger trace in an automated test, but nobody has yet looked at it in the Jaeger UI, the four Grafana dashboards were exercised through Grafana’s query API and not viewed in a browser, and the reminder’s later firing inside the same trace was not exercised. Failure paths: the consumer’s decode-time Schema Registry outage path has no automated test, a Kafka broker outage on its own was not exercised, and the path after a replication slot exceeds its WAL cap was not exercised. Real provider: one send per dedupe key needs an idempotency key at a real SMS or email provider; none is integrated. Scope: only the ten D-07 event types are evented, analytics start at cutover, provider.schedule_changed is published but not consumed, and event-fed local copies were not built.

Hardening: this is a local/dev system with synthetic data only. Kafka, Schema Registry and the Connect REST API have no authentication on the dev network; application and Celery containers run as root (the Semgrep missing-user findings are accepted for now by the user); Temporal runs from the non-production auto-setup image; Mongo audit writes are not atomic with the Postgres commit (WR-04) and moving audit into the outbox is deferred; the outbox, the topics, processed_events and the delivery log have no retention. Logout, PHI log-safety and database isolation are implemented and tested but not fully hardened.

Carried from Phase 1.1: no request-body size cap at the gateway; one shared Redis for the denylist and rate limits. Not yet verified: real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, and the bootstrap_admin.py admin-creation branch (only its no-op path is tested). Three assumptions await mentor confirmation: the provider→department→clinic scope chain relies on write-time validation (ORG-03), overlapping availability templates are still allowed (PPL-03), and clients combining services may briefly see stale state (PPL-04).

Is the local Docker Compose setup production-shaped?

Honestly: the local stack uses Temporal's auto-setup image and single-node Kafka and a single Postgres container (hosting all seven service databases) for developer convenience — that's labeled as dev-only, not a production deployment. Production-shaping (separate Temporal schema management, replicated brokers, a Postgres instance per service, non-root application containers, resource limits) is called out as a decision to document rather than something silently claimed. Being explicit about this is part of the reliability story, not a gap.

Phase 3 adds more dev-only shapes: Kafka Connect and Debezium with a replication slot per database (the slots retain WAL while Connect is down, capped at 2 GB), Kafka, Schema Registry and the Connect REST API without authentication on the Compose network (production would need SASL and TLS, ACLs per consumer group and authenticated Connect access), classic RabbitMQ queues, and containers that run as root (accepted for now by the user; the Semgrep missing-user findings stand).
