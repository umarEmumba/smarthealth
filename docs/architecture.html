Edge — API Gateway · :8000, the only published application port wired

FastAPI + httpx proxy Route table: /api/auth /api/admin /.well-known/jwks.json → Identity · /api/clinics → Organization · /api/providers → Provider · /api/patients → Patient. /internal/* and unsafe paths answer 404. Per-IP fixed-window limits in Redis (auth 20/min, default 300/min), fail-open on a Redis outage, visibly. 503/504 on upstream failure. Does not verify JWTs and does not aggregate responses.

Flows

1 · Gateway request flow
Client ──Bearer access token──▶ Gateway ├─ path safety: no dot segments, encoded / \ NUL ──▶ else 404 ├─ route table (no /internal prefix exists) ──▶ no match: 404 ├─ Redis: fixed-window counter (auth 20/min, other 300/min) │ over budget ──▶ 429 + Retry-After │ Redis down ──▶ fail OPEN (warning log + counter) └─ forward to owning service (hop-by-hop stripped, traceparent added) ├─ verify RS256 locally · denylist · RBAC · clinic scope ├─ service database: read / write, one commit └─ MongoDB: append audit_log (field names only) upstream unreachable ──▶ 503 upstream timed out ──▶ 504 no JWT check and no retries at the edge; reads return ids only
2 · Reference-check flow (D-05) — fail closed
Client ──POST /api/providers { department_id }──▶ Gateway ──▶ Provider Provider ──GET /internal/departments/{id} (caller's JWT forwarded)──▶ Organization up to 3 attempts, backoff, GET and transport errors only 200 active ──▶ INSERT provider (department_id is a plain UUID) ──▶ 201 missing or inactive ──▶ 422, nothing written owner unreachable / 401 / 403 / 5xx ──▶ 503, nothing written Deactivation never cascades (D-06). Kafka / outbox / event-fed copies: Phase 3 (D-08).
3 · Token verification via JWKS
Identity: login ──▶ sign access + refresh JWT (RSA private key, kid smarthealth-identity-1) Any service: request + Bearer token JWKS cache empty / older than 300 s / unknown kid (30 s backoff) ──▶ GET /.well-known/jwks.json verify signature by kid, algorithm and claims locally Redis: jti denylisted? ──▶ yes: 401 Redis unreachable: 503 (fail closed) ──▶ RBAC ──▶ handler Only Identity holds the private key (Compose secret, gitignored file). Service tokens: 60 s, no aud claim (recorded gap).
4 · Connected trace
Gateway (server span, W3C traceparent) └─▶ Provider (httpx client span) ├─▶ Organization (reference check, client span) └─▶ Identity (JWKS fetch on cache miss, client span) Spans exported over OTLP to Jaeger; one OpenTelemetry service name and one Prometheus job per service. Observed as one trace via Jaeger's query API; not yet viewed in the Jaeger UI.

Known limitations and unverified items

  • Gateway buffers whole request bodies with no size cap (the limiter bounds request count, not size).
  • One shared Redis holds the denylist and rate-limit counters: an outage fails the limiter open and token verification closed (503); a flush would drop revocations.
  • Service tokens carry no aud claim; application containers run as root.
  • Not verified: real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, a person viewing the trace in the Jaeger UI. Key rotation is supported through kid but not exercised.
  • Assumptions awaiting mentor confirmation: the provider → department → clinic scope chain relies on write-time validation (ORG-03); overlapping availability templates remain allowed (PPL-03); clients combining services may briefly see stale cross-service state (PPL-04).

Key design decisions

DecisionChoiceWhy
Service cutSix services, database each (D-01)Mentor review asked for true microservices; clear bounded contexts; PHI confined to Patient. Costs: network hops, availability coupling, no distributed transactions
Token modelRS256 + JWKS; Redis jti-denylistOnly Identity can mint tokens; services verify without calling Identity; real logout
GatewayThin FastAPI proxy, per-IP Redis limits, fail-open, no JWT check at the edgeMost reviewable; defence in depth; availability over rate protection
Cross-service integritySynchronous owner check at write time, 422/503, no cascadeNo Kafka/outbox until Phase 3 (D-08); simplest correct option
Slot modelTemplates in Provider; empty provider_slots with live GiST constraint in Scheduling (D-03)Phase 2 inherits a proven double-booking invariant without moving a table
Identity vs profileAccounts in Identity; profiles in Patient/Provider by plain user_id (D-04)Self-registration and no-login staff-created profiles; PHI out of Identity
AuditShared library, one shared audit_log (D-02)Dedicated Audit service is Phase 3; call signature kept stable
DeletionSoft-delete (is_active / deactivated_at)Records stay auditable & retained — no hard deletes
PHI safetyField-name-only audit; structlog redactionNo PHI in logs or traces
