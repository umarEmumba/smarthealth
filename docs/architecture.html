End-to-end request flow — the tracer

Client ──login──▶ FastAPI ──▶ PostgreSQL (fetch user) │ bcrypt verify (constant-time even if user absent) ◀── { access_token, refresh_token } Client ──Bearer access──▶ FastAPI ├─▶ Security: verify signature + claims ├─▶ Redis: jti denylisted? ──▶ no ├─▶ RBAC: require_role(...) + ownership/clinic-scope ├─▶ PostgreSQL: read / write domain data ├─▶ MongoDB: append audit_log (PHI-free, trace_id) ├─▶ structlog: PHI-safe line carrying trace_id └─▶ Jaeger: export OTel span Logout / revoke ──▶ add jti to Redis denylist (auto-expires at token TTL)

Key design decisions

DecisionChoiceWhy
Auth & sessionAccess+refresh JWT, Redis jti-denylistReal revocation (IAM-03); short TTL bounds leaked tokens; no new infra
Slot modelWeekly templates; empty slots + live GiST exclusion constraintP1 config-only; P2 inherits a proven no-double-booking invariant
Identity vs profileSeparate users / patients (nullable link)Self-registration (IAM-01) + staff-created no-login profiles (PPL-01)
DeletionSoft-delete (is_active / deactivated_at)Records stay auditable & retained — no hard deletes
PHI safetyField-name-only audit; structlog redactionHIPAA — no PHI in logs or traces
ConcurrencyAsync ORM + asyncpg, async Mongo/RedisSustains concurrent load without blocking the event loop
