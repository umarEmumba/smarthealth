All services also fetch Identity's JWKS (cached) and use Redis and MongoDB. Workers and the Scheduling/Visit APIs call /internal routes with service tokens minted by Identity from a per-service client secret (Compose secret): short-lived, one aud per token, and every internal route names its allowed callers (Scheduling → patient, provider, organization, billing; Visit → scheduling, provider, billing).

Flows

1 · Gateway request flow
Client ──Bearer access token──▶ Gateway ├─ path safety: no dot segments, encoded / \ NUL ──▶ else 404 ├─ route table (no /internal prefix exists) ──▶ no match: 404 ├─ Redis: fixed-window counter (auth 20/min, other 300/min) │ over budget ──▶ 429 + Retry-After │ Redis down ──▶ fail OPEN (warning log + counter) └─ forward to owning service (hop-by-hop stripped, traceparent added) ├─ verify RS256 locally · denylist · RBAC · clinic scope ├─ service database: read / write, one commit └─ MongoDB: append audit_log (field names only) upstream unreachable ──▶ 503 upstream timed out ──▶ 504 no JWT check and no retries at the edge; reads return ids only
2 · Reference-check flow (D-05) — fail closed
Client ──POST /api/providers { department_id }──▶ Gateway ──▶ Provider Provider ──GET /internal/departments/{id} (caller's JWT forwarded)──▶ Organization up to 3 attempts, backoff, GET and transport errors only 200 active ──▶ INSERT provider (department_id is a plain UUID) ──▶ 201 missing or inactive ──▶ 422, nothing written owner unreachable / 401 / 403 / 5xx ──▶ 503, nothing written Deactivation never cascades (D-06). Kafka / outbox / event-fed copies: Phase 3 (D-08).
3 · Token verification via JWKS
Identity: login ──▶ sign access + refresh JWT (RSA private key, kid smarthealth-identity-1) Any service: request + Bearer token JWKS cache empty / older than 300 s / unknown kid (30 s backoff) ──▶ GET /.well-known/jwks.json verify signature by kid, algorithm and claims locally Redis: jti denylisted? ──▶ yes: 401 Redis unreachable: 503 (fail closed) ──▶ RBAC ──▶ handler Only Identity holds the private key (Compose secret, gitignored file). Service tokens: 60 s, aud-scoped (Phase 2).
5 · Booking saga with compensation (Phase 2)
Client ──POST /api/appointments + Idempotency-Key──▶ Scheduling one tx: idempotency row + appointment pending (uq_appointments_active_slot: a taken slot ──▶ 409) start booking-<id> on Temporal ──▶ 202 { appointment_id, status_url } (client polls) scheduling-worker (scheduling-tq): 1 validate patient / provider / clinic active, via /internal + service token 2 reserve slot available ──▶ held (held_until = now + 10 min) 3 billing pre-check: pending ──▶ verified | failed 4 confirm slot held ──▶ booked · appointment pending ──▶ confirmed 5 notification intent only, best-effort, requested after confirm — never fails the booking on failure, reverse order, forward transitions only (no deletes), one audit entry per step: void billing (failed ──▶ voided) ──▶ release hold (held ──▶ available) ──▶ appointment failed (reason) ──▶ (top-level booking that held the slot, not a lost race) start waitlist-advance for the freed slot Order note: the notification is requested after confirm (SCHED-02 lists notification earlier; the implementation differs on purpose), so a booking that fails at confirm sends no notification. Both changes are workflow.patched; a slot that already started is 422 "slot has already started".
6 · Cancel, reschedule, waitlist advance
Cancel : cancel + release slot ──▶ billing refund_pending ──▶ refunded (> 24 h ahead) | no_refund (staff may waive) ──▶ notification intent ──▶ start waitlist-advance child Reschedule : hold new slot ──▶ ONE tx: release old, book new, repoint appointment ──▶ re-link billing ──▶ notify ──▶ waitlist advance Waitlist : FIFO claim (FOR UPDATE SKIP LOCKED) of the first matching waiting entry ──▶ child BookingWorkflow booked ──▶ entry booked · booking failed ──▶ entry failed, try next (cap 5) · lost race ──▶ entry back to waiting
7 · Visit completion — commit first, downstream after
Provider ──POST /api/visits/{id}/complete──▶ Visit commit: in_progress ──▶ completed, downstream_started_at = NULL start visit-completed-<id> (errors are logged; the 200 is unaffected) ──▶ marker = now visit-worker (visit-tq), four independent branches: billing finalize (verified ──▶ finalized, open-ended retry) · complete the appointment (checked_in ──▶ completed) · follow-up intent (stub) · analytics intent (stub) each step stamps a settlement marker on the visit once it landed or reached a terminal outcome (visit_0002) visit-downstream-sweeper (every 60 s): starts the workflow for completed visits whose marker is still NULL after 30 s. visit-reconciler (every 60 s): settles completed visits whose billing or appointment marker is still empty after 10 min.
8 · Layered idempotency
1 database arbiters: uq_appointments_active_slot · idempotency key row (caller, key, body hash) · conditional UPDATE … WHERE status = expected · uq_visits_appointment · history uniques 2 workflow id : deterministic ids, USE_EXISTING + REJECT_DUPLICATE (namespace retention 24 h) 3 activities : idempotent by construction; Billing calls carry Idempotency-Key; audit dedupe_key
4 · Connected trace
Gateway (server span, W3C traceparent) └─▶ Provider (httpx client span) ├─▶ Organization (reference check, client span) └─▶ Identity (JWKS fetch on cache miss, client span) Spans exported over OTLP to Jaeger; one OpenTelemetry service name and one Prometheus job per service. Observed as one trace via Jaeger's query API; not yet viewed in the Jaeger UI.
9 · Appointment state machine and the check-in window (Phase 2.1, M1)
pending ──▶ confirmed booking saga confirm (slot held ──▶ booked) pending ──▶ failed saga rejected or compensated · hold reaper (hold_expired) · reconciler (workflow_lost) confirmed ──▶ checked_in Visit, via POST /internal/appointments/{id}/check-in (Visit service token only) checked_in ──▶ completed VisitCompleted appointment branch, POST /internal/appointments/{id}/complete confirmed ──▶ no_show reconciler sweep once slot end + SCHEDULING_NO_SHOW_GRACE_MINUTES (30) has passed confirmed ──▶ cancelled CancelWorkflow confirmed ──▶ confirmed RescheduleWorkflow (new slot) cancel / reschedule of checked_in, completed or no_show ──▶ 409 (appointment already checked in / already completed / was a no-show) Window: opens SCHEDULING_CHECKIN_OPENS_BEFORE_MINUTES (60) before slot_start, closes at slot_end (+0), judged by the DATABASE clock in the same locking SELECT that reads the row; 409 check-in window not open / check-in window closed / appointment not confirmed. Check-in: Visit ──internal check-in──▶ Scheduling (confirmed ──▶ checked_in, history row) ──▶ then Visit inserts the visit. A crash in between converges on the next request (Scheduling answers 200 "already", the visit is then created). pending, confirmed, checked_in, completed and no_show all hold their slot: uq_appointments_active_slot and ex_appointments_patient_no_overlap cover them (scheduling_0004).
10 · Provider schedule change (Phase 2.1, M2)
Admin / provider ──PATCH or deactivate a template, deactivate a provider──▶ Provider ONE tx: the change + a schedule_change_events row (template_updated | template_deactivated | provider_deactivated) Schedule scheduling-schedule-change-poller (every 15 s) ──▶ ScheduleChangePollerWorkflow ──▶ poll activity: GET /internal/schedule-changes (Scheduling token, aud provider, oldest first, up to 100) start schedule-change-{event id} (start_once), THEN POST /internal/schedule-changes/{id}/ack (at-least-once, idempotent) ScheduleChangeWorkflow: apply (pass 1) ──▶ durable sleep (hold TTL + 1 min) ──▶ apply (pass 2) apply = set difference: re-expand the provider's CURRENT templates; every future slot whose (start, end) is not in that set is stale stale available ──▶ withdrawn (cancelled) stale held ──▶ skipped in pass 1, re-evaluated in pass 2 stale booked ──▶ appointment FLAGGED (schedule_change_flagged_at / _reason, scheduling_0005), stays confirmed; staff worklist GET /api/appointments?flagged=true&status=confirmed; cancel or reschedule WITHDRAWS the stale slot active provider ──▶ insert the missing future slots (ON CONFLICT DO NOTHING) Open: a slot still held when pass 2 runs gets no third pass · delivered events are never purged · waitlist entries of a deactivated provider are untouched.
11 · Reconcilers (Phase 2.1, S4)
Schedule scheduling-reconciler (every 60 s, overlap SKIP) ──▶ ReconcilerWorkflow, three idempotent activities, batch cap 50, oldest first: 1 stuck pending pending older than 10 min and booking-{id} gone in Temporal ──▶ void billing, release hold, fail (workflow_lost), offer slot to the waitlist billing lookback: failed (hold_expired | workflow_lost) in the last 24 h without a void note ──▶ void billing 2 stuck waitlist entry matched for more than 15 min ──▶ waiting (lost race) | failed (reason) | booked (from its appointment) 3 no-show sweep confirmed, slot end + 30 min passed ──▶ Billing no_refund, then no_show (re-read as confirmed just before Billing) Schedule visit-reconciler (every 60 s, plus one pass at worker start) ──▶ VisitReconcilerWorkflow: completed visits whose billing or appointment marker is empty after 10 min ──▶ the same step bodies and idempotency keys as VisitCompleted Temporal unreachable ──▶ the step is skipped, never a guess. Cancel / reschedule billing remains bounded (*_incomplete:billing_pending).
12 · Refresh rotation and identity carry-overs (Phase 2.1, C1-C3)
POST /api/auth/refresh ──▶ validate token + current user row ──▶ Redis SET revoked:{refresh jti} NX EX (atomic claim) first claim ──▶ 200 new access token (rjti claim) + NEW refresh token reuse or revoked ──▶ 401 Redis down ──▶ 503, not consumed Logout ──▶ denylist the access jti and the paired refresh jti (rjti) (access tokens from before the change revoke only themselves) bcrypt hash / verify run on a bounded thread pool (IDENTITY_BCRYPT_THREADS=4), never on the event loop Email: normalized (strip, lowercase), looked up by lower(email), unique index uq_users_email_lower (identity_0002; no row is rewritten) Lists: patients, providers, clinics ──▶ plain array, limit 1..200 (default 50), offset >= 0, X-Total-Count, order (created_at, id), 422 outside bounds GET /api/patients/me (own profile) · a provider reads only their own appointments (503 if Provider is down)

Known limitations and unverified items

  • Gateway buffers whole request bodies with no size cap (the limiter bounds request count, not size).
  • One shared Redis holds the denylist and rate-limit counters: an outage fails the limiter open and token verification closed (503); a flush would drop revocations.
  • Application containers run as root. (Service tokens gained aud in Phase 2.)
  • Phase 3 replaces the interim mechanisms: pending-booking starter and visit sweeper → transactional outbox; notification / follow-up / analytics stubs → Celery and Kafka; polling → events. Temporal auto-setup is not the production topology.
  • Workers expose no metrics. Waitlist: FIFO per provider, cap 5 tries per freed slot, no priority, no patient notification. Mongo audit is not atomic with the Postgres commit (WR-04).
  • Load and NFRs are targets, not results (Phase 2.1): NFR-01..08 and a runnable k6 load test exist (docs/nfr.md, loadtest/README.md) but are not yet measured; the full profiles have never run against the real stack and the local stack is not claimed to meet NFR-01 or NFR-02. Phase 3 measures them.
  • Audit after a committed step is best effort (S3): a failed Mongo write is logged as audit.write_failed and the outcome stands; the entry can be lost if Mongo is down at that instant (the transition is durable in appointment_status_history). Phase 3's transactional outbox is the general fix.
  • Polled, not event-driven: schedule changes (15 s) and reconcilers (60 s). Delivered change events are never purged; waitlist entries of a deactivated provider are untouched; a slot still held at the schedule-change second pass gets no third pass.
  • Cancel and reschedule billing is still bounded (*_incomplete:billing_pending, for an operator); only visit billing retries open-endedly. Reconcilers are oldest first with a batch cap (50 / 100) and no per-row backoff.
  • no_show is set by the sweep only; visits created before Phase 2.1 settle their appointment as not_checked_in (no backfill); a checked_in appointment with no visit is not reconciled.
  • Refresh tokens are single-use (store the rotated token); tokens issued before the change have no rjti; legacy mixed-case emails are matched, not rewritten. Appointment lists have no X-Total-Count; provider reads need Provider up (503 otherwise).
  • Local/dev only, synthetic data only. Logout, PHI log-safety and database isolation are implemented but not fully hardened.
  • Not verified: real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, a person viewing the trace in the Jaeger UI, and the scripts/bootstrap_admin.py admin-creation branch (tests only cover the no-op path because the harness always has an admin). Key rotation is supported through kid but not exercised.
  • Assumptions awaiting mentor confirmation: the provider → department → clinic scope chain relies on write-time validation (ORG-03); overlapping availability templates remain allowed (PPL-03); clients combining services may briefly see stale cross-service state (PPL-04).
