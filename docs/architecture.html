Flows

1 · Gateway request flow
Client ──Bearer access token──▶ Gateway ├─ path safety: no dot segments, encoded / \ NUL ──▶ else 404 ├─ route table (no /internal prefix exists) ──▶ no match: 404 ├─ Redis: fixed-window counter (auth 20/min, other 300/min) │ over budget ──▶ 429 + Retry-After │ Redis down ──▶ fail OPEN (warning log + counter) └─ forward to owning service (hop-by-hop stripped, traceparent added) ├─ verify RS256 locally · denylist · RBAC · clinic scope ├─ service database: read / write, one commit └─ MongoDB: append audit_log (field names only) upstream unreachable ──▶ 503 upstream timed out ──▶ 504 no JWT check and no retries at the edge; reads return ids only
2 · Reference-check flow (D-05) — fail closed
Client ──POST /api/providers { department_id }──▶ Gateway ──▶ Provider Provider ──GET /internal/departments/{id} (caller's JWT forwarded)──▶ Organization up to 3 attempts, backoff, GET and transport errors only 200 active ──▶ INSERT provider (department_id is a plain UUID) ──▶ 201 missing or inactive ──▶ 422, nothing written owner unreachable / 401 / 403 / 5xx ──▶ 503, nothing written Deactivation never cascades (D-06). Phase 3 built Kafka and the outbox but not event-fed local copies, so these checks are unchanged (D-08 stays open).
3 · Token verification via JWKS
Identity: login ──▶ sign access + refresh JWT (RSA private key, kid smarthealth-identity-1) Any service: request + Bearer token JWKS cache empty / older than 300 s / unknown kid (30 s backoff) ──▶ GET /.well-known/jwks.json verify signature by kid, algorithm and claims locally Redis: jti denylisted? ──▶ yes: 401 Redis unreachable: 503 (fail closed) ──▶ RBAC ──▶ handler Only Identity holds the private key (Compose secret, gitignored file). Service tokens: 60 s, aud-scoped (Phase 2).
5 · Booking saga with compensation (Phase 2)
Client ──POST /api/appointments + Idempotency-Key──▶ Scheduling one tx: idempotency row + appointment pending (uq_appointments_active_slot: a taken slot ──▶ 409) start booking-<id> on Temporal ──▶ 202 { appointment_id, status_url } (client polls) scheduling-worker (scheduling-tq): 1 validate patient / provider / clinic active, via /internal + service token 2 reserve slot available ──▶ held (held_until = now + 10 min) 3 billing pre-check: pending ──▶ verified | failed 4 confirm slot held ──▶ booked · appointment pending ──▶ confirmed 5 notification intent only, best-effort, requested after confirm — never fails the booking on failure, reverse order, forward transitions only (no deletes), one audit entry per step: void billing (failed ──▶ voided) ──▶ release hold (held ──▶ available) ──▶ appointment failed (reason) ──▶ (top-level booking that held the slot, not a lost race) start waitlist-advance for the freed slot Order note: the notification is requested after confirm (SCHED-02 lists notification earlier; the implementation differs on purpose), so a booking that fails at confirm sends no notification. Both changes are workflow.patched; a slot that already started is 422 "slot has already started".
6 · Cancel, reschedule, waitlist advance
Cancel : cancel + release slot ──▶ billing refund_pending ──▶ refunded (> 24 h ahead) | no_refund (staff may waive) ──▶ notification intent ──▶ start waitlist-advance child Reschedule : hold new slot ──▶ ONE tx: release old, book new, repoint appointment ──▶ re-link billing ──▶ notify ──▶ waitlist advance Waitlist : FIFO claim (FOR UPDATE SKIP LOCKED) of the first matching waiting entry ──▶ child BookingWorkflow booked ──▶ entry booked · booking failed ──▶ entry failed, try next (cap 5) · lost race ──▶ entry back to waiting
7 · Visit completion — commit and outbox row first, downstream after (trigger changed in Phase 3)
Provider ──POST /api/visits/{id}/complete──▶ Visit ONE tx: in_progress ──▶ completed + history row + outbox row (visit.completed), downstream_started_at = NULL ──▶ 200 (no Temporal call) Debezium (visit-outbox) ──▶ smarthealth.visit.events ──▶ visit-consumer (group visit-downstream): start visit-completed-<id> (REJECT_DUPLICATE) ──▶ marker = now (the only trigger; the sweeper is retired) visit-worker (visit-tq), four independent branches: billing finalize (verified ──▶ finalized, open-ended retry) · complete the appointment (checked_in ──▶ completed) · follow-up intent record · analytics intent record each step stamps a settlement marker on the visit once it landed or reached a terminal outcome (visit_0002) visit-reconciler (every 60 s): settles started-but-unsettled visits (marker still empty after 10 min). Retired: the visit-downstream-sweeper Schedule is deleted at every visit-worker start; its workflow stays registered as a no-op tombstone.
8 · Layered idempotency
1 database arbiters: uq_appointments_active_slot · idempotency key row (caller, key, body hash) · conditional UPDATE … WHERE status = expected · uq_visits_appointment · history uniques 2 workflow id : deterministic ids, USE_EXISTING + REJECT_DUPLICATE (namespace retention 24 h) 3 activities : idempotent by construction; Billing calls carry Idempotency-Key; audit dedupe_key
4 · Connected trace
Gateway (server span, W3C traceparent) └─▶ Provider (httpx client span) ├─▶ Organization (reference check, client span) └─▶ Identity (JWKS fetch on cache miss, client span) Spans exported over OTLP to Jaeger; one OpenTelemetry service name and one Prometheus job per service. Observed as one trace via Jaeger's query API; not yet viewed in the Jaeger UI.
9 · Appointment state machine and the check-in window (Phase 2.1, M1)
pending ──▶ confirmed booking saga confirm (slot held ──▶ booked) pending ──▶ failed saga rejected or compensated · hold reaper (hold_expired) · reconciler (workflow_lost) confirmed ──▶ checked_in Visit, via POST /internal/appointments/{id}/check-in (Visit service token only) checked_in ──▶ completed VisitCompleted appointment branch, POST /internal/appointments/{id}/complete confirmed ──▶ no_show reconciler sweep once slot end + SCHEDULING_NO_SHOW_GRACE_MINUTES (30) has passed confirmed ──▶ cancelled CancelWorkflow confirmed ──▶ confirmed RescheduleWorkflow (new slot) cancel / reschedule of checked_in, completed or no_show ──▶ 409 (appointment already checked in / already completed / was a no-show) Window: opens SCHEDULING_CHECKIN_OPENS_BEFORE_MINUTES (60) before slot_start, closes at slot_end (+0), judged by the DATABASE clock in the same locking SELECT that reads the row; 409 check-in window not open / check-in window closed / appointment not confirmed. Check-in: Visit ──internal check-in──▶ Scheduling (confirmed ──▶ checked_in, history row) ──▶ then Visit inserts the visit. A crash in between converges on the next request (Scheduling answers 200 "already", the visit is then created). pending, confirmed, checked_in, completed and no_show all hold their slot: uq_appointments_active_slot and ex_appointments_patient_no_overlap cover them (scheduling_0004).
10 · Provider schedule change (Phase 2.1, M2)
Admin / provider ──PATCH or deactivate a template, deactivate a provider──▶ Provider ONE tx: the change + a schedule_change_events row (template_updated | template_deactivated | provider_deactivated) Schedule scheduling-schedule-change-poller (every 15 s) ──▶ ScheduleChangePollerWorkflow ──▶ poll activity: GET /internal/schedule-changes (Scheduling token, aud provider, oldest first, up to 100) start schedule-change-{event id} (start_once), THEN POST /internal/schedule-changes/{id}/ack (at-least-once, idempotent) ScheduleChangeWorkflow: apply (pass 1) ──▶ durable sleep (hold TTL + 1 min) ──▶ apply (pass 2) apply = set difference: re-expand the provider's CURRENT templates; every future slot whose (start, end) is not in that set is stale stale available ──▶ withdrawn (cancelled) stale held ──▶ skipped in pass 1, re-evaluated in pass 2 stale booked ──▶ appointment FLAGGED (schedule_change_flagged_at / _reason, scheduling_0005), stays confirmed; staff worklist GET /api/appointments?flagged=true&status=confirmed; cancel or reschedule WITHDRAWS the stale slot active provider ──▶ insert the missing future slots (ON CONFLICT DO NOTHING) Open: a slot still held when pass 2 runs gets no third pass · delivered events are never purged · waitlist entries of a deactivated provider are untouched.
11 · Reconcilers (Phase 2.1, S4)
Schedule scheduling-reconciler (every 60 s, overlap SKIP) ──▶ ReconcilerWorkflow, three idempotent activities, batch cap 50, oldest first: 1 stuck pending pending older than 10 min and booking-{id} gone in Temporal ──▶ void billing, release hold, fail (workflow_lost), offer slot to the waitlist billing lookback: failed (hold_expired | workflow_lost) in the last 24 h without a void note ──▶ void billing 2 stuck waitlist entry matched for more than 15 min ──▶ waiting (lost race) | failed (reason) | booked (from its appointment) 3 no-show sweep confirmed, slot end + 30 min passed ──▶ Billing no_refund, then no_show (re-read as confirmed just before Billing) Schedule visit-reconciler (every 60 s, plus one pass at worker start) ──▶ VisitReconcilerWorkflow: completed visits whose billing or appointment marker is empty after 10 min ──▶ the same step bodies and idempotency keys as VisitCompleted Temporal unreachable ──▶ the step is skipped, never a guess. Cancel / reschedule billing remains bounded (*_incomplete:billing_pending).
12 · Refresh rotation and identity carry-overs (Phase 2.1, C1-C3)
POST /api/auth/refresh ──▶ validate token + current user row ──▶ Redis SET revoked:{refresh jti} NX EX (atomic claim) first claim ──▶ 200 new access token (rjti claim) + NEW refresh token reuse or revoked ──▶ 401 Redis down ──▶ 503, not consumed Logout ──▶ denylist the access jti and the paired refresh jti (rjti) (access tokens from before the change revoke only themselves) bcrypt hash / verify run on a bounded thread pool (IDENTITY_BCRYPT_THREADS=4), never on the event loop Email: normalized (strip, lowercase), looked up by lower(email), unique index uq_users_email_lower (identity_0002; no row is rewritten) Lists: patients, providers, clinics ──▶ plain array, limit 1..200 (default 50), offset >= 0, X-Total-Count, order (created_at, id), 422 outside bounds GET /api/patients/me (own profile) · a provider reads only their own appointments (503 if Provider is down)
13 · Booking event flow (Phase 3)
Client ──POST /api/appointments──▶ Scheduling ──one tx: idempotency row + appointment pending (no outbox row)──▶ 202 (accept path unchanged) scheduling-worker, confirm step: ONE tx = appointment confirmed + slot booked + history row + outbox row (appointment.booked) Postgres WAL ──▶ Debezium scheduling-outbox ──▶ smarthealth.appointment.events (key = appointment id; headers id, eventType, traceparent, schemaVersion; Avro value) ├─▶ notification-consumer (group notification-trigger): notifications.send on queue notifications.booking ──▶ notification-celery ──▶ fake provider (once per dedupe key) │ start reminder-<appointment> on notification-tq (durable timers) └─▶ analytics-consumer (group analytics-projection): ONE tx in analytics_db = claim the event id in processed_events + upsert the projection Synchronous work added to booking: only the outbox insert inside confirm. Everything right of the commit is asynchronous. "Every state change" means the ten D-07 event types; billing transitions, waitlist changes, visit in-progress and reconciler or hold-reaper actions are not evented.
14 · Cancel and reschedule (Phase 3)
Cancel : ONE tx = appointment cancelled + slot released + history row + outbox row (appointment.cancelled) Reschedule : ONE swap tx (release old slot, book new, repoint) + outbox row (appointment.rescheduled: old and new slot ids and starts) A repeat or a refused change emits nothing; the event id is derived from the post-transition version. notification-consumer: cancelled ──▶ record the appointment closed, signal cancel to reminder-<id>, one cancellation notice rescheduled ──▶ one notice, signal-with-start moves the reminder to the new slot (its dedupe key carries the slot epoch) no_show ──▶ no notice, the reminder stops · checked_in ──▶ the reminder stops analytics-consumer: cancelled ──▶ cancelled_at on the projection row · rescheduled ──▶ count + 1, slot_start replaced only by a newer event
15 · Notifications and reminders (Phase 3)
Delivery : Celery task notifications.send (acks_late, prefetch 1, JSON) ──▶ delivery log (notification_deliveries, unique dedupe_key) ──▶ fake provider (notification_provider_calls, unique dedupe_key; the insert is the delivery) Retries : exponential backoff (base 2 s, up to 5); permanent failures, malformed messages and unexpected errors ──▶ notifications.dlq (never silently acknowledged) Guards : a reminder for a closed appointment is skipped_closed; booking-type events older than NOTIFICATION_MAX_EVENT_AGE_MINUTES (1440) are skipped_stale Reminders : Temporal ReminderWorkflow reminder-<appointment>: leads 1440,120 minutes before the slot, signal-interruptible timers; a fired timer enqueues the same send task Honest : one send per dedupe key holds at the delivery log and at the fake provider; proven by killing a real worker between the provider call and mark_sent. A real SMS or email provider must accept an idempotency key for the same guarantee; without it each crash at that point can cause one duplicate. The Phase 2 notification activities in the workflows are intent records and send nothing.
16 · Analytics (Phase 3)
patient, appointment, visit topics ──▶ analytics-consumer ──▶ analytics_db (processed_events, patients, appointments, visits_completed, five views) Definitions: total patients = registered and not deactivated (current count) · booked and completed per UTC day · cancellation rate = cancelled / booked in the window · average wait = visit start minus check-in · an empty denominator is no data (null), never 0 Start : ANALYTICS_CONSUMER_START=latest with pinned go-live offsets: metrics count from go-live; total patients counts only patients registered after it Rebuild : stop analytics-consumer, dry run, --apply, start it; replays everything still retained, including throwaway test events. processed_events has no retention. Served by : GET /api/analytics/summary and /timeseries (admin, front desk) and Grafana as the SELECT-only grafana_ro role.
17 · Delivery semantics (Phase 3)
No loss : the event exists exactly when the state change committed; the replication slot keeps WAL until Connect confirms it At-least-once : a hard kill of Connect re-emits events (measured: 5 duplicates of 11 messages; 2 copies of one event id with 1 distinct id) Effect level : every consumer is idempotent: processed_events claim in the effect's tx · deterministic workflow id (REJECT_DUPLICATE) · dedupe key at the send ──▶ forced redelivery and offset rewinds of all three groups left every effect at one (effect-level exactly-once) Ordering : per aggregate (key = aggregate id, one partition); none across topics; the projections tolerate any order

Known limitations and unverified items

  • Gateway buffers whole request bodies with no size cap (the limiter bounds request count, not size).
  • One shared Redis holds the denylist and rate-limit counters: an outage fails the limiter open and token verification closed (503); a flush would drop revocations.
  • Application containers run as root (the notification and Celery containers too; Celery warns). The Semgrep missing-user Dockerfile findings are accepted for now by the user; production hardening is deferred. (Service tokens gained aud in Phase 2.)
  • Interim mechanisms after Phase 3: the visit sweeper is retired (the visit.completed outbox event is the only downstream trigger); the pending-booking starter, hold reaper and both reconcilers stay as safety nets because events do not subsume them (the accept path writes no outbox row; an expired hold emits nothing). The workflow notification, follow-up and analytics activities are intent records that send nothing. Temporal auto-setup is not the production topology.
  • Waitlist: FIFO per provider, cap 5 tries per freed slot, no priority, no patient notification. Mongo audit is not atomic with the Postgres commit (WR-04); moving it into the outbox is deferred. Workers and consumers are now scraped on internal ports.
  • Delivery: at-least-once on the wire (5 duplicates of 11 messages after a hard Connect kill; 2 copies of one event id), effect-level exactly-once through idempotent consumers. A real SMS or email provider must accept an idempotency key for the one-send-per-dedupe-key guarantee; otherwise each crash between the provider call and mark_sent can cause one duplicate.
  • EVENT-04 deviation: the analytics projections run on the analytics-projection Kafka consumer, not on Celery (they need the processed-event claim in the effect's own transaction); Celery covers notifications and follow-ups. The user accepted this at plan 03-01; the wording of EVENT-04 in REQUIREMENTS.md is the user's decision.
  • Analytics start at go-live (D-13): ANALYTICS_CONSUMER_START and NOTIFICATION_CONSUMER_START are latest with pinned offsets; total_patients counts only patients registered after go-live; a rebuild replays everything still retained, including throwaway test events; processed_events has no retention. "Every state change" means the ten D-07 event types.
  • Operations: replication slots retain WAL while Connect is down (max_slot_wal_keep_size=2GB; a heartbeat action query keeps quiet databases confirming WAL; deleting a connector does not drop its slot); the outbox and topics are never pruned; Kafka, Schema Registry and Connect have no authentication on the dev network (production: SASL/TLS, ACLs, Connect REST auth); Schema Registry is a cached write-path dependency (a cold start during an outage cannot become ready); provider.schedule_changed is published but not consumed and the schedule-change poller stays paused (user decision); the gateway rate budgets used for tests are a test-time setting.
  • Load and NFRs are targets, not results (Phase 2.1): NFR-01..08 and a runnable k6 load test exist (docs/nfr.md, loadtest/README.md) but are not yet measured: sustained, burst and contention were not run (deferred by the user until after Phase 3). smoke crossed its thresholds twice in plan 02.1-13 (heavily loaded laptop), then passed every threshold in three runs (accept p95 21.8, 29.3 and 49.1 ms; saga p95 about 0.52 s; the host load differed, and accept latency crept up, so it is the number to watch). The local stack is not claimed to meet NFR-01 or NFR-02.
  • Audit after a committed step is best effort (S3): a failed Mongo write is logged as audit.write_failed and the outcome stands; the entry can be lost if Mongo is down at that instant (the transition is durable in appointment_status_history). Carrying audit in the outbox is the natural fix; Phase 3 built the outbox and deferred that.
  • Still polled: schedule changes (15 s, and that poller is paused) and reconcilers (60 s). Delivered change events are never purged; waitlist entries of a deactivated provider are untouched; a slot still held at the schedule-change second pass gets no third pass.
  • Cancel and reschedule billing is still bounded (*_incomplete:billing_pending, for an operator); only visit billing retries open-endedly. Reconcilers are oldest first with a batch cap (50 / 100) and no per-row backoff.
  • no_show is set by the sweep only; visits created before Phase 2.1 settle their appointment as not_checked_in (no backfill); a checked_in appointment with no visit is not reconciled.
  • Refresh tokens are single-use (store the rotated token); tokens issued before the change have no rjti; legacy mixed-case emails are matched, not rewritten. Appointment lists have no X-Total-Count; provider reads need Provider up (503 otherwise).
  • Local/dev only, synthetic data only. Logout, PHI log-safety and database isolation are implemented but not fully hardened.
  • Not verified: real-socket outage behaviour of the synchronous checks, a cold start from an empty volume, a person viewing the trace in the Jaeger UI, and the scripts/bootstrap_admin.py admin-creation branch (tests only cover the no-op path because the harness always has an admin). Key rotation is supported through kid but not exercised.
  • Assumptions awaiting mentor confirmation: the provider → department → clinic scope chain relies on write-time validation (ORG-03); overlapping availability templates remain allowed (PPL-03); clients combining services may briefly see stale cross-service state (PPL-04).
